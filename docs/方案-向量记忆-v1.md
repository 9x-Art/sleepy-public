## 0. 先给结论

**向量记忆要做的事只有一件**：现在角色「想不起来」的东西，靠语义能找到。

现在的记忆注入（`page-memory.js:342 getMemoryInjection`）是**规则挑**：
锚点 → 边界 → 纠正 → 最近的，凑够 6 条。它挑得出「你讨厌什么」，
挑不出「上次聊到海的时候说的那句话」—— 因为后者没有任何标签能命中。

所以 v1 就做**一个检索层**，不做 v5 那套完整的多路召回 + 七路重排。
一句话概括取舍：

> **进向量的只有「原话与事件」；规则与状态（禁区/身份/承诺/授权）继续固定注入，
> 永远不走向量。**（v5 §9.5 那条红线，照抄）

## 2. 哪些进向量库（这一节是重点）

### 进：原始文本块（v5 §8.2 的源料）

| 源 | 切块建议（v5 原值） | 备注 |
|---|---|---|
| 线上聊天 | 4～6 轮 或 600～1000 字，相邻块少量重叠 | 主料 |
| 线下场景 | 2～4 轮 或 1000～1600 字，**优先在动作/小情节结束处切** | 线下是长文，切点比长度重要 |
| 朋友圈动态 | 按**动态事件包**（动态 + 互动 + 图一起算一个包） | v5 §6.1 已设计过 |
| 日记 | 按篇 | 它是「TA 代笔写的」，天然是记忆素材 |
| 记忆库里的档案条目 | 每条一个向量（`memories[]` 里 active 的） | 档案是提炼过的事实，比原文更该被找到 |

### 不进：确定性信息（固定注入，绝不走向量）

照抄 v5 §9.5：

- user 明确禁区 / 边界
- 当前身份与关系定义（大小号、认知模式 —— 这些走 I01，本来就不进记忆）
- 最近明确纠正
- 尚未兑现的重要承诺
- 当前线下续接状态
- 当前已生效的 App 授权（查手机、朋友圈权限）

理由很直白：**向量是「可能相关」，这些是「每轮都必须在」**。
放进向量就会出现「今天要跟他说的事，因为语义分数低没被召回」这种事故。

### 灰色地带，我的判断（要你拍）

| 东西 | 我的建议 | 理由 |
|---|---|---|
| **帷境的剧本正文** | **绝对不进** | 它是虚构作品。v5 那条「共读的故事仍然是假的」如果被向量打破，角色就会拿剧本里的事当亲历讲出来 —— 这是帷境红线（收藏≠分享≠共读≠定史）的地基。**共读事件**（谁和谁一起读过什么）可以进，那是真发生过的事。 |
| 帷境定史写回的事实 | **进** | 它是用户逐条批过的结构化事实，是「最真」的那一档。 |
| **查手机里 TA 自己的内容**（备忘 / 订单 / 健康 / 草稿） | **进**（2026-09-22 用户修正） | 那是 **TA 自己的手机、TA 自己的生活** —— 他自己买的东西、写的备忘，当然该在 TA 的记忆里。查手机施工卡第 5 批本来就写着「App 数据进聊天（确定性注入 + 检索）」。我第一版把这条画窄了。 |
| **「user 翻过他手机」这件事** | **不进** | 这是另一回事：它按「**被察觉才注入**」的规则走（现有 `[手机痕迹]` 那段就是干这个的），不走检索。混淆这两件事会让 TA 记住他不该知道的事。 |
| 角色的内心 / 心声（`heartbeats`） | **不进** | 那是状态不是记忆；而且它已经是「没说出口的话」，被召回进对话会很怪。 |
| 群聊消息 | v1 **先进**，但不单独开一路 | 群里的话也是 TA 看见过的，但它有「谁能看见」的可见性问题，比私聊复杂。先当普通文本块进，可见性那层以后再说。 |

## 3. 最小方案（比 v5 简在哪）

v5 的 §9 有七路候选 + 六个权重的重排 + 邻块扩展 + 去重。**v1 砍到两路 + 一条硬规则**：

```
查询 = 最近 1～2 轮原文 + 当前场景/人名（本地规则抽，不调模型）  ← v5 §9.1 照做
      ↓
候选 = ① 向量语义 top-N（N≈12）
       ② 现有本地规则（锚点 / 最近 active / 世界书关键词命中）   ← 已经在跑，不另写
      ↓
重排 = 硬过滤（角色权限、岛、状态 active、非错误身份）→ 向量分 + 时间近的微调
      ↓
注入 = 3～6 条，拼成一段【相关的过去】，和现有 getMemoryInjection 的输出并列
```

**砍掉的**：七个权重表（改成「向量分 + 时间」）、邻块扩展（v1 不做，看效果再说）、
事件簇。

**调用时机**（v5 §8.3，照抄但可以再懒一点）：
- 线上：累计 12～20 轮，或旧块快离开近期窗口
- 线下：6～10 轮
- App：批次满 / 退到后台时
- 失败保留本地队列重试，**绝不阻塞聊天**

**存在哪**（这条 v5 没写，但必须定）：**IndexedDB，不是 localStorage**。
1536 维 float32 一条就 6KB，本地存档那点配额几百条就爆。
项目里 `media.js` 已经走 IndexedDB 了，照它那套用即可。

**存什么**（2026-09-22 实现时定的，比这一版多两样）：
```
{ id, rootId, charId, userId, sandboxId, chatId,
  kind, at, fromId, toId, msgCount, text, vec }
```
`rootId / charId / userId` 是**召回隔离的判据**（哪个大脑 / 哪张皮 / 面对谁），
照 core 记忆那套「四元组可溯源」的规矩来，不能只按 charId 隔离。

> ⚠️ 「向量是索引，不是副本」这句**只对一半** —— 实现里块**存了一份 `text`**。
> 破例的两个理由：召回必须回填**原文块**才准（只给摘要的「准」是假的）；
> 消息会被删、被编辑、线下会话会被清，只存 id 的话召回时可能什么都取不回来。
> **准确说法**：向量不是事实源，事实源仍是聊天存档；索引里那份原文是
> **本地缓存**，不能脱离原始消息独立存在 —— 原文被删/被改、权限变化、
> 换世界时，索引要跟着失效（现在只做到「换世界过滤」，见 §6）。

**成本**：embedding 是便宜模型，但**块数会很多**。建议一开始就带上限
（比如最多保留 N 条/角色）+ 一个「向量记忆：开 / 关」的开关在设置里。

## 3.5 终态长什么样（用户问「建议最后要能做到什么程度」）

**结论：两路不是「临时简化」，它就是终态的合理形态。** 但有一处要留接口。

为什么这么说 —— 把 v5 §9.2 那七路候选拆开看，其实只有一路真需要向量：

| v5 的候选路 | 靠什么实现 | 需要 embedding 吗 |
|---|---|---|
| ① 向量语义候选 | 向量 | ✅ **只有它** |
| ② 关键词与实体精确匹配 | 本地字符串/实体匹配 | ❌（世界书已经在这么干） |
| ③ 近期相关项 | 按时间取 | ❌ |
| ④ 未完成承诺 / 待办 | 结构化状态查询 | ❌ |
| ⑤ user 手动锚点 | `isAnchor` 标记 | ❌ |
| ⑥ 当前关注队列 | `attentionInbox` 查询 | ❌ |
| ⑦ 同一场景 / 事件簇 | 按 sceneId / 事件 id 取 | ❌ |

重排那六个权重也是同理：「实体吻合 / 时间相关 / 未完成关联」都能用规则算，
「语义相似度」才是向量的活。

**所以终态 = 两路候选 + 一条简单重排**，剩下的五路本来就该走本地规则，
它们不进向量库、也不参与向量打分。

**唯一要提前留的接口**：召回是「打分 + 取前 N」，别写死成「向量分排序取前 6」。
留一个 `rank(candidates) → 排序后` 的钩子，将来要加权重都在这一处。

**什么时候真的需要补重排**（给你一个可判断的标准）：
- 记忆块数量到 **几百条以上**，向量 top-12 里开始出现明显不相关的；
- 或者你自己用的感觉是「它想起来的经常是错的那些」。

在那之前做六权重是过度设计 —— 调参成本远大于收益。

## 3.6 三档时间尺度（用户问「为什么不是固定两百条」）

用户提出：「固定死六条太少，一般来说都是固定记住两百条对话记忆，然后开向量记忆会准一点。」

**先把三件事分清**（当时它们被说成了一件）：

| 层 | 现状 | 能调吗 |
|---|---|---|
| 近期原文（对话历史） | 默认 **40** 条 | ✅ 设置页可调，**上限就是 200** |
| 记忆库注入（关于对方的记忆） | 配额 12 条 | 内部配额，见 §4.5 |
| 存储 | 对话**完全不裁剪** | — 原料一直都在 |

**「两百条全注入」不是解法**，两条硬理由：
- **token**：200 条 ≈ 1.5 万～4 万 token/轮，每说一句话都烧这个；
- **lost in the middle**：上下文越长，模型对中段的注意力越差。真有用的那条在第 150 条时
  大概率读不到 —— **加长度 ≠ 加记忆**，反而把近处的也冲淡了。

**正确形态是分档**：

| 档 | 内容 | 给法 | 现状 |
|---|---|---|---|
| 近景 | 最近 N 条原文 | 无条件全给（保对话连贯） | ✅ 默认 40，可调至 200 |
| 中景 | 更早的**相关原文块** | **向量召回**，按需回填 | ⏳ 就是这个方案要做的 L4 |
| 远景 | 压缩后的事实 | 记忆库 + 总结 | ✅ 已有 |

**一个决定性条件**：召回必须回填**原文块**，不能只给摘要 —— 只给摘要的话「准」是假的，
因为摘要里没有当时的语气、也没有话是怎么说的。

用户说「池子里得有原料」这一点完全对：`chat.messages` 从建立到现在**没做过任何裁剪**
（只有手工删消息才 filter），所以中景的原料一直在，向量只是给它建索引。

## 4.5 附带修掉的一个真问题：记忆注入的配额（已落地）

用户说「六条太少」，去实测了一下，发现**比「少」严重**：那 6 条里
**一条都没留给「我们一起做过什么」和「我答应过你什么」**。

**实测**（写 3 条边界 + 3 条纠正 + 1 共同经历 + 1 约定 + 1 偏好）：

```
注入条数: 6    共同经历: false    约定: false    事实: false
```

**根子**在旧的配额算法（`page-memory.js`）：

> 锚点（不限）→ boundary 固定抢 3 条 → correction 固定抢 3 条 → 剩下的补到 6。

边界 3 + 纠正 3 正好把 6 格占满，**余量是 0**。也就是说：给「规则类」发了固定配额，
而「经历类」没有任何保底 —— 最该被反复看见的先被挤掉，最不需要每轮重复的反而霸屏。
`promise`（约定）掉得最伤：用户不会觉得「它记性差」，会觉得「它根本不在乎」。

**改法**（`getMemoryInjection`）：

- 配额 6 → **12**；
- ⚠️ **锚点**（用户手标的）不吃配额；**约定**先占座（最多 4 条 —— 越近的越可能还没兑现）；
- **经历类保底一半席位**（`shared_event` / `user_fact` / `preference_*` /
  `relationship_fact` / `habit`）；
- **规则类（boundary / correction）各保底 1 条、上限 3 条** —— 够用就行，不许吃满；
- 每一步按「还剩几格」实时结算，不这么做的话先填的那组会吃满整张表。

**配套：生成参数的默认值只能有一份。** 真机踩到 —— `api.js` 的上下文默认改成 40，
实际请求还是 20：因为 `store.js` 的 `chatDefaults` 里也抄了一份 `contextMessages: 20`，
而它在回落链的第三层、**位置更靠后所以赢**。现在 `chatDefaults` 只留前端行为开关
（`heartbeatAuto`），生成参数统一认 `api.js` 的 `GEN_DEFAULTS`；
老存档由 `store.js` 的 `migrateChatDefaultsGenerative` 把**正好等于旧默认**的键清掉
（用户真改过的值一律留着）。

## 5. 顺手看到的几处补充（跟向量无关，但都是真缺口）

1. **总结还在用主 API** —— `page-summary.js` 文件头自己写着「MVP 跟随主 API」。

   设置页那行「总结 API」也灰着。这个比向量更早该接。
2. ✅ **L1.5「近期生活动态」是空的** —— **2026-09-22 已做（v98）**。

3. **记忆没有「事件时间」** —— 每条记忆只有 `createdAt/updatedAt`（**写入时间**），
   没有「这件事是什么时候发生的」。所以「三年前那个夏天」这类召回天生做不了，
   角色也说不清「那是很久以前还是上个月」。v5 §13.2 只要求绑来源，
   但要做时间感，就得在写入时让总结多输出一个 `when`。
4. **S2 关系罗盘是空的** —— v5 里它管「角色现在想不想推进、能推进到哪一步」。
   现在主动消息只有心绪（charState）+ 关注队列，**没有「推进意图」这一层**。
   表现是：TA 会主动找你，但不会「一步步把关系往前带」。
