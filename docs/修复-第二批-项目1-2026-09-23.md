## 2. 数据语义

**清空全部数据**（非原子，逐项报告）：

```
本地数据(store.clearAll)  ┐
图库(media.available→clear)├─ 三步各自 ok/fail → ok = 全部 ok
向量库(wipeAll 三态)       ┘
```
- 全过 → toast「已清除」+ reload
- 任一步失败 → toast「没清干净：本地数据：已清；图库：失败 —— …；向量库：…」+ **不 reload**
- **没有临时快照**（用户口径：清空不留长期快照）

**导入备份**（七步，顺序固定）：

```
① canImport 完整校验（一个字不写）
② store.exportAll() → 写进 sleepy.rb.pending
③ memoryVec.pauseRecall()（关召回门）
④ await wipeAll()  → failed 就中止（不往下写）
⑤ store.clearAll() → importAll(payload)（覆盖写）
⑥ 写不进去 → 按快照整份恢复 → 删快照 → 开召回门 → 报错
⑦ 成功 → 删快照 → 开召回门 → 调用方 reload
```

**`wipeAll` 三态**：

| 返回 | 含义 | 步骤判定 |
|---|---|---|
| `{status:'cleared'}` | 真清了，且 `total()===0` 复核过 | 过 |
| `{status:'not-applicable', why:'noidb'}` | 本机没有 IndexedDB | 过（「没有对象可清」，不是失败） |
| `{status:'failed', why:'blocked'\|'open'\|'clear'\|'residual'}` | 清理失败 | **失败**（报错，不假成功） |

## 3. 是否需要历史迁移

**不需要。** 本轮只加清理入口与失败语义，**没有改任何键名、字段名或存储结构**：

- `wipeAll` 是新增能力，老存档里没有它产生的数据；
- `canImport` 只是把 `importAll` 里原有的校验规则抽成函数，规则本身一字未改；
- 恢复区 `sleepy.rb.pending` 是**过程态**（成功/失败都立刻删），不会在正常使用中留下；
- 唯一要提醒的是：**用户设备上此刻可能残留着旧向量块**（就是这次要修的问题）。清空一次即清掉；不清也不会立刻出错（但会继续有幻觉源 + 隐私残留）。

## 6. 失败时的回滚方式

| 场景 | 回滚 |
|---|---|
| **导入失败**（清库失败 / 写入失败 / 写不全） | 用恢复区 `sleepy.rb.pending` 的完整快照**整份恢复**（`store.clearAll()` + 逐键写回），**不是按 id 删**；恢复完删快照、开召回门、报错不刷新 |
| **导入成功但用户后悔** | 用自己导出的 `.json` 重新导入（恢复区已按语义删除，**刻意不保留**） |
| **清空失败** | 数据已删的部分无法从本轮流程里恢复（清空本就是不可逆操作，界面上有二次确认）→ 提示逐项结果，让用户自己决定是否再导备份 |
| **`wipeAll` 失败** | 导入流程中止并回滚；清空流程报错不刷新（旧块仍在，属于「没清干净」而不是「清错了」） |

## 7. 我做了两个判断，请你复核

1. **导入第 ⑤ 步我加了 `store.clearAll()`**（你的七步里只写了 `importAll`）。
   理由：`importAll` 是**逐键覆盖**，备份里没有的旧键会残留 —— 那不叫「覆盖」，
   而且残留键会让存储越滚越大。若你要的是「合并式导入」，说一声我把这一步去掉。
2. **导入成功后也调 `releaseRecall()`**（你的口径是「清理完成前不得召回」）。
   理由：成功路径也已 reload，门留着反而会让「reload 被拦下」的极端情况变成**永久不召回**。
