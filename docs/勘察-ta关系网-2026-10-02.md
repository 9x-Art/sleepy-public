# 勘察 · ta 关系网 v1（2026-10-02，只读）

> 输入：《Sleepy · ta 关系网 v1 · 产品与第一批施工设计稿》第 9 节七问。
> 本轮**未改任何业务代码**。全部结论带 path:line 锚点，行号以当前工作区为准。
> 先例模板：`docs/勘察-ta首页-2026-10-02.md`。

## 0. 一句话结论

**壳子、路由、人物集合、权限闸、近况摘要全是现成的；缺的是「人—人关系」本身。**

具体说：现有关系数据只有**两种坐标**——
`links`（char × **user**，带 `relation` 自由文本）和 `charRel:<sbId>`（char × char，**只有三态** known/met/unknown，无文本无时间）。
**NPC 与任何人的关系记录为零**。

所以按设计稿 §3「没有依据的两人之间不画边」如实施工，第一版的关系图是一个
**以当前角色为中心的星形**：中心 ↔ user 有边（有 relation 才显示文本），
中心 ↔ 其他正式角色有边（三态原文，`unknown` 不画），**NPC 只有节点、没有边**——
这不是实现偷懒，是数据现状的忠实投影，且正好落在设计稿「关系未注明 / 保留空态」的允许范围内。

另有一条**硬缺口**：`links` **没有 `updatedAt`、没有来源字段**，
`setRelation()` 改 relation 文本时**不写任何时间戳**（core.js:1156-1167）。
设计稿 §7 要 selector 吐 `updatedAt`、§3 要「来源与更新时间（已有时）」——
这个「已有时」在本仓库**对关系文本而言不存在**。

> **P1–P4 四条决策已于 2026-10-02 拍板并锁定**（全部按推荐），见 §9「拍板结果」。
> §7.1 契约与 §10 施工单已按决策回写，**可直接开工**。

## 1. 正式人物列表与 `core.npcsOfRoom` 的合并读取方式（§9-1）

### 1.1 两个集合，各有唯一出口

| 集合 | 唯一出口 | 位置 | 收谁 |
|---|---|---|---|
| 岛名册正式角色 | `core.charsOfSandbox(sb)` | core.js:460-469 | `sb.charIds` 里查得到的 char（查不到直接跳过） |
| 岛内全体 NPC | `core.npcsOfRoom(sb)` | core.js:542-566 | ① `parentType='sandbox'` + `parentId=岛id`（新口径）② 老数据：挂在岛内 char 名下（`parentType='char'`）③ 老数据：挂在「我」名下（`parentType='user'`） |

`npcsOfRoom` 的注释明确写着它是**全仓唯一口径**（core.js:537-541），
`page-island.js:682-684` 已经改成委托给它（「本文件不再自己查」）。
**不要新写第三个查询**。

### 1.2 现成合并先例 = `page-ta.js` 的 04 区块（照抄对象）

page-ta.js:710-718：

```
core.charsOfSandbox(sid).forEach(...)          // 只收 (c.kind||'main')==='main'，排除中心自己
(core.npcsOfRoom ? core.npcsOfRoom(sb) : [])   // NPC 全收，不判 knownBy
```

两个要点：
- **正式角色要过滤 `kind==='main'`**：`charsOfSandbox` 按 `sb.charIds` 取，
  理论上不含 `sub` 皮套，但首页仍显式判了一次——关系网沿用同一把尺子，保持一致。
- **NPC 目前不过滤 `knownBy`**（这是 §4 的缺口，见 §8）。

### 1.3 草稿天然不在集合里（§8「草稿和未确认 NPC 不出现」零成本成立）

`taNpcDrafts` 是**独立 store 键**（store.js:195-205），
草稿**不进 `characters` 表**（ta-life.js:325-333 注释原文「唯一正式通道 core.upsertChar」，
确认后才回填 `formalCharId`）。
`characters` 表里没有的东西，`charsOfSandbox` / `npcsOfRoom` 都查不到 →
**只要 selector 不主动去读 `taNpcDrafts`，草稿就不可能漏进来**。
冒烟要加**反向断言**：造一条 `status:'draft'` 的草稿，断言节点集合里没有它的名字。

⚠️ 一个陷阱：已确认的草稿记录**仍然留在 `taNpcDrafts` 里**（`status:'confirmed'`，
ta-life.js:356-368），它和正式人物是**两条记录**。selector 千万别用「有草稿记录」当节点来源。

### 1.4 NPC 的权限字段（§4 要用的）

| 字段 | 含义 | 写入点 |
|---|---|---|
| `knownBy: [id...]` | 谁认识 TA（char id 或 user id 混装） | page-island.js:1598（添加 NPC 时勾选） |
| `npcVis: {chat, group, moments}` | 岛内可见性三开关 | page-island.js:1454 / 1600 |

**现成的判定先例**（唯一一处，务必复用口径）——page-switch.js:544-546：

```
var knownBy = Array.isArray(n.knownBy) ? n.knownBy : [];
if (knownBy.indexOf(selfRoot.id) < 0 && knownBy.indexOf(charId) < 0) return;   // 跳过
```

即：**`knownBy` 是空数组 / 不含此人 → 不注入**。关系网要做同一件事，只是把「不注入」换成「不进节点集合」。

## 2. `links` 的真实读取出口、方向和权限字段（§9-2）

### 2.1 表与结构

`links` 登记在 store.js:226，删房名单在 core.js:336-364（`scoped` 数组，**已收录**）。

字段全集（`addLink` core.js:1127-1151 + `setRelation` :1156 + `FEED_PERM_KEYS` :1189）：

```
{ id, charId, userId, cognition, barrier, relation,
  createdAt,            // ← 唯一的创建时间；**没有 updatedAt**
  iHideChar, iHideFromChar, charHidesMe, charHidesFromMe,
  sandboxId }           // tagScope 盖章
```

### 2.2 读取出口（三个，语义不同，别混用）

| 出口 | 位置 | 返回 | 用途 |
|---|---|---|---|
| `core.findLink(charId, userId, sandboxId)` | core.js:1077-1086 | **深拷贝** | **只读**（关系网用这个） |
| `core.linkSlot(charId, userId, sandboxId)` | core.js:1104-1113 | `{list, hit}`，hit 是**快照引用** | 只给**写**用 |
| `core.relationOf(charId, userId, sandboxId)` | core.js:1215-1218 | `relation` 字符串 | 只要文本时的捷径 |

⚠️ **两条铁律**（core.js:1088-1103、1119-1126 原文）：
1. 改 `findLink()` 的返回值 = 什么都没改（深拷贝）。关系网只读，天然安全，但注释里要写死。
2. **同一对 (char × user) 在每间房各有一条 link**，全量列表里第一条很可能是别的存档那条 →
   读取**必须带 `sandboxId`**。切岛不串数据（§8 验收项）全靠这条。

### 2.3 方向

`link` 的坐标是 **(charId, userId)**，**单向一条、双向语义**（同一行既是我看 TA 也是 TA 看我）。
「谁能看谁的」由四个开关两两拆分（core.js:1176-1184 原文）：

```
我能看 TA 的 = !(iHideChar || charHidesMe)
TA 能看我的  = !(iHideFromChar || charHidesFromMe)
```

`cognition` 值域 **`aware` / `unaware` / `single`**（读 `core.cognitionOf(charId, userId, sandboxId)` core.js:1228-1232，
返回 `{cognition, barrier}`；**没有 link 时默认 `unaware`**）。
⚠️ 记忆里的老坑：`merged` 是 `awarenessOf` 推的 **mode**，**不是** cognition 值。

### 2.4 `charRel:<sbId>` —— char × char 的第三态（**设计稿没提到，但真实存在**）

page-island.js:647-676：

```
relKey(sbId)  = 'charRel:' + sbId        // 动态键，不在 scoped 名单，删房整键 remove（core.js:398-405）
pairKey(a,b)  = a<b ? a+'|'+b : b+'|'+a  // 排序保证对称
值域          = 'known' | 'met' | 'unknown'   （REL_LABELS page-island.js:662）
读取出口      = Sleepy.island.getPairRel(sbId, a, b)   // 导出 page-island.js:1698
```

**这是本仓库唯一的 char↔char 关系记录**，消费者已有两处：
- 注入：page-switch.js:508-520（`compileIslandKB`，注入口径原文「认识 / 见过面但不熟 / 不认识」）
- 群聊切片：page-group-ai.js:167-175（`pairRelText`）
- 编辑 UI：island-overview 的 `relSeg`（page-island.js:964-981，三档分段控件）
- 认知矩阵：page-island.js:1036-1038

**局限（关键）**：只有三态、**没有关系文本**、**没有任何时间戳**（值就是裸字符串）。
→ 设计稿 §2 要「关系短标签」，对其他正式角色**只能显示三态原文**，
   **绝不能补写成「朋友 / 同事 / 家人」**（§2 红线原文「没有可靠数据时不补写默认词」）。

## 4. 是否已有可复用的图形 / SVG / canvas 组件（§9-4）

### 结论：**没有。关系图必须从零写。**

全仓 grep `graph` / `force` / `layout` / `network` / `createElementNS` —— **零命中**（只有 `app.js:relayout` 这种页面重排）。
`vendor/` 只有两个文件：`three.module.js`、`acrylic-lamp-core.js`（亚克力挂件灯用，且必须懒加载 + http(s)）。

现有 SVG 全是**图标**：
- `ui.js` 的 `ic()` / `page-calendar.js:67-69` 的图标包装
- `page-chat.js:33` 的 data-uri 头像

现有 canvas 只有 `sticker-cut.js`（切片器，纯函数 + canvas 包装，与布局无关）。

**取舍建议**：
- **手写 SVG + 确定性布局**（环形/星形），**不引第三方库**——
  这个仓库是「零依赖静态前端，双击 file:// 能开」（见 `package.json` 与长期约定），
  引 d3/cytoscape 会破坏这条红线，还要多维护一份 vendor。
- 确定性布局还有个附加好处：**冒烟可断言**（同输入 → 同坐标，不引入随机/迭代收敛）。
- 分段控件（图/列表切换）**有现成样式**：`.iol-seg` / `.iol-seg-btn.is-on`（style.css:8764-8774，
  先例 page-island.js:966-981）。直接复用，别新造。

### 5.2 建议新增两个文件

| 文件 | 性质 | 位置 |
|---|---|---|
| `ta-network.js` | **只读 selector**（0 模型 0 网络，纯函数 + 复用 core/island） | 插在 `ta-impact.js` 之后、`page-ta.js` 之前 |

  「本文件在 page-chat.js 之后加载」index.html:222-224），顺序不敏感；
  排在后面更符合「依赖在前」的读法。
- **不塞进 `page-ta.js`**：它已经 77KB / 8 个注册页，再塞一个双视图页面会失控。

## 6. 关系边来源、来源字段和更新时间是否足够（§9-6）

### 结论：**来源不足，更新时间缺失。这是本轮最硬的两个缺口。**

| 设计稿 §7 要的字段 | `links`（char×user） | `charRel`（char×char） | NPC 边 |
|---|---|---|---|
| `relation` 文本 | ✅ 有（自由文本） | ❌ **无**（只有三态） | ❌ 无 |
| 来源 `sourceType/sourceRef` | ❌ **无** | ❌ 无 | ❌ 无 |
| `updatedAt` | ❌ **无**（只有 `createdAt`） | ❌ **无**（裸字符串值） | ❌ 无 |
| 可见性 | ✅ 四开关 + cognition + barrier | ❌ 无（三态本身就是认知） | ⚠️ `knownBy` / `npcVis` |

### 6.1 `updatedAt` 为什么真的拿不到

- `addLink` 只写 `createdAt: Date.now()`（core.js:1145）。
- `setRelation` 改 `relation` 文本时（core.js:1156-1167）**只改 relation 一个字段，不碰任何时间戳**。
- 全仓 grep `relationAt` / `relationUpdatedAt` / `link.updatedAt` —— **零命中**。

→ 设计稿 §3「来源与更新时间（**已有时**）」的括号是对的：本仓库对关系文本**没有**更新时间。
  §7 要 selector 吐 `updatedAt` 只能解释为「**该节点可用的最近时间**」，
  **不是**「这条关系什么时候改的」。

### 6.2 三条可选路线（**需要用户拍板**）

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）如实显示** | 关系行显示「**建立于 `createdAt`**」，并注明「关系文本的修改时间不可知」；`updatedAt` = 节点可用的最近时间（近况时间 / 影响的 `reactedAt` / 无则 `createdAt`） | 零改核心；口径诚实；符合 §7「不能假设文档字段已经存在」 |
| B 补写侧字段 | `setRelation` 加 `relationUpdatedAt = Date.now()`（顺带 `addLink` 加 `updatedAt`） | 动 `core.js` **写路径**——超出「只读勘察 + 不改业务代码」；老数据仍无值，仍需 A 的兜底 |
| C 不显示时间 | 只显示关系文本 | 最省，但 §3 明确要「来源与更新时间（已有时）」，等于放弃一项 |

**建议 A**（并可把 B 作为后续批次的小修，不混进本批）。

### 6.3 关系边到底有哪些（这是第一版图长什么样的决定因素）

| 边 | 数据来源 | 判据 | 标签 |
|---|---|---|---|
| 中心 char ↔ 当前 user | `links` | `findLink(centerId, userId, sbId)` 存在 | `link.relation`（空 → 「关系未注明」） |
| 中心 char ↔ 其他正式角色 | `charRel:<sbId>` | `getPairRel` ∈ {known, met} | 三态原文（认识 / 见过但不熟）；`unknown` **不画边** |
| 中心 char ↔ NPC | **无数据** | —— | **不画边**，节点标「关系未注明」 |
| NPC ↔ NPC / NPC ↔ 其他人 | **无数据** | —— | **不画边**（§3 原文「NPC 与 NPC 的边必须有真实关系记录，不能由事件影响代替」） |

⚠️ **`charRel` 的适用性有限**：`compileIslandKB` 只在**群岛 + ≥2 位主要角色**时才注入
（page-switch.js:507-508 原文），孤岛时这套关系根本没被用过。
关系网里可以照读（孤岛通常只有一个 main，也就没有这条边），但要在代码注释里写明这个语境。

### 6.4 「来源」这一项怎么落

`links` 没有 `sourceType/sourceRef`，但**有一条真实可查的来源线索**：
`taNpcDrafts` 里 `status:'confirmed' && linkMade===true && formalCharId === 该 char` 
（ta-life.js:345-361）——即「这条 link 是确认 NPC 草稿时建的」。
**但**：草稿记录只覆盖「从草稿确认」这一条路径，手动建交、朋友圈加好友等路径都没记录。
→ **不建议**用它当权威来源。建议 `sourceRefs` 如实只填：
- 节点：`{ kind:'char', id }` 或 `{ kind:'npc', id }`（+ `sandboxId`）
- 边：`{ kind:'link', id: link.id }` 或 `{ kind:'charRel', key: pairKey(a,b) }`
- 近况：`{ kind:'moment', at }`
**「来源」= 数据出处（哪张表哪条记录），不是「关系怎么来的」。** 这条要在文档里跟用户说清，避免误期。

## 7. 是否需要只读 selector（§9-7）

### 需要，而且必须只有一个。

理由（设计稿 §7 原文 + 本仓库既有教训）：
1. **图视图和列表视图必须同源**——否则两套过滤逻辑迟早跑偏（本仓库「唯一实现」红线：
   装配只走 `promptEngine.compileCharacter`、头像入口只走 `Sleepy.faceField`、
   时间只走 `Sleepy.calendar.timeFacts`、翻译只走 `msg-trans.js`）。
2. **纯函数可冒烟**：不依赖 DOM，能在 smoke 里直接造岛/造人/造 link 断言结果。
3. **权限过滤必须在 selector 里，不能在各视图里**——§4 原文「读取阶段先过滤节点、边和近况摘要，
   不只隐藏详情」。放在视图层就等于「数据到了 DOM 才藏」，数量变化照样泄露。

### 7.1 建议形状（契约，**已按 P1–P4 锁定**）

```
Sleepy.taNetwork.build({ charId, userId, sbId })
→ {
    ok: boolean,
    why: '' | 'no-island' | 'no-char' | 'no-user',
    center: { id, name, kind:'char', identityLine, updatedAt } | null,
    nodes: [ {
      id, kind:'char'|'npc'|'user', name,
      label,            // 关系短标签；无依据 → '关系未注明'
      labelSource,      // 'link.relation' | 'charRel' | ''   ← 让 UI 能如实标注出处
      recent,           // { text, at } | null
      hasImpact,        // 低敏布尔，§5
      updatedAt,        // **可用最近时间**，不是关系变更时间（P1）
      sourceRefs: [...],
      clickable: true
    } ],
    edges: [ { id, from, to, label, labelSource, visible, sourceRefs, updatedAt } ],
    visibility: { knownByGate: 'center-root', dropped: n },   // dropped **不上屏**，只给冒烟/调试
    updatedAt
  }
```

**锁定口径**：
- `labelSource` 只有三种取值：`'link.relation'`（char×user 的正式关系文本）、
  `'charRel'`（三态原文「认识 / 见过但不熟」）、`''`（无依据 → `label = '关系未注明'`）。
  **绝不出现「朋友 / 亲密 / 家人」这类默认词**（§2 红线）。
- `edges` 只可能有两种 `labelSource`：`'link.relation'` 与 `'charRel'`；
  `charRel === 'unknown'` 的**不进 edges**（P2）。
- 知情闸 `knownByGate: 'center-root'`：判 `knownBy` 是否含中心角色的 root（P4），
  空/缺字段 **fail open**（§9 表）。
- `updatedAt` 是**节点可用最近时间**，UI 上对关系行要写「建立于」而不是「更新于」（P1）。

### 7.2 两条实现纪律（写进代码注释）

1. **selector 绝不写 store**（`store.get` 深拷贝 + 只读投影）。
   `ta-impact.js` 的 `compile()` 就是先例：「读只投影、写要显式」。
2. **selector 绝不调模型**（0 网络）。`page-ta.js` 的静态护栏断言
   （smoke.js:1977-1982：源码里不许出现写入或网络调用）要**照抄一份给 `ta-network.js`**。

## 8. 权限与知情边界（设计稿 §4）的落地锚点

设计稿 §4 要求「读取阶段先过滤节点、边和近况摘要」，且必须区分四件事：

| 概念 | 本仓库对应 | 锚点 |
|---|---|---|
| 玩家能看到 | 玩家侧页面（ta / ta-person / ta-backstage） | 就是本页 |
| char 已知 | `knownBy`（NPC）+ `charRel` 三态 + `cognition` | page-switch.js:544、core.js:1228 |
| 故事内 user 是否认识 | `link.cognition`（`aware`/`unaware`/`single`）+ 草稿 `userKnowsInStory` | core.js:1228；ta-life.js:359 |
| NPC 是否允许自主发展 | 草稿 `autonomousDevelopmentAllowed`（**只存在于草稿**） | ta-life.js:360 |

**§4 的硬要求落到实现上 = 节点集合的三道闸：**

1. **岛闸**：`charsOfSandbox(sb)` / `npcsOfRoom(sb)` 天然按岛过滤；
   `findLink` / `getPairRel` **必须显式带 `sandboxId`**（§2.2 铁律 2）。
2. **知情闸（NPC）**：`knownBy` 不含「中心角色的 root」→ 不进节点集合。
   口径复用 page-switch.js:544-546。**这条现在首页没做**（见 §9 缺口 3）。
3. **草稿闸**：不读 `taNpcDrafts`。天然成立（§1.3）。

### 8.1 关于「数量变化泄露」（§4 原文）

只要节点集合在 selector 里就过滤干净，**数量本身就是权限过滤后的数量**，不会泄露。
但要防一个反向坑：**首页 04 区块现在不过滤 `knownBy`**（page-ta.js:716-718），
关系网过滤 → 两个页面的「身边的人」数量会**不一致**。
→ 建议：**selector 是唯一出口，首页 04 也改成读 selector 的 `nodes`**
（顺带满足设计稿 §7「页面组件不各自拼人物数据」）。
**这条会改动 `page-ta.js` 现有 04 区块的行为**，需要用户确认（见 §9 缺口 3）。

### 8.2 老数据的 `knownBy` 缺失怎么判

- `knownBy` 字段**不存在**（2026-09-21 之前建的 NPC）→ **fail open**（显示）。
  理由：首页现在就显示它们，突然不显示才是「数量变化」。
- `knownBy` 是**空数组** → 同上 fail open（空数组和「没这个字段」在 `Array.isArray` 下不可分，
  除非显式用 `has()` 判；建议用 `has()` 判字段存在性，但两者都 fail open）。
- `knownBy` **有值但不含中心 root** → **fail closed**（不显示）。这是唯一真正生效的闸。

⚠️ 注意这和 page-switch.js:544-546 的**注入**口径**不同**（那边空数组 = 不注入 = fail closed）。
**关系网是显示层，注入是角色认知层，两者 fail 方向本来就该相反**——
这条要写进代码注释，否则下一个人会「统一」掉它。

## 9. 缺口汇总

### 硬缺口（必须解决，否则做不出来）

1. **无图形/布局组件** → 手写 SVG + 确定性环形布局（§4）。
2. **无只读 selector** → 新建 `ta-network.js`（§7）。
3. **NPC 与任何人无关系记录** → NPC 只有节点、无连线（§6.3）。
   **这不是缺陷，是如实投影**；若用户希望 NPC 有边，需要先有数据（后续批次）。

### 拍板结果（4 条，2026-10-02 用户确认，**全部按推荐锁定**）

| # | 问题 | **决定** |
|---|---|---|
| **P1** | `links` 无 `updatedAt`，关系文本修改时间不可知 → 怎么显示？ | **如实显示**：关系行显示「建立于 `createdAt`」+ 注明「关系文本的修改时间不可知」；**不动 `core.js` 写路径**。selector 的 `updatedAt` = 该节点可用的最近时间（近况时间 / 影响 `reactedAt` / 无则 `createdAt`） |
| **P2** | `charRel` 三态算不算「关系依据」？要不要画边？ | **画**：`known` / `met` 画边、标签用三态原文（认识 / 见过但不熟）；**`unknown` 不画边**（视为无依据） |
| **P3** | 首页 04 现在不过滤 `knownBy`，关系网过滤 → 数量不一致 | **首页 04 也改读 selector 的 `nodes`** —— selector 成为人物集合的**唯一出口**，两页口径统一；会改动 `page-ta.js` 现有行为，冒烟要锁住 |
| **P4** | 节点集合的知情闸以谁为准 | **以中心角色为准**：`knownBy` 含中心角色的 root（或其皮套 id）才进节点集合；与 page-switch.js:544-546 注入口径一致 |

### P4 的 fail 方向（**必须写进代码注释，防后人「统一」掉**）

| 层 | 空 `knownBy` | 理由 |
|---|---|---|
| 注入（page-switch.js:544-546） | **fail closed**（不注入） | 角色认知层：没记录就别让 TA 知道 |
| 显示（关系网 selector） | **fail open**（显示） | 显示层：首页现在就显示这些老 NPC，突然不显示才是 §4 说的「数量变化泄露」 |

### 次要缺口（v1 可接受，如实标注）

5. NPC 的近况摘要依赖 NPC 在朋友圈的账号体系（未验）→ v1 允许 NPC 无近况。
6. 无 `sourceType/sourceRef` → `sourceRefs` 只填「数据出处」，不是「关系怎么来的」（§6.4）。
7. 无关系图布局持久化（设计稿 §10 明确不做）。

## 11. 冒烟与验收映射（设计稿 §8 十一条 → 断言）

| §8 验收项 | 断言方式 |
|---|---|
| ta → 身边的人可以进入关系网 | `nav.open('ta')` 后找入口行，`nav.open('ta-network')` 不炸 |
| 图 / 列表切换不写入、不调用模型 | 切换前后 `snap()` 全量键快照相等；静态护栏断言 `page-ta-network.js` 无 `fetch`/`store.set` |
| 当前角色是中心节点 | `build().center.id === activeCharOnIsland().id` |
| 正式人物能按权限显示 | 造 3 人（main / NPC-knownBy 含中心 / NPC-knownBy 不含）→ 断言只出 2 |
| 草稿和未确认 NPC 不出现 | 造 `status:'draft'` 草稿 → **反向断言**名字不在 `nodes` 里 |
| 只有有依据的关系才出现边 | 造 link（有 relation / 无 relation）+ charRel（known / met / unknown）→ 逐条断言 |
| 无关系依据不自动补边 | 两个无任何记录的 NPC → 断言 `edges` 里没有它们之间的边 |
| 点击节点进入既有人物详情 | `nav.open('ta-person', {id})` 走通 |
| 切岛、切角色、刷新不串数据 | 建两座岛各一组人物 → 切岛后 `build()` 的 `nodes` 完全换掉（`sandboxId` 显式传） |
| 空岛 / 无角色 / 无人物 / 无关系各有明确空态 | 四种夹具 → 断言 `why` + 空态文案存在 |
| 手机无横向溢出，节点和列表行可触控 | 无头 Edge 量 `document.scrollingElement.scrollWidth <= clientWidth`；节点触控区 ≥ 现有标准 |
| `check.js` / `smoke.js` / 无头主题检查通过 | 双绿 + 四主题截图 |

**必须包含**：smoke 末尾的**全页渲染冒烟**（smoke.js:8435 / 8699）会自动 open `ta-network`，
所以新页注册后**不用手写**「页面能开」的断言，但**必须**保证 render 不抛异常。
