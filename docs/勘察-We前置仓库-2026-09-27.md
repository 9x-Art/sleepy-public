## 0. 一句话结论

We 在仓库里**不存在任何已接线或未接线的入口、页面、数据实体、方案文档**。它是全新功能。
好消息是：当前世界 / 关系上下文（`core`）、关系数据（`links`）、日历约定、朋友圈动态、相册、消息收藏、近期生活动态（`lifeFeed`）**全部已有真实且按岛隔离的数据源**，We 首页几乎不用造假数据，可以直接组合。真正的缺口集中在「**留痕/共同记录实体**」和「**收藏馆的关系级元数据**」两个没有落表的地方。
桌面入口方面：**第 3 屏（含 todo 组件那屏）共 6 格可替换为 We 或改名「占位」**（用户拍板，§1.1a）—— `p3-fav`收藏夹 / `p3-stickers`贴纸 / `p3-wallet`钱包（这三个在聊天 App「我」内都有同功能入口）、`p3-book`世界书 / `p3-look`外观 / `p3-store`组件商城（这三个主屏已有副本）。**仅保留 `p3-settings`(日历) 与 `p3-gallery`(相册) 两格**（用户未点名、桌面唯一）。We 桌面入口落点问题因此基本解决。

## 1. 入口与路由

### 1.1 桌面 App 注册机制（结论：走 `defaultDesktop` + `RENDER.app`）

桌面 4 屏网格的每个入口都是一格数据，不是独立注册：

- **户型数据**：`defaultDesktop()` → `page-desktop.js:174-272`，返回 `{ version, pages: [4 屏网格] }`，每格形如 `{ i, type:'app', app:'<页面id>', x, y, w, h, label }`（page-desktop.js:106 注释定义）。
- **App 图标渲染**：`RENDER.app` → `page-desktop.js:766-784`，点开调 `ctx.open(cell.app)`；图标取 `ICONS[cell.app] || ICONS.chat`（page-desktop.js:778）。
- **图标表**：`var ICONS = {...}` → `page-desktop.js:58-99`（chat / island / favorites / calendar / gallery / memory 等都有）。
- **布局版本**：`var LAYOUT_VERSION = 16` → `page-desktop.js:172`。**每次改户型必须 +1**，否则老存档直接复用旧布局（page-desktop.js:116-172 有踩坑记录）。
- **点击落点**：桌面渲染出的按钮挂 `click → ctx.open(cell.app)`；全局兜底 `document.addEventListener('click', [data-app] → open())` → `app.js:623-626`。
- **岛级户型覆盖**：`desktop.islands[sbId]` 层，读写走 `getDesktop` / `Sleepy.desktop.setDesktop/getDesktop`（page-desktop.js:274-336）。用户在某岛自定义过才有一份覆盖，全局一份 base。

**新增 We 入口**（后续施工时）：在 `defaultDesktop()` 某屏补一格 `{ i:'p1-we', type:'app', app:'we', x, y, w:1, h:1, label:'We' }` + 在 `ICONS` 加 `we: ic('...')` + `LAYOUT_VERSION` +1。**不需要**改 app.js 的路由表——`app:'we'` 里的 `we` 就是 `Sleepy.register('we', ...)` 的 id。

### 1.2 App 页面打开 / 生命周期（结论：标准 `register` + 页面栈）

- **注册**：`Sleepy.register(id, def)` → `app.js:723`，`def = { title, render, onShow, onHide, onBack }`。
- **打开**：`open(id, params)` → `app.js:395-431`；`build(id, params)` → `app.js:245-360`（建 `.page > .page-inner > .app-head + .app-body` 外壳，`def.render(ctx)` 填充 body，异常吞进 `.empty` 报错页，不炸壳）。
- **页面栈**：`pageStack`（app.js:41），`closeTop`(433) / `closeAll`(460) / `replace`(474) / `requestBack`(498)。
- **生命周期钩子**：打开后调 `def.onShow(ctx)`（app.js:430）；关闭时调 `def.onHide`（app.js:436）；返回可被 `def.onBack(ctx)===true` 接管（app.js:506）。
- **ctx**：`{ id, el, body, params, store, toast, apiFail, setTitle, setActions, open, back, refresh, ... }`（app.js:269-333）。**`refresh` = `onShow`**（app.js:331），切岛后自动刷新走它。
- **页面实例缓存复用**：同一 id 带不同 params 再开，`applyParams` → `app.js:375-393` 会清 body 重调 `render`。
- **桌面是常驻底层**，不在栈里（`bootHome` app.js:784-846）；`open('home')` 特判为回桌面（app.js:403-406）。

### 1.3 是否已有未接线的 We / 情侣空间 / 收藏馆入口

- **没有**。`ICONS`（page-desktop.js:58-99）无 `we`；`defaultDesktop` 无 `app:'we'`；docs 目录无任何「We/关系/收藏馆/共同记录/情侣空间」方案文档（`ls docs | grep -iE 'we|关系|收藏|共同|情侣|留痕'` 为空）。
- 已有**消息收藏** App：`favorites`（`page-chat.js:3866` `Sleepy.register('favorites',{title:'收藏夹',...})`），桌面第 3 屏一格 `app:'favorites'`（page-desktop.js:256）。它是「收藏的单条消息快照」列表，不是关系空间收藏馆。
- `favorites` **不在** chat App 容器里：`page-app.js:282-284` 只映射 `chat-list`/`moments`/`me` 三个入口。所以 `favorites` 目前是独立可点开的 App。

### 1.4 推荐文件与入口

- **推荐新增 `page-we.js`**（复用 `page-*.js` 模式，`index.html` 里加 `<script src="page-we.js" defer>`）。不推荐复用 page-chat / page-app —— We 是独立关系空间首页，语义和聊天容器不同，硬塞会污染聊天页的 4 Tab 心智。
- 入口函数：`Sleepy.register('we', { title:'We', render(ctx), onShow(ctx){ ctx.rebuild() } })`，`render` 里存 `ctx.rebuild = ...` 以便切岛刷新（见 §2.6 / §4.5）。
- 桌面一格 + 图标 + `LAYOUT_VERSION`+1（施工时）。

## 2. 当前世界 / 关系上下文

### 2.1 能拿到的一切（结论：已有统一出口，We 不该自造）

| 需要什么 | 用谁 | 位置 |
|---|---|---|
| 当前 sandbox id | `core.scopeId()` | core.js:436-439 |
| 当前房对象（含 kind/charIds/maskIds） | `core.activeSandbox()` | core.js:426-431 |
| 当前 user（马甲）id | `core.activeUserOnIsland().id`（卫兵） | core.js:1010-1015 |
| 当前主角色 root id | `core.activeCharOnIsland().id` 或 `rootOf(charId)` | core.js:995-1001 / 576 |
| 本岛全部大号 | `core.charsOfSandbox(sbId)` | core.js:453-462 |
| 本岛全部马甲 | `core.masksOfSandbox(sbId)` | core.js:465-474 |
| 本岛「我」的大号马甲 | `core.defaultUserOfSandbox(sbId)` | core.js:959-968 |
| 孤岛 vs 群岛 | `sandbox.kind`（'isle' / 'archipelago'）；`core.needsCharPick()` | core.js:479-483 |
| 切岛 | `core.setActiveSandbox(id)` | core.js:441-450 |

**要点（已核对源码语义）**：
- `scopeId()` 无房时返回 `null`，不是错误（core.js:433-439 注释）——We 要能接受 null。
- `activeCharOnIsland()` / `activeUserOnIsland()` 是**指针卫兵**：当前 char/user 必须在本岛名册里，否则返回 null。**We 所有「跟当前身份走」的读取必须走它们，不能直接 `activeChar()`/`activeUser()`**（core.js:987-1015 注释明确）。
- `activeChar()`（core.js:977）返回的是**大号**（皮套会先归到 root，982），但**不过岛闸**——所以 We 一定要用 `activeCharOnIsland()`。

### 2.2 当前角色 × user 的关系数据

- 关系主表 `links`（store key `links`，store.js:167）。每条 `{ id, charId, userId, cognition:'unaware'|'aware'|'single', barrier:bool, relation:'', createdAt, sandboxId }`（core.js:1098-1113）。
- 读取：
  - `core.findLink(charId, userId, sandboxId)` → core.js:1040-1049（深拷贝，只读）
  - `core.linkSlot(charId, userId, sandboxId)` → core.js:1067-1076（返回 `{list, hit}`，hit 是**快照里的引用**，改完 `saveLinks(list)` 落盘）
- 写入：
  - `core.addLink(charId, userId, cognition, barrier, sandboxId)` → core.js:1090-1114
  - `core.setRelation(charId, userId, text, sandboxId)` → core.js:1119
  - `core.saveLinks(list)` → core.js:1078
- **红线（工作记忆）**：`link.relation` 是「只写不读的死字段」，**别拿它当 We 的关系标题**。关系标题应从 `char`（`findChar(charId).name`）+ `user`（`labelOfUser` core.js:1479）拼，或用日历/留痕这类真实内容。

### 2.3 孤岛 / 群岛判断

`sandbox.kind` 字段；`kind='isle'` 孤岛（1 User × 1 Char），`kind='archipelago'` 群岛（1 User × N Char）。`needsCharPick()`（core.js:479）判断群岛是否要选角色。We 产品方向「不在 We 内切岛」——所以 We 只在**当前房**里展示，不做岛选择器。

### 2.4 是否已有统一「当前世界 / 当前关系对象」读取函数

- **世界**：有，`core.activeSandbox()` / `scopeId()` 就是统一出口。✓
- **关系对象（成对 char×user）**：**没有**一个返回「当前房那一对关系 + 双方档案」的聚合函数。现有 `linkSlot(charId,userId)` 只给单条 link 引用，不带 char/user 档案。这是缺口，但**本轮不重构**——We 施工时在 page-we.js 内组合 `charsOfSandbox + defaultUserOfSandbox + linkSlot` 即可，或提出一个只读的 `core.relationCtx()` 作为新增小工具（待用户拍板，见 §10）。

## 4. 现有持久化与隔离规则

### 4.1 localStorage/store 封装
- 唯一封装 `Sleepy.store`（store.js:893-926）：`get/set/setMany/remove/exportAll/importAll/usage/clearAll/clearUserData/onChange`。所有键前缀 `sleepy.v1.`（store.js:59），`SCHEMA=3`（62）。
- **规则：不新建第二套存储抽象**。We 实体一律走 `store`。

### 4.2 scoped / tagScope / sandboxId 过滤工具
- `core.scoped(list)`（core.js:65-71）：读取侧按当前 `scopeId()` 过滤，null 时原样返回全部（老全局数据兼容）。
- `core.tagScope(rec, sandboxId)`（core.js:72-74）：写入侧盖当前房章。
- **规则：写前盖 tagScope，读时过 scoped**（core.js:55 注释「tagScope 只用在写的地方」）。

### 4.3 IndexedDB
- 有：`media.js` 图片二进制库（photos 只存 mediaId，objectURL 活不过刷新）。**适合 We 的是「引用 mediaId」，不适合存 We 实体**。We 新增实体仍走 localStorage store。

### 4.4 页面状态是否用统一 store
- 是，全局 store（`Sleepy.store`）。页面瞬时状态可放闭包/ctx，持久数据一律 store。
- **规则**：不要把 We 核心状态只放 DOM / 页面闭包——刷新（重新 open）后要从 store 重读。

### 4.5 页面刷新 / 切岛后如何重新读取
- 页面 `render` 里存 `ctx.rebuild = rebuild()`；`onShow(ctx){ ctx.rebuild() }`（page-chat.js:3963-3966 是现成范式）。
- 切岛后：page-switch.js:215 `setActiveSandbox` → 246-258 `Sleepy.__homeCtx.repaint()`（重画桌面）+ `Sleepy.nav.topCtx().refresh()`（刷新栈顶页，若实现了 refresh）。**We 页实现 `ctx.refresh`（=onShow）就能在切岛时自动重读当前房数据**。✓

### 4.6 现有收藏 / 事件 / 记录的新增修改删除范式
- 收藏删除：全量 `store.get('favorites')` → 过滤掉目标 → `store.set('favorites', next)`（page-chat.js:3945-3951）。
- 日历增改：`addEvent`/`updateEvent`/`cancelEvent`/`removeEvent`（calendar.js:441-511）。
- **共同记录新增范式：没有现成实体**（见 §3.2 缺口）。需要新建时，遵循「全量→改→tagScope→落盘」+ 引用存 sourceType/sourceId（见 §6.4）。

### 4.7 迁移 / 清空清单
- 清空：`clearAll`（store.js:520）、`clearUserData`（541，只清正式用户数据）。
- 导出：`exportAll`（419）遍历 `DEFAULTS` + 兜底扫带前缀未登记键（442-451）。**新 key 若不进 DEFAULTS，导出兜底仍会带（好）；但要进 `DEFAULTS` 才有默认值兜底。**
- 删房清理：`core.purgeSandbox`（core.js:281）→ `cleanupSandbox`（329），内部有一份 **scoped 数组**（core.js:343 含 'todos','favorites','userMasks','characters','moments',...）——**新增 We 实体 key 必须加进这份删房名单**（用户拍板项，见 §10）。
- 迁移版本：`SCHEMA`（store.js:62）；老字段补齐靠 `merge`（232）。We 若加字段，老存档自动补默认值。

## 6. We 首版最小施工边界（建议切片）

> 基于真实数据支撑，给出最小纵向闭环，可直接开工。

### 6.1 首页第一版显示哪些区块
基于「有真实数据支撑」原则，首版 We 首页（`page-we.js`）建议：
1. **关系标题**（封面）——`charsOfSandbox(sb)[0].name × labelOfUser(defaultUserOfSandbox)` + `calendar.timeFacts(charId)` 的事实行。
2. **三段事实数**——共同记录数 / 馆藏数 / 贴纸套数（馆藏数可先取 `favorites`+`wj.tickets`，其余待定）。
3. **接下来**——`calendar.upcoming(charId, 7)` 最近一条 shared_event/约定，票根样式。
4. **最近时光**——`lifeFeed.recent(charId, userId)` 扁平取最近几条（朋友圈/日历/日记聚合），或 `momentsTab.listForChar` 横向拍立得。
5. **收藏入口**——指向收藏馆（首版可先复用 `favorites` 页或新建轻量收藏馆）。

### 6.2 哪些区块有真实数据支撑
- 关系标题、接下来、最近时光、日历事实、倒计时（纪念日）：**全部有真实数据**（§3.3/§3.5/§3.8）。
- 共同记录数：**待定**（无实体，见 6.4）。
- 馆藏数：有（favorites + wj.tickets）。

### 6.3 第一版唯一或首批写入动作
- **保存一条共同记录**（从「最近时光 / 日历约定 / 聊天收藏」中「收进 We」），或**新增一条共同记录**（简表：标题 + 一句话 + 来源引用）。
- 落点 = 新增 `weEntries` 实体（见 6.4），遵循 store 全量→tagScope→落盘。

### 6.4 需要新增的实体或字段（本轮不建，施工时建）
- **新增 store key `weEntries`（共同记录）**，结构建议：
  ```js
  { id, sandboxId, title, note, at,
    sourceType: 'chat'|'calendar'|'moments'|'photo'|'offline'|'manual',
    sourceId, refCharId, refUserId,
    createdBy: 'user'|'char', createdAt, updatedAt }
  ```
  只存**引用**（sourceType/sourceId），不复制聊天全文/图片本体。
- **`favorites` 若做关系级收藏馆**：建议新增字段 `kind`（ticket/photo/letter/music/place）、`charId`、`reason`（为什么留下）、`refSourceType/refSourceId`。或另建 `weCollection` 表，不动 favorites 语义（**待用户拍板**，见 §10）。
- 这些 key 必须进：`DEFAULTS`（默认值）、`purgeSandbox` 删房名单（core.js:343）、`exportAll` 自动带出。迁移用 `merge` 补默认。

### 6.5 明确不做
- 不做岛选择器（产品：不在 We 内切岛）。
- 不做跨岛数据合并（We 只显示当前房）。
- 不做对话全文复制进 We。
- 不做收藏馆的「双方共同编辑 / 确认流」（Demo 的「待确认」卡片首版暂缓）。
- 不做复杂导入导出 / 搜索。
- 不把帷境/贴纸套/音乐等重交互塞进首版。

### 6.6 成功标准
进入 We 首页 → 看到当前房关系标题 + 最近时光 + 即将到来的日历约定 + 收藏入口 → 保存一条共同记录 → 返回再进入（或刷新）→ 该记录仍在 → 切到另一座岛再进 We → **不串线**（显示那座的房，且保存的只落在本座）。

## 7. 发现的阻塞缺口（按影响排序）

1. **无「共同记录」实体**——We 的「新增/保存一条共同记录 + 刷新仍在」闭环没有落表。必须新增 `weEntries`（或等价 key），否则首版写入动作无从发生。
2. **favorites 缺关系级元数据**——收藏馆要「藏品」需扩展字段或另建表（charId / kind / reason / 来源引用）。
3. **无统一关系上下文聚合**——没有 `relationCtx()` 一次性给出「当前房那对 char×user + link + 档案」；We 需组合多个 core 函数（可接受，不重构）。
4. **相册无 charId**——「共同照片」无法从 photos 直接圈出关系照片，需靠 weEntries 引用。
5. **无统一 drawer / loading 组件**——We 详情浮层要按 openSheet 范式自建；加载态基本用不上。
