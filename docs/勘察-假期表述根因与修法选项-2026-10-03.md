# 勘察 · 「模型把假期说成第一天」的根因与修法选项 · 2026-10-03

> 用户反馈：设置中国大陆 + 中国传统节日 + 国际节日 + 时区上海，
> 模型却说「今天是国庆第一天」。**换了几个 API 都一样**，上次中秋也出过。
> 本文只做取证与方案对比，**未改任何生产代码**（等用户拍板）。

## 一、决定性线索：换 API 也一样

这一条把矛头从「模型能力」转向「**我们喂的事实本身**」——
多个不同厂商、不同能力档次的模型在同一处说错同一个词，
概率上不可能是巧合。更可能是原文里存在**结构性的误导**。

实测 2026-10-03 真正发给模型的全部内容（131 字，就这四行）：

```
【时间事实】现在的真实时间以这里为准；不要自己编日期，也不要把它当台词念出来。
你的现在：2026年10月3日 星期六 19:36（上海 · Asia/Shanghai）
公共日期（中国大陆）：今天是国庆节（假期期间的周末）。它只描述客观环境，不代表你一定休息。
```

**没有「第几天」三个字**（全仓搜 `第一天/第 1 天/假期第/放假第/首日/第一日` 零命中）。
所以「第一天」是模型自己加的。

## 二、真正的病根：`今天是X` 这个句式在多天假期里**语义就是错的**

不是措辞不够精确，是**事实层面的错误**。

`calendar.js:1329` 无条件把假期块的名字按「今天是<名字>」的句式吐出来：

```js
seg = '今天是' + info.legal.name + …
```

而 `info.legal.name` 来自 `CN_OFFICIAL` 的**整段假期区间**，
不是「节日当天」。逐日实测：

| 日期 | 星期 | 注入原文 | 实际是什么 |
|---|---|---|---|
| 2026-10-01 | 四 | 今天是国庆节（法定放假日） | 国庆当天 ✓ 碰巧对 |
| 2026-10-02 | 五 | 今天是国庆节（法定放假日） | 假期第 2 天 ✗ |
| **2026-10-03** | **六** | **今天是国庆节（假期期间的周末）** | **假期第 3 天 ✗** |
| 2026-10-04 | 日 | 今天是国庆节（假期期间的周末） | 假期第 4 天 ✗ |
| 2026-10-05 | 一 | 今天是国庆节（法定放假日） | 假期第 5 天 ✗ |
| 2026-10-06 | 二 | 今天是国庆节（法定放假日） | 假期第 6 天 ✗ |
| 2026-10-07 | 三 | 今天是国庆节（法定放假日） | 假期第 7 天 ✗ |

**7 天里有 6 天「今天是国庆节」是假的。** 模型读到这句，
再叠加第一行的「2026年10月3日」，两条信息打架：
一条说今天是 10 月 3 日，另一条说今天是国庆节（通常＝10 月 1 日）。
模型调和这两条信息的最省力方式就是**采信节日名、忽略日期**，
于是说出「国庆第一天」。**它不是算错了，是被我们逼着二选一。**

### 中秋那次一模一样（用户记忆正确）

| 日期 | 注入原文 | 实际 |
|---|---|---|
| 2026-09-25 五 | 今天是中秋节（法定放假日） | 中秋当天 ✓ |
| 2026-09-26 六 | 今天是中秋节（假期期间的周末） | 假期第 2 天 ✗ |
| 2026-09-27 日 | 今天是中秋节（假期期间的周末） | 假期第 3 天 ✗ |

**根本不是偶发，是这个句式在所有多天假期上都会触发。**

### 清明更荒唐：节日当天在假期中间

官方 2026 清明放假 `04-04(六) ~ 04-06(一)`，但**清明节当天是 04-05**。
于是：

```
2026-04-04 六  今天是清明节（假期期间的周末）   ← 清明前一天说「今天是清明节」
2026-04-05 日  今天是清明节（假期期间的周末）   ← 唯一说对的
              今天是：清明节。                    ← 文化层这天才补了一句
2026-04-06 一  今天是清明节（法定放假日）       ← 清明后一天还说「今天是清明节」
```

**前后各一天都被说成「今天是清明节」**，而且这三天**没有任何一句在讲真实日期与节日的关系**。
春节同病：`02-15` 说「今天是春节」（那天是腊月二十八）、`02-16` 除夕、`02-17` 初一，
三天全是「今天是春节」。

## 三、为什么「加第 N 天」不是最优解

加「第 N 天 / 共 M 天」能消掉歧义，但它**治标不治本**，而且有三个副作用：

1. **句式仍然是错的**。10 月 3 日那天依然会说「今天是国庆节」，
   只是后面补了「第 3 天」—— 两句自相矛盾，模型仍要调和。
2. **喂给模型的是行政语言**。「共 7 天」「还剩 4 天」是日历 App 的说法，
   不是人说的话；模型会原样念出来，破坏「活人感」。
3. **没覆盖 2027+**。`CN_OFFICIAL` 只内置 2025/2026，超出年份如实降级
   （`builtin:false`）—— 那时候「第 N 天」根本无从计算，会又变成新的瞎猜。

## 四、四个修法选项（推荐 B）

### A. 最小改法：只在「假期首日」说节日名，其余说「假期期间」
```
10-01  公共日期（中国大陆）：今天是国庆节（法定放假日）。
10-03  公共日期（中国大陆）：今天在国庆假期里（假期期间的周末）。
```
- 成本：低（`buildYear` 里记一下 `isFirstDayOfBlock`）。
- 好处：不加任何行政语言；不给模型算术任务。
- 不足：「10-03 在国庆假期里」仍然没给位置（但已经不冲突了，模型不会瞎排）。

### B. 推荐：把「事实」和「解读」分开，只给事实 ★
**核心思想：不要给模型任何需要它自己推理的东西。**
```
公共日期（中国大陆）：法定假期 · 国庆（10 月 1 日—10 月 7 日） · 今天是 10 月 3 日，
是这段假期的第 3 天。
```
- 一次性把三件事说全：**区间**（不需推理）、**今天**（不需推理）、**位置**（不需推理）。
- 「第 3 天」在这里是**事实陈述**（来自 `from` 到今天的天数差），
  不是让模型去数的 —— 跟 A 的区别在于 A 留着矛盾让模型自己解，B 不留矛盾。
- 天然覆盖 2027+ 的降级：没数据时就说「该年度未内置法定节假日数据」，不含糊。
- 成本：中（`dayInfo` 补 `blockFrom/blockTo` 字段，文案重写）。

### C. 换成让模型无法误解的句式：只说「公共日期名」，不说「今天是」
```
公共日期（中国大陆）：国庆（放假中）。
```
- 成本：极低。
- 好处：零冲突。
- 不足：信息太少，「放假中」不告诉它是第几天、还剩多久。**适合当兜底，不适合当主方案。**

### D. 彻底交出去：让模型自己查
- 需要接工具/联网，**本项目红线**（日历层 0 网络 0 模型调用）。
- **不建议**，且与项目「离线优先」的定位冲突。

### 建议组合

**B 为主 + C 为兜底**：有内置数据时走 B 的完整事实；
超出内置年份走 C 的最简表述（不瞎猜、不硬算）。
