## 一、最终实现方式与理由

**轻量共享 We 导航组件挂三个主路由（实施单首选方案），维持现有收藏馆路由与实现。**

- 新出口 `Sleepy.weNav`（page-we.js）：`mount(ctx, activeId)` 把同一条 `.we-tabbar` 挂进页面 `.page-inner`（`.app-body` 之后的文档流兄弟，flex:none 常驻，**非 fixed**），并给页面打 `has-tabbar`，借 style.css 既有的 `.page.has-tabbar` 布局机制（滚动交给 `.app-body`）。挂载**幂等**（render 因 applyParams 重跑只更新高亮，不长第二份 bar）；`onShow`/切岛重画只清 `ctx.body`，不碰 bar。
- 三个宿主：`'we'`（首页）、`'we-time'`（新时光页）、`'collection'`（门厅，page-collection.js 在 render 里挂）。二级页 `collection-item` / `collection-proposal` **不挂** bar（smoke 反向断言），返回回实际来源页。
- **主 Tab 与返回栈**：切 Tab 走 `Sleepy.nav.replace(id)`。为此修正了 app.js 的 `replace()` 两点：
  1. `open()` 增加 `opts.replaceHist` —— replace 弹掉栈顶后重开时，浏览器历史用 `history.replaceState`（新 `histReplace()`）**原地替换**而不是 pushState。反复切 Tab 浏览器历史深度不变，按一次返回就退出 We，进入 We 前的返回目标原样保留（实施单定案 5）。
  2. replace 落在 open「目标已在栈里」分支时（如正文入口推进收藏馆后点首页 Tab），open 原本不喊 onShow —— replace 里补喊一次，切回下层页面不显示旧数据。
  - 兼容性：`nav.replace` 全仓唯一调用方是 page-group.js:2078（线下交接换页），语义完全一致且历史行为更正确（原来会多出一条死历史条目）。
- `goTab` 点当前 Tab 直接 return：不重挂、不加历史、不触发写入。
- 新增「＋」是动作不是第四页：SVG 加号（无特殊字符图标），`aria-label="记一条共同记录"`，复用 `openAddDrawer`（导出为 `weNav.openAdd`）；保存成功后改为调 `ctx.refresh()`（宿主页自己的 onShow），谁打开谁刷自己，同一条保存出口。
- 滚动位置：`paintKeepingScroll` 模式 —— 三个主页面的重画都先存 `ctx.body.scrollTop` 再重画后还原（has-tabbar 下 `.app-body` 是滚动容器）。普通切 Tab / 切岛不丢位置；重画本身是 onShow 重读，数据始终新鲜。
- 不整体套用聊天 page-app（绑死 TABS/is-moments/backGuard，前置勘察已点名不复用）；不重写任何收藏提议/确认/来源校验/存储。

## 二、变更清单（真实路径 + 关键片段）

### 1. app.js（页面栈）
- `open(id, params, opts)`（~:395）：push 分支 `opts.replaceHist ? histReplace(id) : histPush(id)`。
- 新增 `histReplace(id)`（~:539 旁）：`history.replaceState({sleepy:id, depth}, '', '#'+id)`。
- `replace(id, params)`（~:482）：记录 `popped`，调 `open(id, params, {replaceHist: popped})`；`pageStack.length <= before` 时对栈顶补 `safeCall(def.onShow, ctx)`。

### 2. page-we.js（We 空间：底栏 + 时光 + 抽屉）
- 头注释新增三页导航说明。
- 新增 `WE_TABS` / `mountBar(ctx, activeId)` / `goTab(id)` / `paintKeepingScroll(ctx, build)`（`arr()` 之后一段）。
- `openAddDrawer` 保存成功：`paint(ctx)` → `ctx.refresh()`。
- `paint(ctx)`：首尾加 scrollTop 存/还。
- `'we'` render：加 `mountBar(ctx, 'we')`。

### 4. style.css（末尾追加段，~75 行）
- `.page.has-tabbar .we-page-paper{margin-left:0;margin-right:0;padding-bottom:30px}` —— **关键坑**：has-tabbar 下 `.page-inner` 左右 padding 收零，纸张原有的 `-22px` 通栏负 margin 会把整张纸推出屏外（真机截图发现正文贴边、编号被裁）；margin 归零后纸张占满，封面/待确认条继续用自己的 -22px 出血到屏缘。底部安全区只算一次（bar 自带，纸张归零）。

## 三、时光 v1 数据口径

- **来源（全部只读，已接入出口，不建新仓库）**：
  1. 朋友圈：`momentsTab.all()` + `core.scoped`，关系内（TA 发的 + 当前号我发的），**user 视角三道闸 `canSee(m, user.id, 'user')`** —— 红线方向：给 user 看的页面用 canSee，不用 canCharSee（首页 lifeFeed 才是 TA 视角）。
  2. 日记：`diary.list()`（scoped）；TA 写的挂他名下（`charId===char.id`）；我写的归当前号（`userId===user.id`，老数据无 userId 放行——与日记页展示同口径）；`status='pending'`（待补）排除——不冒充已发生。
  3. 共同记录：`weStore.list()`（scoped）。P2 pending 提议在 `weProposals` 表，天然不混入。
- **未覆盖的来源（明确列出）**：日历的已发生事件。lifeFeed 只接「即将到来」（未来约定留在首页「接下来」）；已发生事件的 user 可见性口径（TA 的 private 事件不能泄进时光）需要单独拍板，v1 不擅自扩。已发生的约定如需留，会以共同记录/藏品形式出现。
- **时间字段**：moments `at`（number，缺则 Date.parse 或 0）、diary `timestamp`、weEntries `at`（number 或日期字符串，`atNum` 归一，解析不出当 0）。排序倒序；0 → 排最后显示「时间不详」，不编日期。
- **去重**：`type + id`（真实稳定来源标识），不靠标题合并。当前 sourceCandidates 只产 calendar/offline 来源，跨源重复实际不可达，去重是防御性的。
- **分页**：三张表都是本机小表，全量读、按 30 条/批渲染，「还有更早的 · 加载更多」真实可继续（跨批次保留日期分组上下文）。
- **点击跳转（现有机制）**：moments → `nav.open('moments')`；diary → `nav.open('diary')`；共同记录 → `nav.open('collection-item',{id})`（其现有查看实现）。不是一律跳收藏馆。
- **失败 ≠ 空态**：聚合 try/catch，「时光暂时读不出来」+ 重试按钮；空态「这里还没有一起经过的片段。」+「记一条」。异步缩略图 `isConnected` 前置守卫，重画后旧响应改不到新视图。
