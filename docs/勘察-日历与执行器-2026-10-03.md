## 1. 日历真实数据模型与状态机

### 存储键与隔离

| 键 | 定义 | 结构 | 隔离 |
|---|---|---|---|
| `calConfigs` | `calendar.js:31` | `{id, sandboxId, charId, region, cultures[], timezone, scheduleOn, anniversaryPerm, remindOn, createdAt, updatedAt}` | `core.tagScope`（`:252`） |
| `calEvents` | `calendar.js:32` | 见下 | `core.tagScope`（`:523`） |

两张表都在 `core.js:360` 的删房 scoped 名单里，`cleanupSandbox` 按 `sandboxId` 清。

### 事件完整字段（`calendar.js:495-522 addEvent`）

```js
{ id, ownerCharId, eventType, title, desc, startAt, endAt, timezone, allDay,
  status, tentative, createdBy:{type,id}, participants[], visibility,
  deviceProtection, sourceType, sourceIds[], memoryId, meaningType,
  repeatRule, cancelReason, createdAt, updatedAt }
/* updateEvent 时才追加： history[] = [{at, from, to, reason}]  (calendar.js:542-548) */
```

逐一回答勘察单 A 段的语义问题：

- **`ownerCharId`** —— 挂在谁名下。**不等于「谁定的」**，也不等于「谁能看」。反例就在生产代码里：`page-calendar.js:1095` 建「我的提醒」时也写 `ownerCharId: ch.id`，而 `createdBy` 才是 `{type:'user'}`。`life-feed.js:108-110` 专门注释了这一点（「刻意不看 ownerCharId」）。
- **`createdBy`** —— `{type:'user'|'char', id}`，`addEvent` 默认 `{type:'user', id:'user'}`（`:510`）。**它是可见性判定的一半**（`life-feed.js:114`）。
- **`participants`** —— `[{type:'user'|'char', id, state}]`。**只写不读**：全库读 `participants` 的地方只有 `life-feed.js:119`（`visibility==='participants'` 时查成员）和 `calendar.js:446`（`eventsOf` 关联）。
- **`participantStates`** —— 另一个字段（**与 `participants[].state` 并存、不一致**）。见 §3。
- **`visibility`** —— 真实取值四个：`'private'`（默认，`calendar.js:512`）、`'participants'`（共同事件，`:1114`）、`'shared_busy'`、`'shared_detail'`（纪念日页 `:576`）。**这四个值只在两处被真正判定**：`life-feed.js:111 charViewOf`、`page-calendar.js:160 visText`（显示文案）。
- **`sourceIds`** —— `addEvent` 默认 `[]`（`:515`），只有 `saveAnniversary` 会填（`:659` `sourceIds: mem.sourceRef ? [mem.sourceRef] : []`）。**UI 新建路径永远是 `[]`**。
- **`memoryId`** —— 只有纪念日写（`:658`）。`removeEvent` 会因为它拒绝删除（`:571`）。
- **`history`** —— 只在 `updateEvent` 追加，**全库无读取**（页面只显示「改过」）。只写不读。
- **版本字段：没有。** `updatedAt` 是全量覆盖式时间戳，`ta-proposal.js` 那套 `baseVersion` 乐观锁**不适用于日历**。
- **只写不读的死字段**：`deviceProtection`（只在 `:513` 写出一次，全库无读取）、`tentative`（只在 `:509` 写出，无读取）。

### 状态机

**没有状态机。** `status` 是一个自由字符串，`updateEvent(id, patch)` 接受任意键（`:549` 无白名单）。

- 值域（文案表 `page-calendar.js:46-49`）：`pending` / `confirmed` / `in_progress` / `completed` / `cancelled`
- 实际会写入的值：`'confirmed'`（`addEvent` 默认 `:508`；`saveAnniversary :654`）、`'pending'`（共同事件新建 `:1104`）、`'cancelled'`（`cancelEvent :559`）、`'completed'`（`:921`「做完了」）。**`in_progress` 只出现在文案表里，没有任何代码写入它。**
- **谁可以改**：任何能拿到 `Sleepy.calendar.updateEvent` 的人。数据层**无调用者鉴权**（`:537`）。UI 层的分工是：`char_schedule` 明确不给改（`page-calendar.js:880-883`）、共同事件只能答应/改期/取消（`:885-914`）、私人提醒可改期/完成/删除（`:915-938`）。
- **开始 / 结束会不会自动改状态：不会。** 全库没有定时器去推进事件状态（`upcoming:595` 只是读的时候过滤掉 `cancelled`/`completed`）。**事件永远不会自己变成「进行中」或「已完成」。**
- **重复事件**：规则 + 单个对象（`occursOn:452` 现算），**没有实例表**。`updateEvent` 改的是那一个对象 → **改未来实例必然影响历史实例**，且没有「只改这一次 / 只改未来」的选项。
- **模型 / 总结 / 主动消息能不能直接写日历：不能。** 全库 `addEvent` 的生产调用点只有三处：`calendar.js:647`（纪念日）、`page-calendar.js:1132/1137`（UI 新建）、`wj-canon.js:356`（帷境定史，走审阅台）。`scripts/` 下那二十几处是测试夹具。

**新建只有两种类型**（`page-calendar.js:1014-1015`）：`user_reminder`（我的提醒）/ `shared_event`（邀请他）。**刻意不给「替他建私人行程」**（`:991` 注释）。

## 3. 邀请与参与者状态

### 表达

`shared_event` 新建时（`page-calendar.js:1108-1114`）：

```js
participants: [ {type:'user', id:'user', state:'accepted'},
                {type:'char', id:ch.id, state:'pending'} ],
participantStates: { user: 'accepted' },
visibility: 'participants',
status: 'pending'
```

⚠️ **两套并存且不同源**：`participants[].state` 与 `participantStates` 都写了 user=accepted，但后续逻辑**只读 `participantStates`**（`page-calendar.js:150`、`:888`）。`participants[].state` 写完就没人再动。

### 状态推进（**这是全轮最硬的一条断裂**）

「答应这次」按钮（`page-calendar.js:887-894`）：

```js
var ps = ev.participantStates || {};
ps.user = 'accepted';
var both = ps.user === 'accepted' && ps[ch.id] === 'accepted';
c.updateEvent(ev.id, { participantStates: ps, status: both ? 'confirmed' : 'pending' });
```

**`ps[ch.id]` 在全库没有任何一处被赋值。** 全库 `participantStates` 只有 4 处命中：`:150`（读）、`:888`（读）、`:891`（写 user）、`:1113`（建的时候写 user）。

**【已跑】运行验证**：新建一条 `shared_event`（pending）→ 完整走一遍上面那段代码 →
`both = false`、`status` 仍为 `'pending'`、`participantStates = {"user":"accepted"}`。

> **结论：共同事件一旦发出，就永远停在「待确认」。** 没有任何路径让它变成 `confirmed`。
> 这同时意味着「未回应保持待确认」是成立的（因为回应了也一样），但「已确认」这个状态**不可达**。

### 其余几点

- **不存在「代替 user 接受」的路径**：`ps.user` 只在用户点按钮时置 `accepted`（`:889`）。
- **共同事件 vs 私人事件**：靠 `eventType`（`shared_event` vs `user_reminder`）区分，不看 `participants` 长度。
- **参与者权限 / 故事内知情 / 玩家可见性是否分开**：**只分了一半。** 玩家可见性由 `visibility` 管（但只在 `life-feed.js:111` 和显示文案里判）；**「故事内知情」没有任何字段表达** —— 没有「char 是否知道这个邀请」的记录位。
- **「事件能否被不同 App 引用、会不会复制成多条」**：We 会。`weEntries` 是独立表（`store.js:168`），从日历引用时**新建一条 `weEntry`** 并记 `sourceId`（`page-we.js:274` `sourceType:'calendar'`），原日历事件不动 —— 所以是**两条记录 + 引用关系**，不是复制正文。提议侧有 `dedupeKey` 幂等（`page-we-proposal.js:183-202`），手动新增路径无去重。
- **回源核实**：`page-we-proposal.js:131-144` 会拿模型给的 `sourceId` 回 `Sleepy.calendar.getEvent` 复核 —— 这是全库唯一「不信模型自报」的日历相关闸。

## 4. 时间与冲突判断

### 冲突函数（`calendar.js:482-493`）

只做**同一天内的 `HH:MM` 字符串区间重叠**：`eventsOn(charId, iso).filter(s < ee && es < e2)`。

**【已跑】三个假阴性**（都是真跑出来的）：

| 场景 | 结果 |
|---|---|
| 通宵班 `23:00 → 次日 01:00` vs 次日 `00:30—01:30` | **不报冲突**（`crossDay = []`） |
| 同一天，班 `23:00 → 次日 01:00` vs `23:30—23:50` | **也不报冲突** —— 因为 `endAt` 的 `timeOf` 取到 `'01:00'`，字符串比较 `'23:30' < '01:00'` 为 false |
| 存了 `timezone: 'Asia/Tokyo'` 的事件 | `conflictOf` **完全不读 `timezone`**（源码文本里没有 `timezone` 字样） |

> 一句话：**任何 `endAt` 跨过午夜的事件，都不参与冲突判断。**

其余：
- 已取消的不占时间（`:488`）；全天事件按 `23:59` 算（`:485`、`:490`）。
- **排序**：`eventsOn:473` 按 `timeOf(startAt)` 字符串排，全天（空串）按 `'99:99'` 排最后。
- **时间精度**：只到分钟，字符串是 `YYYY-MM-DDTHH:MM`。**无时区折算、无夏令时处理**（`tzNow:676` 只在喂模型时算一次「现在」，事件本身的时间就是裸字符串）。
- **离线恢复不会补造过去事件**：没有任何后台扫描会建事件，唯一的自动写入是 `wj-canon.js:356`（而且只写带日期的定史候选）。
- **当前时间推进是否只读**：**只读。** `timeFacts`（`calendar.js:722`）全程 `store.get`，唯一写盘的是 `cfgOf → cfgRec`（也不写，无存档时返回默认副本并且**不写盘**，`:128` 有注释）。

## 5. 执行器候选及真实回执

**`executor` / `idempot` / `receipt` / `reschedule`：生产代码零命中。** 没有统一动作层。真实存在的是**三条各自为政的写路径**：

| 路径 | 锚点 | 幂等 | 用户确认 | 真实回执 |
|---|---|---|---|---|
| ① 手机 delta | `phone.js:621 PHONE_OPS`（op 白名单）→ `:672 validateDelta` → `:909 applyDelta`；自动触发 `page-phone-ai.js:170 settle` | `runId` 有幂等意图；但 `phone.js:970` **无条件推进 `settledUntil`**，与 `page-phone-ai.js:192` 的注释不符 | 无（后台自动） | 无外部回执，只改本机 store |
| ② ta 提案接受 | `ta-proposal.js:212 fp 去重`、`:301 baseVersion 乐观锁`、`:292 高影响 needConfirm`、`:429 appliedRef` | fp + `requestId`（`:261 hasRequestFp`，但 `saveProposals` 实际不调它，去重靠 fp） | **必须手点** | **本地回执**（`appliedRef` 指向真实落库 id） |
| ③ 帷境定史 | `wj-canon.js:316 rec.written`、`:317 blockers`、`:356 calendar.addEvent` | `written` 标记 | 审阅台即确认台（`:341`） | 无外部回执，无 retry/timeout |

**最接近「真实回执 + 重试幂等」的一处**：`ta-life.js:307 confirmDraft` —— 判据是 `d.formalCharId` 是否为空，回执是 `core.upsertChar` 返回的**真实 charId**（`:310-313`、`:356`）。

**缺的东西**：没有 attempt 计数、没有 retry、没有 timeout、没有把「一次动作」登记成带 `status` 的持久记录。
`taProposals.STATUSES` 里有 `'failed'`（`ta-proposal.js:51`）但**全库没有任何一处写入它** —— 死状态位。
`api.js:389` 的 `subRetry` 是候补模型轮换，不是动作重试。

**能声明能力的地方**：没有统一的 `caps` 注册表。`tts.js:299` 的 `caps` 是 TTS 档位能力表（「发不发某个字段」的判据），不是权限闸。

## 6. ta proposal / follow-up 当前是否接入日历

**没有接入，而且字段名都不存在。**

- `followUpRequests` —— **全库零命中**（生产与测试都没有）。勘察单 F2 那条链不存在。
- 提案类型闭集（`ta-proposal.js:49`）：
  `['item_update', 'follow_update', 'promise_review', 'npc_event', 'impact_review', 'contact_candidate']`
  —— **六种里没有一种是「建日历事件」**。操作闭集 `:50`：
  `['add','update','resolve','flag_review']`。
- `taEvents`（`:47`）是 **ta 自己的私有表**（已成立 NPC 事件），与 `calEvents` **完全不互通**（除了都叫 event）。
- 提案 extra 白名单（`:59-63`）里也没有任何日期/日程字段。

逐条回 F 段七问：

| 链 | 是否存在 | 证据 |
|---|---|---|
| 1. ta 事项/承诺 → 日历候选 → 确认 → 事件 → 回写 | **不存在** | 无候选生成代码；`page-ta.js` 不引用 `Sleepy.calendar` 的写入函数 |

## 7. 主动消息、聊天发送、日历写入之间的边界

| 通道 | 谁发起 | 用户确认闸 | 写什么 | 回执 |
|---|---|---|---|---|
| **主动消息** | 程序筛候选（`page-proactive.js:124 gateFor`）+ **模型决策** | **无。** 唯一「模型决策直接生效」的通道 | 真往聊天插一条消息（`:283 chatStore.addMessage(..., proactive:true)`） | 事后写回 `ta-impact.js:492 noteProactive`（send 是终态、不覆盖，`:507`） |

| **日历写入** | **只有 UI 手点** 或 帷境审阅台 | UI 有（新建冲突时 `ui.confirm`；取消有 `ui.prompt`；删除有 `ui.confirm`） | `calEvents` | 无 |

2. **主动消息是唯一「模型输出 → 真实副作用」的通道**（往聊天里插一条真消息）。日历没有这条通道，这是好事。

## 8. 权限、世界隔离、用户确认和模型越权风险

### ✅ 站得住的

- **世界隔离**：`calConfigs` / `calEvents` 都过 `core.tagScope`，`eventsOf:441` 按 `sandboxId` 过滤，`core.js:360` 删房跟着清。
- **拆岛不串档**：`cfgRec:147-151` 与 `eventsOf` 都带 `sandboxId` 比对。
- **角色日程不可被 user 改删**：`page-calendar.js:880-883` 明确写明并只显示提示。
- **玩家查看幕后不改变角色知情**：`page-switch.js` 无任何 `calEvents` 引用；切视角只改 active 指针。
- **模型不能直写日历**：`addEvent` 生产调用点三个，全是人触发的。
- **提醒无执行**：`remindOn` 只有开关，`Notification` 全库零命中 —— **不会误发真实通知**。
- **金钱/定位/外部账号**：日历侧完全不碰。

### ⚠️ 三条真实风险

**风险 1（最高）：I02 注入侧没有 `visibility` 判定 → user 私人提醒泄进 char 的 prompt。**

`calendar.js:768-783`（`timeFacts` 的日程层）：

```js
if (cfg.scheduleOn) {
  var soon = upcoming(charId, 7, mine.iso).filter(x => x.event.eventType !== 'anniversary').slice(0, 5);
  // ↑ 只过滤了「不是纪念日」，没有 visibility / createdBy 判定
  lines.push('你近期的安排：' + ... e.title ...);

```

`upcoming → eventsOn → eventsOf` 也只看岛 + owner/participants（`calendar.js:439-447`）。
而「我的提醒」新建时写的正是 `ownerCharId: ch.id` + `visibility:'private'` + `createdBy:{type:'user'}`（`page-calendar.js:1095/1105/1118`）。

**【已跑】**：建一条 `visibility:'private'`、`createdBy:user` 的「秘密买礼物」→ 打开 `scheduleOn` →
`timeFacts` 输出 = `…你近期的安排：明天 20:00—21:00 probe2uaw秘密买礼物` → **`i02_hasPrivateTitle = true`**。

对照组：同一条事件，`life-feed.js:111 charViewOf` 判为 `''`（看不到），K03b 生活流 `compileLife` 输出**不含**它。
→ **同一条事件，K03b 挡得住、I02 挡不住。** `charViewOf` 在 `scripts/smoke.js` 里**零命中**，这条不一致没有任何测试覆盖。

**风险 2：共同事件永远停在 pending**（见 §3）—— 用户被告知「等他表态」，但 char 侧没有表态入口，实际上永远等不到。

**风险 3：`updateEvent` 无白名单 + 无调用者鉴权。** `patch` 任意键直写（`:549`），`status` 可以被设成任何字符串（包括不在值域里的）。目前没有越权调用点，但这是个敞开的口子 —— 将来接执行器时它是第一个要加固的地方。

补充：NPC 视角的日历 —— **没有专门处理**。`charViewOf(e, charId)` 可以传任意 id，但没有任何 NPC 分支，群聊装配也不接日历。

## 9. 四条闭环逐条判定

| 闭环 | 判定 | 断点 |
|---|---|---|
| **1 创建日程** | ✅ **完整**（用户手点这条路） | 约定/操作 → 表单 → 冲突提示 → 写入 → 展示 → 后续读取，六步全通。**但没有第二条路**：模型/ta 都进不来 |
| **2 邀请共同事件** | ❌ **断在「接受」** | 提出 → pending ✅；发送/送达（无真实送达，只有本地状态）；对方查看（**无记录位**）；接受（**char 侧无入口，`both` 永远 false**）；事件状态（永远 pending）；形成共同经历（**只能靠 We 手动新增**，不自动） |
| **3 执行动作** | ❌ **不存在** | 没有执行器层。最接近的是手机 delta（有 op 白名单）与 ta 提案接受（有回执）—— 但两者都不是通用协议，且日历这一侧完全没接 |
| **4 承诺核验** | ⚠️ **原承诺侧成立，落到日历侧不成立** | 承诺不会自动兑现（`ta-proposal.js:28/345/354`）✅；但「条件成立 → 日历候选 → 执行结果 → 完成标准核验 → 承诺状态更新」这条链**一步都不存在** |

## 10. 结尾（§7 要求的八项）

### 可复用的日历模块
- `Sleepy.calendar`（`calendar.js:842`）—— 事件 CRUD + 公共日期 + 时区 + `timeFacts`，**已经是全项目时间事实的唯一出口**（`prompt-engine.js:730` 注释写明「不要再在别处手写一份日期字符串」）。

- `conflictOf`（`calendar.js:482`）—— 可复用，但要先把跨日修了。
- `page-we-proposal.js:131-158` 的「`sourceId` 回源核实」—— 可复用的防伪造模式。

### 可复用的执行器或动作模块
- **没有通用执行器。** 可复用的**零件**有三个：
  `phone.js:621 PHONE_OPS` 的 op 白名单模式、
  `ta-proposal.js` 的「fp 去重 + baseVersion 乐观锁 + 高影响 needConfirm + appliedRef 回执」四件套、
  `ta-life.js:307 confirmDraft` 的「真实 id 回执 + 重试幂等」。

### 真正缺失的最小能力
1. **动作请求 / 结果 / 回执的最小协议**（`{actionId, kind, target, params, status:'pending'|'ok'|'failed', attempt, receiptAt, resultRef}`）—— 目前一个都没有。

4. **共同事件的「对方表态」入口**（否则 `confirmed` 不可达）。
