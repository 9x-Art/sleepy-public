# We 收藏馆 — 只读勘察与最小方案（2026-09-27）

> 只读勘察，未改动任何生产代码 / 测试 / 未提交 / 未部署。
> 视觉与产品参考：《Sleepy · We 收藏馆 Demo v1（门厅 + 藏品详情）》；真实仓库结合已完成的 We 首页（page-we.js）。
> 本报告只回答「读什么、打开哪里、真实结构、怎么降级、是否建新表、怎么隔离、怎么接入、首轮做哪些」，并给出需拍板的最少问题。

## 0. 一句话结论

**收藏馆在本仓库里不存在任何独立页面。** 当前 We 首页「去收藏馆 →」只是打开了 `favorites`（消息收藏夹 App），不是门厅 + 藏品详情。Demo 的门厅要的「藏品实体」（有来源、有归属、可进详情）目前只有 `weEntries`（共同记录，we 首页已在用）和 `favorites`（消息快照）+ 帷境票根（`wjTickets`）三个候选。**首轮最小闭环用 `weEntries` 扩展一个 `kind` 维度即可收一件有来源的藏品，不必另建 `weCollection` 新表**——它已进 DEFAULTS、已进删房名单、已接 scoped/tagScope、已有数据层 smoke 护栏。

## 1. We 首页「当前陈列 / 收藏数量 / 去看看」现状

全部位于 `page-we.js`（`index.html:228` 注册，`Sleepy.register('we', …)`）：

| We 首页区块 | 读取什么 | 打开哪里 | 行号 |
|---|---|---|---|
| 三格 facts「收 藏」计数 | `favoritesCount()` = `store.get('favorites')` 里 `sandboxId === scopeId()` 的条数（**只数聊天消息收藏**，不含帷境票根） | — | page-we.js:184-188, 392-396 |
| 「当前陈列」展台 `04` | 三个格：共同记录数 / 收藏数 / 接下来数（`exhibitCell`，全是数字占位） | — | page-we.js:453-471 |
| 「收藏里存着 N 条 / 收藏还是空的」行 | 同上 `favN` | **按钮「去收藏馆 →」→ `Sleepy.nav.open('favorites')`** | page-we.js:462-469 |
| 共同记录列表（收在「当前陈列」区块下） | `weList()` = `core.scoped(store.get('weEntries'))` 按 `at` 倒序 | 点卡片**无跳转**（首版只展示，无详情） | page-we.js:372-374, 476-490 |

**关键事实**：
- 当前 We 首页**没有 Demo 里的「去看看」**（Demo 的「去看看」是随机重遇区打开具体藏品/来源）。现状唯一的入口是「去收藏馆 →」= 打开 `favorites` App（`page-chat.js:3866` 注册），它把「聊天收藏（按岛）+ 帷境票根（全局）」两段列在一个列表里，无门厅、无分类、无详情。
- Demo 门厅的「当前陈列（本月陈列）+ 随机重遇 + 待确认 + 馆藏分类」**在仓库里都没有对应实现**；`favorites` 页是消息快照平铺列表。
- 所以「从 We 首页进收藏馆 → 打开一件藏品 → 看到来源」这条链，**终点（收藏馆详情）目前不存在**，需要新建一个 `collection` 页面，首轮从 `weEntries` 里取。

## 2. 五个候选来源的真实数据结构 / 归属 / 删除行为

### 2.1 `favorites`（D2 消息收藏）
- **key**：`favorites`（store.js:158 DEFAULTS = `[]`）。
- **结构**（写入 `page-chat.js:2357-2365`，长按一条消息 → 收藏）：
  ```js
  { id, chatId, chatName, role, content, savedAt, sandboxId }
  ```
  其中 `content = bubbleText(msg, idx)` 收的是**被点中那一个气泡**（可能带 `||` 多气泡切分），非整轮。
- **归属**：`tagScope(fav)` 盖当前 `sandboxId`（page-chat.js:2366）。**无 charId / userId / rootId**——只到岛级，区分不了「哪个角色 × 哪个 user」。
- **读**：`Sleepy.core.scoped(store.get('favorites'))`（page-chat.js:3882）。
- **删除**：全量 → 过滤 `id` → 落盘（page-chat.js:3946-3951，UI「移除」按钮）；拆岛走 `cleanupSandbox` scoped 名单（core.js:343 含 `'favorites'`）。
- **能否稳定引用原物**：**不能直接引用到消息本体**——它只存 `chatId`（聊天 ID）。原聊天删了（`getChat(chatId)` 为空）时，「去看看」报「原来的对话已经删掉了」（page-chat.js:3939）。它是快照，**不追踪消息级删除**，所以作为「收藏馆藏品」引用是**弱引用**：原消息删了，favorites 快照还在，但「来源跳转」失效。

### 2.2 `weEntries`（We 共同记录，**首轮主表**）
- **key**：`weEntries`（store.js:160-168 DEFAULTS = `[]`），新增于 2026-09-27 We 首页施工。
- **结构**（写入 `page-we.js:75-98`）：
  ```js
  { id, sandboxId, title, note, at,
    sourceType: 'manual'|'chat'|'calendar'|'moments'|'photo'|'offline',
    sourceId, sourceRef, refCharId, refUserId,
    createdBy: 'user', createdAt, updatedAt }
  ```
  只存**引用**，不复制聊天全文/图片本体（page-we.js:61-64 注释红线）。
- **归属**：`core.tagScope(entry, sandboxId)` 盖当前房章（page-we.js:92）；`refCharId`/`refUserId` 记录当时身份（`activeCharOnIsland`/`activeUserOnIsland`，page-we.js:283-284）。
- **读**：`weStore.list()` = `core.scoped(store.get(WE_KEY))`（page-we.js:68-71）。
- **写入**：`weStore.add(rec, sandboxId)`（page-we.js:75）。
- **删除**：**目前没有任何 UI 删除入口**（首页只读展示）。数据层拆岛清理已收录：`cleanupSandbox` scoped 名单（core.js:343 含 `'weEntries'`）。
- **能否稳定引用原物**：`sourceType` + `sourceId` 是弱引用——原物删除后 `sourceId` 仍留着，详情页需要「回源复核」判断原物还在不在，不在则降级（见 §4）。

### 2.3 `photos`（相册）
- **key**：`photos`（photos.js:46-49；不在 DEFAULTS，刻意后加，导出兜底靠 exportAll 扫带前缀键 store.js:446-451）。
- **结构**（写入 `photos.js:103-119`）：`{ id, caption, at, sandboxId, mediaId|url, w,h,type,size,name }`。
- **归属**：**岛级**（`tagScope` 盖 sandboxId，photos.js:119），**无 charId**（相册不分角色）。
- **读**：`Sleepy.photos.all()`（scoped）/ `allFull()`（写入方专用）；图片本体走 `media.url(mediaId)`（IDB，objectURL 活不过刷新）。
- **删除**：`photos.remove(id)`（photos.js:128-139）删记录 + **顺手删 IDB 本体**；拆岛清 `photos`（core.js:342）。
- **能否稳定引用原物**：照片是**独立实体**（`mediaId`），不绑定对话/朋友圈。若一件藏品以 photo 为来源，引用 `sourceId = photo.id`；照片删了，`mediaId` 失效 → 详情降级为「原图已删，只剩文字」。可作为藏品来源，但需处理图失效。

### 2.4 `calendar`（日历约定 / 共同事件）
- **key**：`calEvents`（calendar.js 事件表，删房名单 core.js:357）；`calConfigs` 是每 char 配置。
- **结构**（写入 `calendar.js:441-461`）：`{ id, sandboxId, ownerCharId, participants[], createdBy, visibility, eventType, sourceType, sourceIds[], time, place, title, … }`。
- **归属**：按 `(sandboxId, charId)` 隔离；`eventsOf(charId)` 内部已按 scopeId 过滤（calendar.js:385-393）。
- **删除**：**已成立过的 `shared_event` 只能取消不能删除**（`removeEvent`，calendar.js:508-522）——对「收藏馆引用日历」是**好事**：共同事件一旦成立就基本不可删，来源稳定。普通日程可删。
- **能否稳定引用原物**：`sourceId = 事件 id`；事件可取消（status 变 `cancelled`），详情降级为「该约定已取消」。

### 2.5 帷境票根 `wjTickets`（Demo「票根」品类的最接近现成物）
- **key**：`wjTickets`（wj-data.js:392）。
- **结构**（写入 `saveTicket`，wj-data.js:409-428）：`{ id, workId, title, reality, chapters, chars, cast[], at }`。**无 sandboxId**。
- **归属**：**全局不 scoped**（wj-data.js:384-390 注释：群岛作品不归属单岛，换岛不该消失；票根唯一真相在 wjTickets）。`wjWorks` 全局也不 scoped。
- **读**：`Sleepy.wj.tickets()`（wj-data.js:394）。
- **删除**：`wj.removeTicket(id)`（wj-data.js:430-434）只删票根，作品一个字不动；作品本身不随票根删。拆岛**不清**票根（不在 scoped 名单，故意）。
- **能否稳定引用原物**：`workId` 引用作品；作品删了（`wj.get(workId)` 为空）时「去看看」报「这部剧本已经不在门厅里了」（page-chat.js:3904-3906）。**弱引用**。

### 2.6 删除/失效矩阵（汇总）

| 来源 | 引用字段 | 原物删除行为 | 拆岛 | 详情降级策略 |
|---|---|---|---|---|
| favorites | `sourceId=chatId` | 聊天删 → favorites 快照仍在，跳转失效 | 清 | 「原来的对话已删除」，只留快照文字 |
| **weEntries** | `sourceId`（本表自存） | 原物删 → 记录仍在，回源复核判失效 | 清（已收录 core.js:343） | 显示「来源已不在」，留 title/note |
| photos | `sourceId=photo.id` | 照片删（记录+IDB 本体一起） | 清 | 「原图已删」，只留 caption |
| calendar | `sourceId=event.id` | shared_event 只能取消；普通日程可删 | 清 | 「该约定已取消 / 已删除」 |
| wjTickets | `sourceId=workId` | 作品删 → 票根仍在，跳转失效 | **不清**（全局） | 「剧本已不在门厅」，留票根样式 |

## 3. 能稳定引用原物的来源 & 详情降级

- **「稳定引用」按从高到低排**：
  1. **weEntries 本身**（引用 `sourceType/sourceId`，但源是快照式文字，最稳——它不依赖原物存活）。
  2. **calendar shared_event**（成立后不可删，最稳的「事件」引用）。
  3. **photos**（独立实体，mediaId 在 IDB，删除需显式动作）。
  4. **favorites / wjTickets**（快照式，原物删了只剩文字，跳转失效）。
- **详情页必须做「回源复核 + 三级降级」**（首轮实现「+ 看到来源」时执行）：
  - **原物在** → 正常显示来源标题 + 可跳转（去聊天/日历/相册/帷境）。
  - **原物删了但记录在** → 显示「来源已不在（原对话已删 / 该约定已取消 / 原图已删 / 剧本不在门厅）」，藏品本体（title/note）仍完整展示。
  - **藏品被拆岛删** → 列表里根本读不到（scoped 隔离），不存在「失效详情」。

## 4. 是否新建独立 `weCollection`？最小字段

**结论：首轮不新建独立表，扩 `weEntries` 一个 `kind` 维度即可。** 理由：

- `weEntries` 已经：进 DEFAULTS（store.js:168）、进删房名单（core.js:343）、走 scoped/tagScope、有数据层 smoke（smoke.js:8489-8545）和真机闭环（browser-we-test.js W1-W8）。
- 它已有 `title / note / at / sourceType / sourceId / sourceRef / refCharId / refUserId / sandboxId / createdBy`，**正好是「一件藏品」所需的最小骨架**——Demo 的藏品详情（为什么留下 / 你们分别写过 / 它从哪里来 / 状态）全部可由此映射。
- Demo 的「品类」= 票根 / 照片与拍立得 / 信件与卡片 / 音乐纪念 / 礼物与信物 / 地点纪念。这些是**藏品展示分类**，不是数据实体差异。给 `weEntries` 加一个可选 `kind` 字段（`'ticket'|'photo'|'letter'|'music'|'gift'|'place'|'other'`）就够分类用，**不新建表、不动 favorites 语义**（满足「不要改旧 favorites 结构」红线）。

**若要落到 `weCollection`（用户若更想独立表），最小字段**：
```js
{ id, sandboxId, kind, title, note, at,
  sourceType, sourceId, sourceRef, refCharId, refUserId,
  createdBy: 'user', createdAt, updatedAt, onDisplay: bool }
```
需同步进 DEFAULTS + `cleanupSandbox` 名单 + export 兜底 + smoke 反串断言。

> **待拍板 A（见 §7）**：扩 weEntries 加 `kind`（推荐，最省）vs 另建 weCollection 独立表。

## 5. 一件藏品归属哪座岛 / 哪对 user/char；切岛如何避免混看

- **归属**：`sandboxId`（房章）标识岛；`refCharId`（角色大号/皮套 id）+ `refUserId`（马甲 id）标识「哪对身份」。首轮 `createdBy:'user'` 固定（page-we.js:87 注释「首版只允许 user 创建」）——**User 主动收进**，不自动建 char 提议（符合本轮目标）。
- **不混看**：所有读取走指针卫兵——
  - `core.activeSandbox()` / `core.scopeId()` 定岛（page-we.js:344-349，无房空态）。
  - `core.activeCharOnIsland()` / `core.activeUserOnIsland()` 定「当前身份」——**必须是本岛名册里的一件才非 null**（page-we.js:352-358，两边缺一空态）。**禁止直接用 `activeChar()`/`activeUser()`**（core.js:987-1015 红线：不过岛闸）。
  - 读列表 = `core.scoped(store.get('weEntries'))`（page-we.js:70），天然只返回当前房。
- **切岛刷新**：`onShow(ctx){ paint(ctx) }`（page-we.js:691-693）就是 page-switch.js:246-258 调 `topCtx().refresh()` 的落点 → 切岛后自动重读当前房，不串线。已在 browser-we-test W5/W6 验证。
- **群岛 vs 孤岛**：`sandbox.kind`（'archipelago'/'isle'）。首轮不做岛选择器，We 只展示当前房（We 首页既定产品边界）。

## 7. Demo 门厅 / 分类 / 藏品详情：哪些首轮能真做，哪些必须后置

### 首轮（本轮目标纵向闭环内，全部有真实数据支撑）

1. **从 We 首页进收藏馆**：新建 `collection` 页（`page-collection.js`，`Sleepy.register('collection', …)`），把 We 首页「去收藏馆 →」的 `nav.open('favorites')`（page-we.js:467）改成 `nav.open('collection')`。
2. **用户主动收一件有来源的藏品**：复用/扩 `openAddDrawer`（page-we.js:194-295）的「从一段现成记忆带进来（可选）」——`sourceCandidates()` 已给日历/线下候选（page-we.js:102-146）；首轮**只做「user 主动确认后落表」**，候选点了才写 `sourceType/sourceId`，纯手记也行。
3. **在馆内打开详情、看到来源**：藏品详情 = 复用 `weEntries` 字段渲染（title/note/at/sourceType/sourceRef/createdBy），「它从哪里来」区按 `sourceType` 展示来源标签 + 若原物可回源则跳转。
4. **刷新仍在**：weEntries 走 localStorage store，onShow/paint 重读，W7 已证。
5. **切岛不串线**：scoped + 指针卫兵，W5/W6 已证。

### 必须后置（本轮不做，明确列出）

- **Demo 门厅的「本月陈列（你布置 / 换一组）」**：需要 `onDisplay` 语义 + 布置交互 → 后置（`onDisplay` 字段可留空）。
- **随机重遇区**（「今天恰好遇到」）：需按日期/歌/纪念日做「恰好」匹配 → 后置。
- **待确认卡片（char 提议「收进馆里 / 暂时不用」）**：用户明确本轮不做 char 提议、双方确认 → **整块后置**。
- **馆藏分类索引（票根 4 / 照片 5 / … 数量）**：可先按 `kind` 分组给**真实计数**（有 weEntries 数据），但「地点纪念」这类空品类要空态占位；若首轮无 `kind` 数据则全显示 0/—。
- **DIY / 音乐纪念 / 贴纸套 / 双方共同编辑**：用户明确不做。
- **详情页的「你们分别写过」（我 / char 双栏）**：需要 char 侧文字（首轮 createdBy:'user' 无 char 提议）→ 后置，首轮「为什么留下」只用 user 填的 note。
- **票根品类**：可首轮把 `wjTickets` 作为「全局票根」单独一段带进来（不属单岛），但**不做**跨来源合并成一件藏品的复杂逻辑。

### 首轮边界（对齐用户约束）

- ✅ 改 We 首页入口从 favorites → collection（页面级，不动 favorites 数据语义）。
- ✅ 新增 `page-collection.js` + index.html 脚本行 + （可选）桌面一格。
- ✅ 用 weEntries（+ 可选 `kind`）收有来源藏品，详情看到来源。
- ❌ 不改 `favorites` 结构。
- ❌ 不自动把全部聊天收藏 / 照片搬进馆。
- ❌ 不做 char 提议 / 双方确认 / DIY / 音乐 / 贴纸套。

## 8. 需要拍板的最少问题
