## 一、现状链路（动手前必须知道的）

| 链路 | 现状 | 位置 |
|---|---|---|
| char 常驻地点 | `char.city/region/timezone` 三件套，contact-edit 可编辑 | `page-idcard.js:558-612,796-800` |
| 时间注入 | `calendar.timeFacts(charId)`：「你的现在」读 char 时区；「user 那边」读**设备本地时间** | `calendar.js:665+` |
| 语言推断 | `calendar.langOf(charId)` 从常驻地点推 → 翻译闸门；REGION_LANG 六键 | `calendar.js:109`、`calendar-data.js:301` |
| 法定假日 | regionMeta(REGIONS)，**CN 有官方调休数据，JP/KR/US/UK 只有规则注记（builtinYears:null），NONE 不注入** | `calendar-data.js:246+` |
| user 侧地点 | 马甲**只有 city 一个字段**；upsertUser 新建分支丢 city、不 tagScope；桌面双城时间 offset 写死 0/7 | `page-idcard.js:1160`、`core.js:536-545`、`page-desktop.js:1126-1134` |
| 换岛红线 | 换岛=换数据+视觉；岛内身份只换 activeCharId/activeUserId；NPC 归整岛 | MEMORY 语义红线 |

**比审查报告乐观的部分**：地区/时区/语言的基础设施其实已经铺到 5 国（REGIONS × TIMEZONES × REGION_LANG），日历对国外地区已有降级（builtinYears:null → 只算周末+规则注记，不猜未公布数据）。**缺的不是数据，是入口和 user 侧的口径。**

## 二、时区会影响什么（逐一下游，判定是否要同步调整）

| # | 下游 | 现状 | 要不要同步调 |
|---|---|---|---|
| 1 | **char 的时间认知**（timeFacts「你的现在」） | 读 `char.timezone` | 要 —— 岛级设定的值必须能进到 timeFacts。这是本方案的核心问题（见 D1） |
| 2 | **user 的时间**（timeFacts「user 那边」） | 设备本地时间 | 要 —— user 马甲有自己的时区后，应读马甲时区、设备时间兜底。否则「你在东京他在纽约」永远只显示设备时间 |
| 3 | **语言推断**（langOf → 翻译闸门） | char 从 placeOf 推；user 侧**整个绕过**（马甲无 region） | 要 —— 马甲补三件套后 user 语言推断自然成立，顺手接上 |
| 4 | **日历法定假日** | 按 REGION 算，国外有规则注记降级 | **不用改** —— region 表已有；换地区后 timeFacts 用 char 时区的 iso 算周几/假日，本来就对（跨时区连「今天周几」都换算对了） |
| 5 | **聊天/手机/朋友圈 UI 的时间显示** | 全部设备时间 | **不改** —— UI 是「我」的视角，微信也显示本机时间；列表时间显示对方时区反而是错的 |
| 6 | **消息时间戳** | 绝对时刻（Date.now），显示时本地化 | **不改** —— 同上 |
| 7 | **实时性** | timeFacts 每次注入实时算 | **无需同步机制** —— 没有「改了要推送」的问题，下一轮对话自动生效 |
| 8 | **NPC** | 无独立地点，归整岛 | **跟随岛**：NPC 不单设时区（要设也是岛级统一覆盖，不逐个填） |

结论：**要同步调整的只有 3 处**（表里 1/2/3），而且全是「把新数据接进已有读数点」，不动结构。

## 三、设计决策点

### D1 数据归属：不加 override，直接设在档案上 ✅ 2026-09-21 与用户对齐

初稿建议过「岛级覆盖 `placeOverride:<sbId>`」，查证数据模型后**作废**：

- **皮套 / NPC 是按房建的**（`core.js:456-461`：`kind !== 'main'` 自动 `tagScope`）—— 物理隔离，直接在档案上设 city/region/timezone 就天然按岛分开。用户说得对。
- **大号本体（kind:'main'）是全局的**（`core.js:458` 注释明说「不能带房标签」）；**user 马甲也是全局键**（`userMasks` 不 scoped）。但语义正确：main 和马甲是「同一个人」，跨岛共享同一个时区是**对的**；想要两套设定就分开建档（用户的做法）。

**结论：不新建任何键。** 要做的是把**编辑入口**补上（审查四.1：浮岛档案页现在只显示不编辑；mask-list 只能切不能编辑）+ 马甲三件套（D3）。

### D2 国籍 ≠ 常住地：两条轴分开 ✅ 2026-09-21 用户点名要清晰

用户原话点破的场景：「我是美国人但我现在住在中国，那我用的什么时区，在哪里设置」。

设计成**两条轴，职责分开**：

| 轴 | 字段 | 管什么 | 不管什么 |
|---|---|---|---|
| **常驻地点** | city / region / timezone 三件套 | 时区、语言推断、法定假日、日历 —— **一切计算** | 文化身份 |
| **国籍** | 显示层（从 region 映射或自由填写） | 档案展示；可作日历「文化节日组」的默认勾选建议 | **永不参与时区/语言计算** —— 「美国人住中国」时区就是 Asia/Shanghai |

每处编辑入口都写明一句话：「时区跟**常住地**走，不跟国籍走」。设置位置：

- char：浮岛角色档案页补「编辑资料」入口（走 contact-edit 同款三件套，全局字段，皮套按房建天然隔离）
- user：mask-edit 的「城市」单行升级成三件套（对齐 char 口径）

### D3 user 侧：马甲补齐常驻地点三件套

`mask-edit` 的「城市」单行升级成 city/region/timezone 三件套（对齐 char 口径），同时修：

- `upsertUser` 新建分支丢 city、不 tagScope（审查四.3 的锅，本来就要修）
- 桌面双城时间 offset 写死 0/7 → 改读两边 timezone
- timeFacts「user 那边」改读当前马甲时区，设备时间兜底

### D4 「user 那边」措辞

timeFacts 里「user 那边」的判断依据从「设备时间」变成「当前马甲时间」后，无马甲（user 没填地点）时行为不变 —— 兜底设备时间，语义不变。

## 四、施工切分（建议）

本方案与审查四.1（浮岛编辑入口缺失）、四.3（user 三件套）是**同一批**（都动 island/idcard 页、共享同一批读数点）：

1. **浮岛批**：四.1 编辑入口 + 四.3 user 三件套 + 本方案 override + 桌面双城时间修正
2. **四.2 NPC 口径收敛**：独立施工卡（core.js 唯一 `npcsOfRoom()` 全仓替换，工作量大但独立）

验收要点（施工时展开）：

- 皮套档案把时区改成东京 → 当轮对话 timeFacts「你的现在」是东京时间；另一座岛的同一设定互不影响（按房隔离）
- user 马甲设纽约 → 「user 那边」显示纽约时间（不是设备时间）；无马甲回落设备时间
- 语言：char 常驻东京 → langOf 推日语，翻译闸门按此走
- 日历页选日本 → 只算周末+规则注记，页面明示「未公布年份不猜」
- 国籍只是显示/文化默认，改国籍不动时区；改常住地时区立刻跟着变
