## 2. 修正 A4：装配判断

### 2.1 前稿的错误

前稿 §4 A4 写「线上已接 shell，线下若也接会重复注入」，并建议**线下只接 N/S2**。
**这个推理错误**：它把「`shell` 是跨场景共享的**卡对象**」误读成「同一次请求内会被注入两次」。

### 2.2 事实

- **线上请求**：`page-chat.js:2630` → `assembleOnline` → 读 `cardBody('shell')` 或 `btDec.shellText`（`prompt-engine.js:1316`）。
- **线下请求**：`page-offline.js:1145` → `assembleOffline` → 读 `cardBody('shell')`（`prompt-engine.js:1591`）。
- **两者是两次独立调用、两个独立 `messages` 数组、两次独立 API 请求。**
- ⇒ 线上请求里 B/P/L 出现一次，线下请求里 B/P/L 出现一次，**互不构成重复**。

### 2.3 修正后的目标与方案

**目标（不变）**：线下每次请求 = `B + P + L + N + S2`，**各模块各一次**，无缺无重。

**槽位契约（可以按前稿方案核对）**：

| 槽 | 模块 | 对应 `PLANS.offline` 前三项 / 后两项 | 状态 |
|---|---|---|---|
| `shell`（C01-C03） | `B` + `P` + `L` | `['B','P','L']` | 契约一致 |
| `f2`（C04） | `N` + `S2` | `['N','S2']` | 契约一致 |
| 拼平校验 | 两者顺序拼起来必须**逐项等于** `PLANS.offline` | `['B','P','L','N','S2']` | 与 `behavior-text.js:56` 一致 |

**注意 `PLANS.offline` 的实际顺序**（`behavior-text.js:56`）：
```js
offline: Object.freeze(['B', 'P', 'L', 'N', 'S2'])
```
⇒ shell 取前三、f2 取后两，拼平正好等于全量。**契约成立。**

### 2.4 共享 shell 的用户 override（**不能因此省掉线下共用模块**）

**关键区分**：
- `cardBody('shell')` 读的是**同一个** `overrides['shell']` 存储键（`prompt-engine.js:812-816`），
  所以**用户改一次 shell，线上线下都受影响** —— 这是**共享数据**。
- 但线上判「被改过」用的是 `btCardsTouched()`（`:113-115`）= `isOverridden('shell') || isOverridden('f1') || isOverridden('c05')`；
  线下若照抄同一函数，会被**线上专属的 f1/c05** 拖成 `touched`，导致**用户只改了线上 f1 就把线下也拖回退**。
  ⇒ 线下必须**只判自己那两张**：`isOverridden('shell') || isOverridden('f2')`。

**结论（明确写清，防止被误读成「可以省」）**：
> 共享的是**用户 override 文本**，不是**共用模块的注入义务**。
> 线下请求仍然必须**独立获得 B/P/L/N/S2 全部五段**，各一次。
> override 只决定「读新正文还是回退旧正文」，**不减少模块数量、不改变模块清单**。

## 3. 修正 B1：N/S2 与输出协议的职责划分

### 3.1 前稿的错误

前稿 §4 B1 写「新增 `BT_F2_OFFLINE` = N+S2，**由 `offlineOutProto` 演化，不另写协议**」。
**职责混淆**：把「行为正文」定义成了「协议生成器的衍生物」，并预设了「要新建一份平行协议常量」。

### 3.2 修正后的职责划分（两类完全独立）

| 类别 | 来源 | 形态 | 是否需要新建 |
|---|---|---|---|
| **行为正文** N + S2 | 冻结模块 `Sleepy.behaviorText.forScenario('offline')` | **只读纯函数**，返回冻结正文，与协议无关 | ❌ **不新建任何常量**，直接取 |
| **输出 JSON 协议** | **现有** `offlineOutProto(session, needScene)`（`prompt-engine.js:1509-1553`） | 程序生成，**读 session 开关**（`showSuggests` / `timeAdvance` / `pendingSetup` / `transAsked`） | ❌ **不新建、不改、不克隆** |

**为什么线下不需要像线上那样新建一个协议常量？**
线上需要 `BT_C05_ONLINE`（`:242-251`）是因为**旧 `CARD_DEFAULTS.c05` 里混着需要退役的表达配额**（`:405-416` 的「每条气泡 1-2 句」「2-7 个气泡」等）。
线下的 `offlineOutProto` **本来就没有那类配额**，它是按 session 开关动态生成的**程序槽**（`OFFLINE_SLOTS` 里 `c05off` 是 `kind:'program'`，`prompt-engine.js:1404-1405`）——
**它不需要迁移，也不需要副本。**

**因此修正后的 F2-B 只有一处正文替换**：
- `f2` 槽（`prompt-engine.js:1592`）：`btDec.ok ? btSlotText(N,S2) : cardBody('f2')`
- `c05off` 槽（`:1636`）：**一行不动**。

## 4. R1–R5 重新处理：不从「旧稿更细」推导「删除必然回退」

### 4.1 撤回前稿的推导

前稿 §3.3 把五条列为「旧稿独有职责 → 删除即行为回退 → 需逐条裁决补写」。
**这个推导不成立**：旧稿某处更细，只说明**它写了更多**，不说明**冻结稿没写就会退**。
真正要判断的是三件事：**① 冻结稿是否已覆盖；② 剩下的部分属于"细则"还是"风险"；③ 风险是否需要实测才能确认。**

### 4.2 三分法

#### 第一类 · 已被冻结稿覆盖（前稿的"独有"判断过头了）

| 前稿编号 | 位置 | 前稿说"独有" | 复核结论 |
|---|---|---|---|
| **R1** | `shell:269-272` | 「角色声音」力度独有 | ❌ **不是独有**。P 首段「依据其资料、相关经历与当前状态，理解此刻的关注、愿望、顾虑和立场。选取与处境有关的部分形成言行」+ P 末段「文学性的角色念头只在有效视角与输出协议允许的范围内表达」（`behavior-text.js:42`）已给正面依据。`:271` 的「不要磨成中性话」在 E 模块「用词、称呼、语气、直接程度与发送节奏体现人物」（`:44`）有对应。 |

**T5–T9 样本设计（只写设计，不调模型）**：
- T5 连续 3 轮自由闲聊 → 看每轮最后一句是否都是问句/总结句。

## 5. 诊断：必须对应实际请求（最小字段与出口设计）

### 5.1 前稿的不足

前稿 §4 A6 写「诊断出口（页面可见）：复用线上预览的槽表」。
**问题**：`page-presets.js` 的 `runOnline`/`runOffline`（`:463`/`:492`）是**打开设置面板时重新装配一次**，与用户真机那次请求是**两次独立装配**。
⇒ **预览通过 ≠ 真机请求走了同一路径**（用户可能在两次之间改了 override、模块版本可能变、装配时机不同）。

### 5.2 必须区分的两类诊断

| 类别 | 采集点 | 用途 |
|---|---|---|
| **① 预览装配诊断** | `page-presets.js:483`（线上）/ `:507`（线下）调 `assembleOnline/Offline` 的返回值 | 看**结构**：槽位顺序、tokens、模块是否齐 |
| **② 实际请求诊断** | `page-chat.js:2630`（线上）/ `page-offline.js:1145`（线下）**调用点当场** | 证明**那一次出站请求**用了哪条路径 |

⇒ **只有 ② 能作为「真机走了新路径」的证据。** ① 只能证明「装配函数在当前配置下会产出新正文」。

### 5.3 最小诊断字段（不采聊天正文、不采敏感配置）

线下 `assembleOffline` 返回值新增（线上已有 `behavior`，线下无 —— `:1666` 目前是 `{messages, slots}`）：

```js
behavior: {
  used:     boolean,   // 本次装配是否采用新正文
  reason:   string,    // 固定原因码，闭集，不含异常全文
  touched:  boolean,   // 是否因用户 override 回退
  VERSION:  string|null,  // 模块版本锚，不匹配即回退
  modules:  string[]   // 本次实际取到的模块 id 序列
}
```

**隐私边界（硬约束）**：
- 只带**固定原因码 + 版本串 + 模块 id**，**不带**任何异常消息全文、prompt 正文、user override 内容、聊天正文、API 配置；
- 与线上 `btDiag`（`prompt-engine.js:1281-1287`）**同构**，便于一份出口同时服务两侧。

**采集点**（最小改动）：
- 线上：`page-chat.js:2630` 已有 `built`，**加一行**把 `built.behavior` 挂到本次请求的返回元数据上；
- 线下：`page-offline.js:1145` 已有 `built`，同样加一行；
- **不写进聊天记录、不进 `store`**（除非你要求持久化，见 §6 待裁决 2）。

### 5.4 出口设计（三层，缺一层就等于没做）

| 层 | 位置 | 显示 |
|---|---|---|
| L1 · 请求内 | 出站那次请求就地 | **不进 UI**，只随返回结构存在（供 L3 取） |
| L2 · 会话内瞬时 | 线下场景页顶部一条极细状态行 | 「本次：新正文 B/P/L/N/S2 · 无 override」/「本次：旧 F2（原因：user-override）」；**下一轮发送即刷新** |
| L3 · 事后取证 | 设置页「关于 Sleepy」开发者区一行 | 只显示**最近一次**的 `used/reason/VERSION/modules` + 采集时间戳 |

**明确不做**：不写聊天记录、不入库、不导出、不采 override 内容。
**若不做 L2/L3，等于回到前稿那个「有生产无出口」的坑** —— 上一轮线上就是这个状态（`behavior` 有字段、无消费者、无法导出），本轮不能再犯一次。
