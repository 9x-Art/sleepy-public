## 一、一句话说明白

这不是「加几个页面」，是给整个 App **补上「作用域」这一层**：
sleepy 从「角色树 + 换肤」升维成「**以沙盒（房子／岛屿／存档）为顶层容器的多宇宙**」。

现在的状态是：切号只切**皮肤**（角色卡、情绪印章、思念电量、双城时间），
数据其实还在同一口大锅里 —— `chat-list` 列全部对话不做任何过滤，
`photos / todos / diaries / favorites / moments` 全是全局单份。
房子一落地，这口锅必须按房切开。

## 二、目标架构（三层）

```
造物主层   浮岛（云海漫游）── 孤岛 1v1 ／ 群岛 1vN ── 存档列表 ── 岛屿配置台
                                                                    │ 降落
局中层     桌面（每个岛一份，独立美化）── 聊天 App ── 底栏 4 Tab
                                                                    │ 撤离（捏合／下拉）
           ────────────────────────── 回到云海 ──────────────────────
```

- **降落落点是「桌面」，不是 4 Tab。** 4 Tab 是聊天 App **内部底栏**（微信式），
  不是全屏界面。（第一版理解错过一次，已纠正。）
- 造物主层与局中层的**视觉语言是不同的**：造物主层用树状／星型拓扑的「关系」视角，
  局中层用平铺列表的「社交」视角。

## 三、已确认的设计决策（**以后不要再反复**）

| # | 决策 | 说明 |
|---|---|---|
| 1 | 沙盒 = 顶层容器，两形态 | **孤岛** 1 User × 1 Char（绝对封闭）／**群岛** 1 User × N Char（可拉群、可查手机、朋友圈雄竞） |
| 2 | 存档 = **平行存档，两段人生** | 记忆与业务数据按沙盒物理切开。同一个角色住在两间房里 = 两段互不知情的人生 |
| 3 | 角色本体**全局共用**，小号与 NPC **按房建** | 本体＝名字/头像/人设/红线/文字锁脸/图片锁脸；小号(皮套)、NPC 挂在房内 |
| 4 | 桌面差异只在**步骤与数据** | 孤岛：打开即该角色桌面。群岛：先选角色再进。**App 集合完全相同，不做隐藏** |
| 5 | 桌面 = 每个岛**整份独立** | 结构（pages）+ 配色 + 字体都按岛各存一份，互不影响 |
| 6 | 4 Tab = 聊天 App 的**底栏** | chat（消息）／通讯录／朋友圈／我 |
| 7 | 通讯录 = **只读映射 + 平铺列表** | 只显示当前沙盒的成员，**不要树状图**（树状图归造物主层）。加人/建小号/改认知回配置台 |
| 8 | 马甲（User 侧小号）**完全按房分组** | 每间房独立一套。全局 `activeUserId` 退化为「每个沙盒自己的当前马甲」 |
| 9 | 「我」页 = 钱包／表情包管理／设置 | 详见 P2 |
| 10 | 全局设置是**系统级** | API 连接、备份、外观留在桌面设置 App，**不随房变**。房内按 char 单独配 API ＝ 后续批次 |
| 11 | 沙盒数据存法 = **键内加 `sandboxId` 字段** | 不新建独立存储键（见「四、数据模型」的理由） |
| 12 | 查手机**两个形态都做** | 孤岛也做。机制可复用 `core.unmask()` + `dropEvents` 的注入管线 |
| 13 | 配置台**不做世界书挂载** | 世界书模块（B）已独立完成，不要重复造入口 |
| 14 | **浮岛 = 名片夹的进化版，是取代不是并存** | 加了浮岛就必须把名片夹去掉。原「名片夹（树状列表）」整页已删除；<br>它的职责拆到 `island`（哪几间房）/ `island-config`（房内捏人）/ `contact-edit`（角色骨架六字段）。<br>桌面那个格子 `p1-idcard` 的 `app` 从 `contacts` 改成 `island`，标签改成「浮岛」 |
| 15 | **浮岛是三层，不压成两层** | ① `island` 一屏一座岛，**左右滑动**（孤岛 / 群岛），**不摆任何存档**；<br>② 点某座岛才是 `island-saves`（它的存档列表 + 新建）；③ 点存档才进 `island-config`。<br>**两座岛之间不画任何连线** —— 它们只是两种房型，像货架上并排的两样东西，没有关系可言。<br>红线是用在「我 ↔ 角色」之间的（决策 21），不是用在这里的。<br>**云海上方不放标题和诗句**（放过一句「霓为衣兮风为马」，用户问「为啥上面是这个诗句呀」—— 它在说别人的事；每座岛各配一句就够了） |
| 16 | **房名不是用户填的东西** | 新建存档**不弹输入框**，配置台里也**没有「改名」**。<br>一段存档的标题由**房里的人**推出来（`island.roomTitle()`）：<br>空房 →「空着的一座岛」；一个人 → 角色名；两三个 → 并列；再多 →「A、B 等 N 人」。<br>`sandbox.name` 字段保留（留给以后的备注 / 搜索），但不由 UI 写入 |
| 17 | **造物主层的文案用古诗** | 孤岛「一生一代一双人」（纳兰性德《画堂春》）／群岛「乱花渐欲迷人眼」（白居易《钱塘湖春行》）／<br>浮岛首页「霓为衣兮风为马，云之君兮纷纷而来下」（李白《梦游天姥吟留别》）。<br>**不要再写「1v1 纯净沙盒·两个人，绝对封闭」这种说明书**（smoke 里有断言钉住） |
| 18 | **配置台用关系树，不用列表也不堆竖塔** | 「我」在最左，角色往右排开，NPC / 皮套挂在自己那个人下面。空位画成虚线圆圈，点它就是加人 |
| 19 | **「我」下面也能挂 NPC** | `characters.parentType`：`'char'` 挂在角色名下 / `'user'` 挂在「我」名下。<br>两种 id 在不同命名空间，**不能靠 id 前缀去猜**。`core.userNpcs(userId)` 读「我这边的人」 |
| 20 | **从关系树加人走「加人设 / 加 NPC」各自那一页** | 「**加人设**」= 名字 / 头像 / 人设 + 一个「**有小号吗**」开关（打开才**展开**小号的设置，关着就整个收起来）。<br>「**加 NPC**」= 名字 / 头像 / 人设，**没有**小号开关 —— 皮套本来就是「大号对外用的另一张脸」，NPC 不存在小号。<br>那个带「大号 / 皮套 / NPC」三选一身份切换器、所在城市、状态签名的完整页**没有删**，从这一页最底下的入口进。<br>用户原话：「点击加 char 就是只加 char」「不要这样！！！」 |
| 21 | **整棵树「整体」居中（不是「我」居中）** | 红线画在「我 ↔ 角色」之间（月老那种意象）：两条平行的弧 = 一条丝带的两边，**向上拱**，<br>关系文字压在**两个圆之间的正中间**把带子截断。<br>角色右 1、左 1、右 2、左 2 交替排开（`sideOf(i)` / `colOf(i)`）。<br>**位置算法**：先算出相对于「我」的**包围盒**（含每个人半径，虚线空位也算），<br>再整体平移 `xMe = W/2 − (lo+hi)/2` 使包围盒中点落在画布中心 —— 于是「我」会自己漂到该在的地方。<br>用户原话：「总的来说这个总体要在中间，不是指 user 一定要在中间，是**整体**！不然你不觉得视觉偏了么」<br>**别把「我」钉在正中** —— 角色全在右边时那样重心是往右倒的。<br>与之相对：我 → NPC、角色 → 皮套 / NPC 一律**淡绿细线** —— **红的是「我和你」，绿的是「谁属于谁」**。<br>拱多高是**算出来的**（`bowFor()`：对前面每一个人求出「从他头顶过去至少要抬多高」，取最大值），<br>**不能写死**；向下弯也不行（节点下方挂着名字，会正压在上面）。标签最多 6 个字 |
| 22 | **浮岛两座岛之间不画任何连线** | 曾经画过一条跨屏彩带，是理解错了 —— 要连起来的是「我」和角色，不是这两座岛（它们只是两种房型，<br>像货架上并排的两样东西，彼此没有关系）。`.isl-tie` 已删除，红线只在配置台的关系树上 |
| 23 | **桌面上横向容器要自己补「切页」的通道** | `overflow-x:auto` 在鼠标下**拖不动**（那是触摸的手势），光有底部页码点等于没切法 ——<br>用户反馈「也没能右滑」。补四条：**鼠标拖拽**（pointer 事件，触摸不插手）、**两侧箭头**、**页码点**、触摸滑动。<br>拖拽期间要临时 `scroll-snap-type:none`（mandatory 会在每帧抢 `scrollLeft`），<br>拖完（位移 > 8px）紧跟的那次 click 要在**捕获阶段**丢掉，否则会误进那座岛 |
| 24 | **「加人设」的空位只占最近那一格** | ① 还没人 → 右边第一格；② 有一个了 → **左边第一格**（这时两边正好对称，也就是用户要的<br>「往左右加 char」）；③ 两侧第一格都有人 → **不画**（加人走下面那个大按钮）。<br>孤岛住满时也不画，而且主按钮那行**整行换成说明**（「孤岛只住得下一个人 …」）——<br>用户原话「为啥右边还有加人设」「然后点哪里加呢」：多了不行，少了也不行。<br>**别让它一直往外排**（右 2、左 2…）：树会越来越宽要横向滚动，空位还容易被挤出屏幕外，<br>那就又回到「点哪里加呢」 |

## 四、数据模型

### 新增

```js
sandboxes: [{
  id, kind: 'isle' | 'archipelago',
  name, cover,                 // 存档卡：名字 + 封面
  charIds: [],                 // 这间房有哪些大号（kind='isle' 恒为 1 个）
  maskIds: [],                 // 这间房「我」有哪几件马甲（决策 8）
  theme: {...},                // 每岛一套配色 + 字体（决策 5）
  deskVersion, pages: [...]    // 每岛一份完整户型（决策 5）
}]
activeSandboxId
```

### 改造（新增 `sandboxId` 字段）

`chats` · `memories` · `links` · `photos` · `diaries` · `todos` · `favorites` · `userMasks`

`characters` 特殊：`kind:'main'`（角色本体）**全局一份，`sandboxId: null`**；
`kind:'sub'|'npc'`（小号／NPC）**带 `sandboxId`**，按房建（决策 3）。

### 为什么不是「每房一套独立存储键」

`sleepy.v1.sb.<id>.chats` 这种做法隔离更彻底，但 `store.js` 的前缀、遍历、
导入导出、体积统计全要大改，迁移还得逐键搬运，P0 会直接重一倍。
键内加字段的隔离度靠「**所有读取点强制过沙盒过滤**」同样拿得到 ——
代价是这条纪律必须写进 smoke 断言，不能靠自觉。

### 🐞 返工时挖出来的真 bug（会串档，值得单记）

`addLink` / `setBarrier` / `setCognition` / `setRelation` / `unmask` 这五处都在
**全量**列表里找「第一个匹配」的 link —— 可同一对 `(Char × User)` 在**每间房里
各有一条** link，全量里第一条很可能是**别的存档**那条。
后果：写关系 / 撕障壁 / 改认知会写到别的存档上去，**串档而且不报错**
（实机复现：在 A 房写的关系，B 房读到的是 B 自己那条 —— 因为 A 房那条被写脏了）。

修法是 `core.linkSlot(charId, userId)`：扫全量快照（保住引用，改完能落盘），
但**只认当前房那条**。smoke 里配了一条专门的回归断言
「同一对关系在两间房里互不串」，会检查两间房各持一条 link 且内容互不影响。

### 🐞 第三轮又挖出两个真 bug

**① 配置台读的是「当前降落的那间房」，不是「被点开的那间房」（会串档）**

`linkSlot()` 里的房是 `scopeId()` —— 也就是 `activeSandboxId`。
可配置台渲染的是**被点开的那段存档**，未必是此刻降落着的那一段。
后果：在 A 房写的关系、A 房的配置台里看得见，但如果你当时正降落着 B 房，
B 房的配置台会显示「写关系」（读不到），**认知锁的显示也同样是错房的**。

修法：`findLink / linkSlot / addLink / setRelation / setBarrier / setCognition /
cognitionOf / relationOf` 全部加一个**可选的 `sandboxId`**，
不传 = 当前房（聊天页 / 切号器 / 掉马都是这个语境），
**配置台显式传 `sb.id`**（5 处调用点）。

**② 「加人设」建出来的大号是**悬空**的 —— 根本没进这间房**

`core.charsOfSandbox()` 读的是 `sandbox.charIds`，而 `upsertChar()`
**不会**把人写进任何房。以前只有 `charIO` 的导入走了 `setSandboxChars`，
手工「加人设」建出来的大号谁也没往 `charIds` 里塞 ——
于是建完回配置台，**关系树上是空的**（等于白建），
而且孤岛的「只住得下一个人」校验被整个绕过。

修法：`renderSimple` 保存后补一步 `setSandboxChars(sb.id, ids.concat([id]))`；

### 已知的皮（写进 app.js 注释了）

`Sleepy.nav.closeTop()` 内部走 `history.back()`，是**异步**的 ——
「同一个 tick 里先 `closeTop()` 再 `open(别的页)`」会被 popstate 追上来，
把刚开的那一页一起弹掉（表现是「脚本点了 A，屏幕上却是 B」）。
程序化切页请用 `closeAll()`，或把两步拆到不同 tick。

### 八之六、状态栏透明化（所有页面）

用户截了朋友圈顶上那条白带：「**这个所有的屏幕的显示都改成透明底**」。

**做法**：状态栏不再占布局，改成**浮在页面之上**——

```css
#statusbar{ position:absolute; top:0; left:0; right:0; z-index:60; }  /* 一字不提 background = 透明 */
```

它一让位，所有页面内容会整体上移 32px，所以由三处把位置补回来，
**三处用的是同一个数 `calc(env(safe-area-inset-top) + 32px)`（下面简称「chrome 高」）**：

| 谁 | 怎么让 |
|---|---|
| `.page-inner` | `padding-top: chrome 高` —— 普通页面的内容从这里开始（视觉跟以前一模一样） |
| `.app-head`（吸顶顶栏） | `position:sticky; top: chrome 高` —— 页面滚动时顶栏停在状态栏下面，不会钻上去叠字 |
| 浮岛 / 朋友圈的绝对定位顶栏 | `top: chrome 高` |

这样一来，状态栏背后看见的正是**当前页面自己的顶**：朋友圈是封面、
浮岛是天空、普通页面是页面底色 —— 「透明」才真的有意义。

**朋友圈**：因为封面要顶到屏幕最上边，那一屏的 `.page-inner` 单独把
`padding-top` 归零；状态栏文字改成白色 + 阴影（压在深色封面上），背景仍然透明。

**🐞 两个坑（都是这轮实机撞出来的）**

1. **`#statusbar` 里原来还有一条 `position:relative`** —— 我在规则开头加了
   `position:absolute`，但同一规则里**后面的声明胜出**，computed 查出来还是 `relative`，
   状态栏照样占位、封面照样顶不上去。排查时先怀疑了浏览器缓存、又怀疑服务，
   最后才去看规则末尾。**教训：改一条老规则，先把它整块读完。**
2. **浮岛被状态栏压住**：`.page[data-page="island"]` 的 `page-inner` 是 `padding:0`，
   它的顶栏又是 `position:absolute;top:0` —— 两处都顶着屏幕最上边，于是
   「浮岛」标题和「21:18」叠在一起（截图里很清楚）。两处都改成让位。

**实测**：`#statusbar` computed = `absolute`、`#stack` 顶 = 0；逐页看过桌面 /
4 Tab（消息 · 通讯录 · 朋友圈）/ 浮岛 / 配置台：朋友圈封面顶到屏幕最上、
状态栏白字；其余页面状态栏深字浮在页面底色上，内容位置与改动前一致。
`check` + `smoke` 双全绿（新增 2 条：状态栏 absolute 且透明、chrome 高在 CSS 里同源出现 ≥4 处）。

### 八之七、IndexedDB 图库 + 设置页收口

用户三条：「浮岛上面还有那个颜色，不是透明的」「把设置里需要做的做了吧~比如 **indexDB**，

**① 浮岛顶上的那截颜色** —— `.isl-sky` 挂在 `.app-body` 里（绝对定位），
而 `.app-body` 从 `page-inner` 的内边距之后开始，所以天空铺不到状态栏那一条，
露出的是页面兜底色。修法：浮岛页的 `page-inner` 不留 padding-top
（标题不会被压 —— `.app-head` 是绝对定位的，自己让了位）。

**② 图库：新增 `media.js`（IndexedDB）**

这是「方便之后存图」的地基。以前所有图都只能塞 localStorage（5MB、字符串），
一张照片 base64 就 3–8MB，存两张爆配额，而且 `setItem` 抛错会**连累别的 key**
（整个数据层一起坏掉，不是「这张图没存上」）。现在：

| 层 | 放什么 |
|---|---|
| `media.js`（新） | blob 本体。`put / get / url / usage / clear / shrink`。`url()` 带 objectURL 缓存（同一张图在相册、照片墙、聊天里显示只建一次） |
| `photos.js` | 只留一条 `mediaId` 引用（**老记录的 `dataURL` 仍然能读** —— 升级不能让人看不见旧照片） |
| 聊天附件 | 发照片时先 `shrink`（长边 1600）再入库，气泡里**真的能看见图**了（以前只存文件名，永远是一张灰卡） |

- `available()` 探活：**真去开一次库**（无痕模式下 API 在但开库会失败）。
  不可用时自动退回 dataURL 老路径 —— 降级，但不崩。
- 删照片会连 IDB 里的 blob 一起删（只删记录 = blob 永远留着占配额、还看不见）。
- 「清除全部数据」也清图库（同理）。
- 设置页 → 数据与备份：新增「图库」一组（占用 / 张数 / 存放位置 / 清空图库）。
  导出说明补了一句「**图片不在备份里**」。

**③ 删掉「聊天默认参数」那一页** —— 温度 / 上限 / 上下文条数 / 流式本来就是
**每个接口自己的生成参数**，接口配置页里各有一份，两处都能改迟早出现
「在这里改了、请求里还是老值」。心声开关没丢（心跳 App 里有它自己的入口）。
`store` 的 `chatDefaults` 保留（`api.js` 拿它做第三层兜底），只是不再有 UI 去改它。
「模型连接」的形态不动：打开就是主 API / 副 API / 后台任务那些行。

**实测**（无头 Edge + CDP，真往 IndexedDB 写了一张 canvas 生成的图）：
`media.available()` = true → `put` 成功（6949 B）→ 聊天气泡 `<img>` 载入（`blob:` 480px）→
相册缩略图与页脚「共 1 张 · 图库 6.8 KB」→ 设置页「图库占用 6.8 KB / 1 张 /
IndexedDB（只在本机）」；设置页已无「聊天默认参数」行；浮岛 `.isl-sky` 的 top = 0。
`check` + `smoke` 双全绿（新增「media: 图库」8 条：接口齐全 / 无 indexedDB 时老实返回 false /
加载顺序 / photos 认 mediaId / 删照片连本体一起删 / 默认参数页已删 / 聊天发照片真的入库）。

  （不给兜底的话气泡里就是个破图 + 一行 alt 文字）。
- `attachText()` / `previewOf()` 都认它 —— 角色在上下文里看到的是
  `[我发了一个表情：小熊打招呼]`，会话列表预览是「你发了个表情「小熊打招呼」」。

**③ 打字推荐（这次的重点）** —— 输入框**上面**一条横着排的推荐条：

- `Sleepy.stickers.match(query, limit)` 纯函数（好单测），按**解释**（`name`）匹配，
  打分从紧到松：完全相同 100 → 解释里含这段 80−差字 → 这段含整个解释 60−差字 →
  输入的每个字都出现过 30（打一半也能命中）。同分新的在前。

  不能让它被裁掉）。点一张直接发出去。
- 发完**不清空输入框** —— 那几个字可能是你本来就要发的话，表情只是顺手发的，
  清掉了他还得重打一遍。

**实测**：表情包页两组默认收起（展开数 0、网格 0）→ 点第二个组头展开（网格 1、格子 5）；

加号 → 表情包 → 面板（组 chips 小熊/猫猫/测试 + 网格）。

### 八之十、表情包收尾 + 角色也能发表情

用户原话：「两个都可以做~宝宝决定就好，但是**外链挂了也是发表情包的那种大图的样子**？
但是上面写的是「**表情包丢失了qwq**」，然后**先做那种发完就清空吧**！」

**① 图挂了也保持大图的样子** —— 破图不能缩成一行小字，要跟正常表情一样是
132×132 的方块，中间写「表情包丢失了qwq」。两种挂法都兜：外链加载失败（`img.onerror`）
和本地图取不到（图库清过）。

**② 发完清空输入框** —— 上一轮我判断「那几个字可能是你本来要说的话」所以**不清**，
用户这次明确要清。逻辑上也对：那几个字本来就是拿去**搜表情**的，表情发出去了它就
完成使命了，留着反而让人以为没发出去。

**③ 表情面板底部加「管理表情包 ›」** —— 从聊天直接去管理页（导入 / 分组 / 删），
不用退出去绕「我 → 表情包」。

**④ 角色也能发表情**（这次的重头）

不能靠模型直接吐图片 URL —— 它不知道也不该知道这些。做法是**约定一个标签**：

- 请求里给模型一段说明书（`Sleepy.stickers.replySpec()`）：列出它手上有哪些表情
  （**只列名字**，名字就是解释），想发的时候**单独占一行**写 `[表情:名字]`。
  没有表情时不加这段 —— 别平白多一段指令让模型照猫画虎瞎编。
- 回复落地前 `extractStickers(text)` 把标签抽出来（全角半角冒号都认、一行多个也认），
  正文里那段去掉。纯函数，冒烟里单测。
- `charSendSticker(name)` 按名字找图：先精确、再退一步「谁包含谁」
  （模型把名字记岔一点点也能中），找不到就当它没发（**不猜**）。
- 两个边界：正文被表情吃光时，把提前落的占位消息**删掉**（否则留一个空气泡）；
  用户**主动停止**时只去掉标签、**不补发**表情（他是不想聊了，别再弹东西出来）。

**实测**：破图方块 + 「表情包丢失了qwq」、发完清空、面板管理入口都过了；
角色发表情这条链路用冒烟单测覆盖（解析三种写法 / 说明书只在有表情时出现 /
「标签 → 名字 → 对得上那张图」）。`check` + `smoke` 双全绿。

> ⚠️ **还没实测到的**：「真模型回复 → 自动变成表情消息」这条端到端，
> 在无头环境里跑不通（要一个真能连上的 API 和完整的角色上下文）。
> 解析和匹配都是单测过的纯逻辑，但**第一次真实使用时留意一下**。


### 八之十一、朋友圈 P0：带图 · 表情评论 · 回复 · 删除 · 记忆挂钩

### 八之十五、反应决策步 · 活人感（2026-09-17 晚）

**用户拿一份「角色对朋友圈反应的原则」来核对**：每条动态算一个「主动关注机会」，
行为由人设、关系状态、心绪、重要度共同决定，禁止全员「检测到负面情绪 → 关怀模板」。
核对结论：延迟 / 认知锁 / 记忆挂钩这些骨架符合，但「主动关注机会」的评估层没有 ——
旧实现是被挑中的角色**必须回一句**。按用户确认的方案（全做 + skip 留痕）补齐。

- **决策步**（moments-ai.js）：`decide()` 一次调用同时给出「做什么」和「说什么」，
  `extractDecision()` 解析五种标签（宽容原则同 extractPost：没标签但说了话当评论）
- **硬护栏**：`recentActivity()` 数近 1 小时互动，≥2 强制 skip；点名（回复 / @）`must` 必接
- **skip 留痕**：用户选「留」—— 轻记忆「刷到了没说话」
- **私聊提起**：`postPrivate()` 把话插进对应会话末尾（不做推送，真后台是另一批）
- **延后**：`[later: N]` 重排同款任务，N 分钟后再走一次决策
- **修复**：`[later: 30]` 的 30 被当**秒**用了（30 分钟变 30 秒，实测队列里「0 分钟后」）——
