## 1. 入口与路由表

### 1.1 结论先说

**当前没有任何「临时双人测试入口」。** 生图页「试一张」实验区的主体是一个**单选下拉**，选项只有两类：

| 主体下拉实测选项（本机 headless 读取 DOM） | 说明 |
| --- | --- |
| `无人场景／物品（走 01 底座）` | `subjects: []`，走 `buildSceneObjectExperimentPrompt` |
| `单人（临时测试，不读取角色资料）` | `tempSingle:true`，不读任何身份 |

（`page-imggen.js:474-476` `subjPick` + `:440-444` `subjOptions`；本轮浏览器取证第 3 步已把两个 option 的 `textContent` 原样打出来。）

生图页全文关键词扫描「双人 / 两人 / 合影 / 两个人 / 关系图 / 第二个人 / 多人」→ **零命中**（浏览器取证第 2 步）。

「试一张」按钮的事件处理（`:548-644`）在三种分支里**都只造一个主体**：

```js
// page-imggen.js:616-639
} else {
  var one = subjectForRef(ref, shot);            // ← 单个主体，ref 只能是 char:xxx / user:xxx / TEMP_SINGLE_REF
  if (!one) { /* 拦下来让人重选，不静默换人 */ }
  built = imggen.buildSingleSubjectExperimentPrompt({
    api: collect(), description: subject, shot: shot,
    subjects: [one],                              // ← 硬编码一个
    visualMode: expMode, customVisualStyle: imggen.visualExpCustom(),

}
req = (built && imggen.generateBuilt({ ... })) || Promise.resolve({ ok:false, error:{message:'这个模式不能画这张'} });
```

而实验拼接器本身就拒绝多人：

```js
// imggen.js:745-757（buildSingleSubjectExperimentPrompt 守卫）
function buildSingleSubjectExperimentPrompt(opts) {
  var mode = ...; if (mode === 'legacy') return null;
  ...
  var subjects = Array.isArray(opts.subjects) ? opts.subjects : [];
  if (subjects.length !== 1) return null;      // ← 双人直接 null，调用方走「不能画这张」
```

浏览器取证第 6 步实测：`buildSingleSubjectExperimentPrompt({visualMode:'sleepy-default', subjects:[char,user]})` → **`null`**（两种模式都 null）。即：**在 UI 实验区里，试图双人＝根本发不出请求**，页面会显示「这个模式不能画这张」。

### 1.2 唯一能触发双人的真实链路（都依赖 AI 输出）

| 链路 | 触发条件 | 主体来源 | 最终调用 | 走哪个拼接器 |
| --- | --- | --- | --- | --- |
| 聊天 · TA 主动发图 | 角色回复里出现 `[生图:...]`，内容是 JSON 且 `subjects` 同时含 `char` 与 `user` | `page-chat.js:3530-3531` `subjectForChar(ch)` / `subjectForUser(subUser)` | `page-chat.js:3457` `generate({plan})` | `buildPromptForPlan`（**legacy 预设基底**） |
| 聊天 · 导演出图 | `planFromDirector` 解析模型输出（`page-chat.js:3428-3446`，push 在 `:3436-3437`） | 同上 | `genAndDeliver` → `:3457` | 同上 |
| 朋友圈 AI 配图 | `moments-ai.js:237-238` push | `subjectForChar(ch)` / `subjectForUser(bigUser)` | `:253` `generate({plan:...})` | 同上 |

| 生图页「试一张」 | 无（只有单主体 / 无人） | — | — | 实验拼接器（拒绝双人） |

**关键点：双人只可能由「模型自己写的 `[生图:]` JSON」触发**，没有任何用户可控开关。拼装出口是
`imggen.js:877-912 buildPromptForPlan`，**不是**实验拼接器，也绕过 `SLEEPY_VISUAL_STYLE` / `SLEEPY_SINGLE_STYLE` / 视觉模式 / 手部附加段。

说明书确实允许两个都写（`imggen.js:1237-1247 replySpec`，第 1241-1242 行）：

```
- 方括号里推荐写一个 JSON：{"description":"…","contentType":"…","shot":"auto|selfie|portrait|full|candid|group|scene","subjects":["user","char"]}
- subjects 只写画面里真实出现的人：你出镜写 "char"，镜头对准对方写 "user"，合影两个都写
```

**注意措辞是「推荐」「合影两个都写」——是给模型的软建议，不是 UI 功能，图上没有对应按钮，也没有选项可勾选。**

### 1.3 各类「双人」的支持实测（设计意图 ≠ 已实现，逐条标注）

| 组合 | 是否支持 | 怎么选主体 | 证据 |
| --- | --- | --- | --- |
| `user + char`（我 + 角色） | **仅代码层支持，需模型输出两个 key** | 无 UI：`subjects:["user","char"]` → `parsePlanJson` 两种都收 → `subs` 两项 | `imggen.js:226-228`、各处 push |
| `char + char`（角色 + 角色） | **不支持** | 三处链路都只有一个局部变量 `ch`（当前会话角色），`if (k==='char' && ch)` 重复 push 只会 push 同一个 `ch` 两次 → 两个 subject **指向同一角色** | `page-chat.js:3530`、`moments-ai.js:237`、`page-diary.js:328` |
| 临时双人（不建岛不建角色） | **无入口** | 实验区只有「临时单人」哨兵，没有双人哨兵 | `page-imggen.js:440` |

`parsePlanJson` 的 subjects 过滤（`:226-228`）只认字符串 `'user'` / `'char'`——**不能写 `char:<id>`**，所以第二个角色即使写出也没法被识别。

### 1.4 双人「怎么判定」——实际没有任何双人专用判定

`buildPromptForPlan`（`imggen.js:877-912`）里与人数有关的只有一行：

```js
var hasPeople = plan.subjects.length > 0;              // :879
var scene = !hasPeople && (plan.contentType === 'scene' || plan.contentType === 'object');  // :880
```

- **没有 `contentType === 'duo'` / `'group'` 之类的双人档位**；`PLAN_CONTENT_TYPES`（`:141`）只有 `scene / object / person / mixed`。
- `shot` 在 `buildPromptForPlan` 里**只用于选锁脸补充组**（`faceTextFor(ch, shot)`：非 selfie/portrait 即走 `faceLockFull`），**不产生任何镜头词**（镜头层 `SLEEPY_SINGLE_STYLE[].frame` 只被实验拼接器消费，见 `:796`）。
  → **确实存在「写了 group 却走无镜头层」**：双人图上 `shot:"group"` 除了替主体挑全身组锁脸词之外，没有任何构图表达；画面描述里的构图只能靠 description 自己写。
- UI 实验区的镜头下拉也**选不了 `group`**：`SINGLE_EXP_SHOTS = ['auto','selfie','portrait','full','candid']`（`imggen.js:464`），而 `PLAN_SHOTS` 含 `group`（`:142`）——两边枚举不一致。

### 1.5 最终 provider 与负面发送方式

## 2. 身份与动作是否各自绑定（沿真实链路追踪）

追踪对象：**`user + char`**（唯一可能的双人组合），从 `subjectForChar/subjectForUser` 到最终 prompt。

### 2.1 两人的 id / 身份类型 / 外貌 / 年龄从哪来

| 项 | 来源 | 实测 |
| --- | --- | --- |
| 身份类型 | `subject.entityType`，只认 `'user'` / `'char'`（其余返回 null） | `imggen.js:759-761` |
| entityId | `entityId` 只**原样透传、进 debug 与落盘**，拼接时不使用 | `:762-768`、`:819` |
| 外貌 / 锁脸 | `faceText` = `faceLockText` + `faceLockSelfie|faceLockFull`（shot 决定补哪一组），`faceTextFor`：`imggen.js:124-131` | 单人/均分：两人各一段，互不读对方 |
| 名字绑定 | `subjectTextForPlan`（`:172-185`），**多主体才带名字前缀**：`(subs.length>1 && s.name) ? name + ' (' + seg + ')' : seg` | 实测输出 `林砚 (1girl, black short bob hair…), 我 (1girl)` |
| user 马甲取当前有效身份 | `core.defaultUserOfSandbox(sb)`（朋友圈 / 生成方），或 `core.activeUserOnIsland()`（日记兜底）；聊天链路用 `c.userId → KC.findUser` 再回落 `activeUser()`，**没有 defaultUserOfSandbox 那条兜底** | `moments-ai.js:229-231`、`page-diary.js:326-329`、`page-chat.js:3432-3433` |
| 年龄 | **没有任何身份字段承载**，只能写进 description | 见 §4 C 组 |

`subjectForUser`（`imggen.js:203-212`）的 `name` 有兜底 `'我'`，所以「我」这一方**永远有名字、不会被空壳 filter 丢掉**；但 `faceText` 可以为空（马甲没填外貌）→ 实测出现 `我 (1girl)` 这种**只有性别、没有外貌**的身份段。

### 2.2 两人描述是否分块、有没有编号/称呼绑定

- **没有编号、没有称呼绑定机制**。绑定全靠名字前缀（`林砚 (…), 我 (…)`），而名字是中文中文标签进 tag 管线。**中文名进英文 tag 模型是否稳定识别，未知**——本轮不判定。
- 不合并：`subjectTextForPlan` 整段进 `coreParts`，注释明写「身份段永不合并去重」（`:168-171`、`:890`）。
- 不去重：整句级 `pushDedup`（`:893-898`）按**整串**判重。实测同一句 `shared light, shared light` **两份都留下**（只去掉整句复制的那份，不会合并成一句）。
- 不截断、不覆盖：`buildPromptForPlan` 无长度上限、无 `slice`；description 原样进。
- 位置/视线/动作/持物/接触：**没有任何专用结构**，全部由自然语言 description 承担。实测 B 组（递物）动作文本原样落进 prompt，人物归属由 description 的「one / the other」自行承担——**拼装器不校验归属，也不校验左右手**。

### 2.3 本岛隔离 / 失效主体 / 重复主体 / 缺外貌资料

| 场景 | 实际行为 | 位置 |
| --- | --- | --- |
| 主体失效（char 移出本岛 / 被删） | **静默减成单人**：`#if (k==='char' && ch)` 直接跳过，不报错、不提示 | `page-chat.js:3530`、`moments-ai.js:237`、`page-diary.js:328` |
| 同上，但走的是实验区 UI | **显式拦截**：`subjectForRef` 返回 null → 页面提示「这个主体已经不在本岛或已被删除」，请求不发 | `page-imggen.js:461-472`、`:616-627` |
| 重复主体（写出两个 `"char"`） | `parsePlanJson` 不去重（`:226-228` 只过滤白名单），`subjects:["char","char"]` → push 两次**同一个角色** → 代码层出现「两个人其实是同一张脸」，**无守卫** | `imggen.js:226` |
| 空壳主体（无 name / gender / faceText） | `normalizePlan` 的 filter 丢掉（`:161-164`）。实测：name 为空的 char 被丢，name='我' 的 user 保留 | 纯函数取证 §5 |
| 缺外貌资料 | 只有性别 tag（实测 `我 (1girl)`）；两张图的辨识度只能靠 description 区分。**这不是视觉锁脸**，只是把文字塞进 prompt | §2.1 |
| 用户不在本岛（生成方拿不到马甲） | `subs` 少一个 → **静默减成单人**，而 description 仍写「Two adults…」→ 见 §5 问题 P2 | 反例 E1 |

⚠️ 明确口径：**身份引用正确 ≠ 已实现视觉锁脸**；本轮也**不把任何禁止串脸的词称为检测器**——全链路没有任何图像侧反馈，出图好坏只能人眼看。

### 3.2 逐项核对（按工单的「不机械按关键词判错」要求）

- **误带 `solo / exactly one person / single subject`？→ 双人路径上没有。**
  那串只在 `SLEEPY_SINGLE_STYLE.general.structure`（`:513`）里，只被 `buildSingleSubjectExperimentPrompt`（`:793`）消费；`buildPromptForPlan` 不引用它。
  实测 A 组 positive 全文**不含** `solo` / `exactly one person` / `single subject` / `1boy`（两人都是 female 时也不含单人性别标签以外的东西，性别 tag 是 1girl/1girl 各一份，属于身份段而非单人负面）。
- **误套临时男性 v2 / 女性 C？→ 没有。** 这两个底座只在 `tempMaleLookOn` / `tempFemaleLookOn` 命中时替换 `look[shot]`（`:798-800`），而 `buildPromptForPlan` 根本不调它们。双人图目前用的**旧视觉词 = `BUILTIN_PRESET.general.positive` 自带那套质量词**（`masterpiece, best quality, ultra detailed, beautiful detailed eyes, delicate face, detailed skin, soft lighting`），**没有任何 E2 定稿底座参与**——所以不可能是「男女两套单人词拼一起」，也**没有把 C 版拼进双人**。
- **写死男女组合 / 恋爱关系 / 搂抱接吻？→ 没有。** 全链路常量里不含 `couple /拥抱/kiss / 1boy`。实测 C 组（母女）positive 里**没有**任何情侣措辞，年龄与亲属关系完全来自 description（`A 30-year-old daughter and her 60-year-old mother…`）。
- **custom 是否只换审美、保留人数与身份？→ 双人路径上 custom 完全不生效。**
  实测（纯函数取证 §2）：`visualMode` 传 `'sleepy-default'` 与传 `'custom'`（以及把自定义词塞进 `extras`）三种情况下，A 组 positive **逐字相等**。
  `visualExpCustom()` 只被 `singleSubjectVisualStyleText`（`:646-649`）读，而那条只在实验单人路径上被调用。**空 custom 的真实行为**：`page-imggen.js:520` 只是把输入框藏起来，不填→`visualExpCustom()` 返回 `''`→视觉层为空串，不影响其它层；双人路径下它**连读取都不会发生**。
  ⚠️ 反过来说：**E2 刚定稿的「custom / default 对齐」对双人图没有任何作用**，两侧是两套独立代码。
- **双人实际手部词 / negative 来源，是否与单人实验不同？→ 是，且不是「推广关闭」。**
  双人 negative = 老 legacy 的 `BUILTIN_PRESET.general.negative`（带 `extra fingers / bad hands / extra limbs`）；单人实验 negative = `SLEEPY_VISUAL_STYLE.qualityNegative + negativeStructural (+ 仅 default 的 negativeAesthetic)`。
  即：**防多余肢体那一串只在双人路径存活**（实验单路径已通过 `visibleHandsText` 恒空关掉，legacy 未动）。按本轮基线，我不推广、不改动，仅如实记录两套来源并存。
- **provider 最终怎么发负面**：见 §1.5，General 走独立 `negative_prompt` 字段（已实测）。

**negative（实测原文，节选尾部）：**
`… blurry, bad anatomy, bad hands, bad proportions, deformed, mutated, disfigured, extra fingers, fewer digits, missing fingers, fused fingers, too many fingers, extra limbs, malformed limbs, ugly, old, aged up, elderly, wrinkle, long face, cross-eyed, watermark, signature, username, text, logo, cropped`

**对照结论：** `default` / `custom` / `custom视觉词塞 extras` 三种输入 → positive **逐字相等**（脚本直接断言 `=== true`）；three 份 negative 也逐字相等。
**custom 视觉词对双人图零影响 —— 已取证，不是推测。**

### B 递物（走现有默认路线）

description：`One person holds the lower half of a glass bottle with their right hand, the other receives the upper half with their left hand, both facing each other and looking into each other's eyes, the other arms hang naturally at their sides or stay hidden behind their bodies`

positive 实测尾部：`… , 我 (1girl), One person holds the lower half of a glass bottle with their right hand, the other receives the upper half with their left hand, both facing each other and looking into each other's eyes, the other arms hang naturally at their sides or stay hidden behind their bodies, masterpiece, best quality, ultra detailed, …`

- **动作文本保留 ✓**（整句原样进 prompt，未经任何解析器改写）。
- **人物归属：拼装器不做归属绑定**，归属靠 description 里 `One person / the other` 自行表达；拼装器不校验左右手、不校验「一瓶被两只手分持」是否自洽。→ **只验证「文本及归属描述被保留」，不判断图像解剖是否正确**（本轮不贴图、不出图）。
- 手部词：positive 里**没有任何系统手部附加词**（`visibleHandsText` 恒空且不在 plan 路径）；negative 里的手部负面来自 legacy 表（`bad hands / extra fingers / extra limbs`…），**与单人实验的来源是两套**。
- 浏览器拦截实测（第 5 步）拿到的真实请求体：`model:'duo-fixture-model'`、`size:'1024x1024'`、`prompt` 与上述一致、`negative_prompt` 独立字段非空。

- **年龄 / 亲属关系保留 ✓**（`30-year-old daughter` / `60-year-old mother` 原样落到 description 里）。
- **没有额外情侣措辞 ✓**（全文无 couple / kiss / hug / boyfriend / girlfriend / lovers）。

### 5.2 问题分类

**P1 · 试图前必须解决的工程问题**

1. **入口不可达**：UI 无任何双人开关；实验区单选 + `subjects.length !== 1 → null`（`imggen.js:757`），双人连请求都发不出去。
2. **双人只能靠模型自觉**：触发双人的唯一途径是模型在 `[生图:]` 里写出 `subjects:["user","char"]`（`imggen.js:1241-1242` 只是「推荐」措辞），没有可勾选选项、没有可复制的 UI 路径。
3. **`char + char` 不支持**，且写两个 `"char"` 会 push 同一个角色两次、无守卫（`imggen.js:226`、`page-chat.js:3530`）。
4. **shot 枚举不一致 + group 无构图表达**：实验下拉无 `group`（`imggen.js:464`），plan 路径又根本不产出镜头层（§1.4）→「写了 group 仍是无镜头图」。
5. **失效主体静默减员**（E1/E2/E3/E4 全部照发），与实验区「拦下重选」的既有哲学不一致。
6. **custom / 视觉模式 / 手部下拉在双人路径上完全不生效**（§3.2），E2 定稿成果对双人图零覆盖；用户若照「E2 那套参数」去试双人，会得到与参数无关的图。
7. （沿用既有记账）D1 角色下拉刷新缺陷仍会让「主体怎么选」这件事不可靠。

**P2 · 已有明确文字冲突的提示词问题（附原文与位置）**

1. **负面里的年龄词 vs 老年主体**：`imggen.js:67-72` `BUILTIN_PRESET.general.negative` 含 `old, aged up, elderly, wrinkle, long face`，而它是双人图的**唯一负面来源**（`imggen.js:909`）。C 组「60 岁母亲 + 女儿」会被这套负面反向压。
2. **负面里的人手词 vs B 组递物**：同一份 negative 含 `bad hands, extra fingers, extra limbs`，而 B 组的整张图就是「两只手分持一瓶」——**为防单人崩手而写的负面，正好压在双人的手部动作上**。这两处不在实验路径（那边已关），但在 plan 路径上**照旧生效**。
3. **失效时描述自相矛盾**：E1/E2 下身份段只有一个人、description 仍写 `Two adults…`（`imggen.js:890-899` 顺序决定），模型会收到互相打架的约束。
4. **`subjects: []` + `contentType:'scene'` 的负面含 `1girl, 1boy, person, face, close-up`**（`imggen.js:92-94`），若 description 有内容则自相矛盾。

**P3 · 必须真实出图才能判断的效果类（本轮不判）**

1. 中文名字前缀（`林砚 (…), 我 (…)`）作为人物绑定标签，模型是否稳定识别 → 只能看图。
2. 两人同框的身份区分度 / 是否串脸 → 只能看图（本轮无视觉锁脸、无检测器）。
3. 递物动作（左右手、瓶身上下半）的解剖正确性 → 只能看图。
4. `negative_prompt` 那个中转站是否真支持 → 未知，需真实出图或接口文档确认。

## 7. 结论（给「宝宝」可以直接抄走的这一段）

### 当前是否已具备真实双人试图条件？

**不具备「可直接照做」的双人入口。** 阻塞位置三个，任一都在 UI 之前：

1. `page-imggen.js:440-444 / 616-639` —— 「试一张」主体是**单选**，双人选项不存在；
2. `imggen.js:757` —— 实验拼接器 `subjects.length !== 1 → null`，双人请求发不出去；
3. 唯一能触发双人的真实链路是模型自己写 `[生图:{"subjects":["user","char"]}]`（`imggen.js:1241-1242` 只是建议），**没有可点、可勾选、可复制的 UI 路径**，也没有临时双人夹具。

所以：**我不会让你去试一个尚不存在的入口。**

### 现在能做的（不装作是双人验收）

- **能试的**：生图页的**单人**路径（临时单人 / 已有的角色马甲 + 视觉模式 sleepy-default / custom），本轮复跑 E1/E2 检查仍是 76 ✓。
- **已经查清但不能从 UI 点出来的**：`generate({plan})` 的运行时路径**确实支持两个 subject**（§4 A/B/C 三组 positive/negative、provider、镜头、视觉模式、拦截证据都在上面），这是**可复用的现成能力**，M1 只要把它挪到 UI 上就能用——但那属于施工，本轮不做。
- **本轮实测可达的地址**：本机 `http://127.0.0.1:5173/`（`pnpm dev`）；拦截取证用的是临时端口 `127.0.0.1:5207`。**没有起 LAN 临时网址，旧 IP 不沿用。**

### 最小待施工项（按顺序）

1. **M1**（必做，唯一 blockers）：加「临时双人」两个主体下拉 + 一个 `buildTwoSubjectExperimentPrompt`，配套 `shot` 补 `group`。做完 A/B/C 三张就能真出图。
2. 出图后按 P3 逐条看图判效果（中文名绑定、串脸、递物解剖、`negative_prompt` 支持度）——这些本轮一律不给结论。
3. M3（双人负面常量）等真人看过图、确认 `elderly / wrinkle / bad hands` 这几条是否真在压图之后再定词；本轮不写候选、不拼男女两套单人词。
4. M2 / M4 可后置，不阻塞。

**一句话：先补 M1 这个工程口子，别拿现在的聊天链路去赌模型会不会帮你写两个 subjects。**
