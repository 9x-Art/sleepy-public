## 一、本批做了什么（一句话版）

总结卡要求模型产出 `relation` / `review` / `uncertain` 三个字段，
`page-summary.js summaryEngine.ingest` 的字段白名单此前只接
changes / charState / openLoops / attention 四样——**三字段产出即丢弃**（模型白付 token）。
本批接上，处置方案经用户拍板：

| 字段 | 处置 | 落点 |
|---|---|---|
| `relation.confirmedChange` | 入库 + **user 确认闸** | relationship_fact **恒 pending**（模型自称 user_explicit 也不放行）；复用现有留痕确认 UI；条目带 `via: 'relation.confirmedChange'` |
| `relation.intent`（+currentReading/evidence/sourceIds） | 入库，程序消费 | `relationIntent:<rootId>` 整块替换（同 charState 模式）；**本批只落库，主动消息接线另批** |
| `review` / `uncertain` | 只做诊断 | `reviewLog:` / `uncertainLog:<rootId>`，capped 留最近 10 次；不进 prompt、不进主动消息、无 UI |

**结构性修复**：ingest 不再因 `changes` 为空 early-return（零记忆变更也可能有意向/评估）；
relation 缺失或空 intent **不覆盖旧状态**（卡：缺失字段用空结构）。

## 三、关键实现事实（后续会话必读）

1. **pace 严格整数**：`paceOf()`（page-summary.js 模块级）——只收 1~5 整数
   （number 整数或纯整数字符串 `"2"`）；`3.7`/`"3.7"`/越界/非数一律 null **不夹值**。
   gate（intentHasContent）与存储值共用同一函数。此前 parseInt 会把 3.7 截成 3，已修。
2. **拒绝出口语义**（易踩）：`deleteMemoryItem` **只许 `source==='user_manual'` 物理删除**
   （page-memory.js:316）。ai_summary 来源的「拒绝」= 留痕 UI「标记错误」→
   `invalidateMemoryItem`（status=invalid，原始数据保留）。测试按真实出口断言。
3. **重复 ingest 现状（未变）**：confirmedChange **无内容级去重**（与 changes 通道同纪律），
   重复申报 = 重复建 pending。去重责任在模型（replaces 引用旧 id）+ user（留痕侧处理）。
   smoke 已用测试把现状钉死（「重复申报重复建 pending」），**未新增去重逻辑**。
4. **确认前不进已成立事实**：`getMemoryInjection`（page-memory.js）只滤
   `status==='active'` —— pending 结构上进不了聊天 prompt，无需本批加闸。
5. **作用域**：三新键 = `<键>:<rootId>`，与 charState 家族完全同族（S6 键归 root）。
   char 按岛打 sandboxId 章 + rootId 全局唯一 ⇒ 切岛不互写；无 user 马甲维度
   （同族既有拍板，非本批缺口）。
6. **存储写入纪律**：store.get 深拷贝 ⇒ ingest 内 confirmedChange 段重新
   `loadCharMemory` 再 save，不复用 changes 段的 file 引用。
