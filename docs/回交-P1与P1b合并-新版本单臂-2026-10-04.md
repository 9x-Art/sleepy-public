## 六、★ 具体样本里发现的问题（不据此宣布效果通过/失败）

### P1-1　`reasoning_content` 只在 1/7 轮存在 → 截断是**波动项**

| 轮 | 耗时 | completion | 推理字段 |
|---|---|---|---|
| P1-G4-1 | 6.4s | 183 | 未提供 |
| P1-G4-2 | 120.0s | — | —（无响应） |
| P1-G4-3 | 7.7s | 173 | 未提供 |
| **P1-G7-1** | **80.1s** | **564** | **提供 958 字** |
| P1b-G4-1 | 8.2s | 195 | 未提供 |
| P1b-G4-2 | 8.7s | 180 | 未提供 |
| P1b-G4-3 | 11.7s | 239 | 未提供 |

**结论**：同一模型同一线路，**推理形态不恒定**。
历史那个「3/10 预算截断」很可能是**偶发的长推理轮**（80s 那一类）撞上额度。
⇒ **截断率是波动项，7 轮估不出来**（本批 0 次截断，最多用到 564，离 8192 很远）。
⇒ 也再次证明「字段缺失必须记 `null`／`false`」——填 0 会被读成「推理了 0 字」。

### P1-2　延迟抖动，且与成败不成正比

```
6.4s ✓  7.7s ✓  8.2s ✓  8.7s ✓  11.7s ✓  80.1s ✓  120.0s ✗(超时)
```

**80s 成功了、120s 挂了。** 延迟与成败**不成正比**，像服务端随机拥塞。
⚠️ 这直接影响下一个待决项：timeout 降到 90s 会**砍掉 80s 那个成功轮**的余量
（G7 只差 10s）。**建议暂不降 timeout**，或降到 **100s**（给 80s 留 20s 余量）。

### P1-3　G4-2 超时后仍发了轮 3 —— 与你的停止规则有偏差

你的规则：「某轮失败就停止其依赖后续轮」。**实跑轮 3 照常发出**（P1 那批多花 1 次请求）。

**根因**：停机判断在**轮次结束后**执行，而轮 3 紧随轮 2 之后已开始。
**客户端无法预知会不会超时**（除非降 timeout，但那会砍掉 80s 成功轮）。
⚠️ 这是**实现与规则的已知偏差**，如实登记。
