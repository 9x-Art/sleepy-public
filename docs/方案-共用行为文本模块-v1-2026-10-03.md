## 3. 共享 shell 的兼容策略（裁决 9）

### 3.1 消费者清单

`[源码证据]` `cardBody('shell')` 全库 **4 处**：

| # | 消费者 | 锚点 | 出站形态 |
|---|---|---|---|
| 1 | 私聊线上 | `prompt-engine.js:1127` | 多条 system |
| 2 | 私聊线下 | `prompt-engine.js:1402` | 多条 system |
| 3 | 主动消息 | `page-proactive.js:200` | 1 条 system（`\n\n` 拼） |
| 4 | 群线下 | `page-group-offline.js:196` | 1 条 system（`\n\n` 拼） |

**群线上不在消费者内**（`page-group-ai.js` 无 `cardBody('shell')`）。

### 3.2 overrides 语义与风险

- `cardBody(id)`：`overrides[id] != null` → 返回 override，否则返回 `CARD_DEFAULTS[id].body`（`:635-639`）。
- `shell` 是 `locked: true`（`:80`），`resetCard`（`:647`）/`isOverridden`（`:653`）语义不变。
- **[源码证据] 风险**：直接改 `CARD_DEFAULTS.shell.body` 会**同时**改动 4 个消费者 ——
  违反裁决 9（"不能先改共享默认值牵连其他场景"）；且群线上**不在这 4 个之内**，
  改默认值反而会造出"四个场景换了、群线上还是老样子"的新不一致。

### 3.3 兼容策略

**O1 · 并行新增（推荐，采纳）**
- 新模块只**新增** `Sleepy.behaviorText`，**完全不碰** `CARD_DEFAULTS` / `cfg().overrides` / `cfg().disabled`。
- 每个场景**各自**在其装配函数里显式决定"用新模块还是旧 shell"，**逐场景切换、逐场景验收**。
- 旧 `shell` 卡**字节不变**，直到 4 个消费者全部迁移完成才考虑下线（下线另案，需单独授权）。

**O2 · 就地改默认值 —— 不采纳**。理由见 §3.2。

**O3 · 新建卡 id `shell2` —— 仅作 O1 的可选补充**。
若某场景正式切换时希望继续尊重用户的 `overrides.shell`，可在该场景内做**一次性继承**：
把 `overrides.shell` 的文本接在该场景的 B 之后（保真但可能重复），并在 UI 提示用户"你改过的共享外壳在本场景已被 B/P/L 取代，可一键回退"。

**overrides 迁移期规则（明确）**
1. 迁移前先检测 `isOverridden('shell')`：为真 → 该场景**暂不迁移**（或走 O3 继承），不静默丢弃用户改动。
2. 用户自定义卡（`cfg().custom`）**不受影响**：`K/S` 槽位语义不变（`assembleOnline:1145-1154`、`assembleOffline:1430-1441`）。
3. `resetCard('shell')` 的行为在迁移完成前**保持不变**；迁移完成后它只影响尚未迁移的场景。
4. 群线上补 B **不得**复用"改 shell 默认值"这条路（它本就不是 shell 消费者）→ 必须在新模块里为群线上单独取 B，这也正好避免牵连其他场景。
