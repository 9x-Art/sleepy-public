## 1. P0-1｜AI 回复里的 `[手机]` 痕迹从不落库

### 现象 / 根因（复盘）

- 现象：角色回复里带 `[手机]` 痕迹时，查手机里一条都不多，且**全程不报错**。
- 根因：`page-chat.js` 的回复后处理里写了 `chat.characterId`，但 `chat-detail`
  页面的 render 作用域里**只有 `chatId`**（`page-chat.js:1135`）；`var chat` 只在
  **另一个函数** `createChat` 里声明（`page-chat.js:383`）。'use strict' 下抛
  `ReferenceError`，被同段代码外层的 `catch (e) { /* 手机痕迹失败不影响这条回复 */ }`
  吞掉 —— 整条链路等于没接。

### 改动

| 文件:行 | 改动 |
|---|---|
| `page-chat.js:551`（新增函数） | `applyPhoneTrace(chatId, text)`：把原内联逻辑收成一个函数；归属改为**从 chatId 现查** —— `getChat(chatId).characterId` → `SC.rootIdOf(charId) \|\| charId` |
| `page-chat.js:2536-2543` | runReply 里只剩三行调用：`finalText = trace.text` / `pdApplied = trace.applied` / `granted = trace.granted`（原 33 行内联逻辑删除） |
| `page-chat.js:3848-3854` | `Sleepy.chatApp.applyPhoneTrace` 导出，供冒烟走**同一个函数** |

函数返回 `{ text, applied, granted }`，与原内联逻辑行为一致（抽干净的正文、落库条数、
授权类 delta 的负载）。返回值里不含新数据结构，`phones` / `phonePerms` 等表**一字未改**。

> ⚠️ 写这个函数时的注意事项（已写进代码注释）：`applyPhoneTrace` 内部**不能**引用
> 调用方作用域里的名字。原 bug 就是这么来的。

### 为什么把它抽成函数（唯一的结构性动作）

原逻辑困在 `chat-detail` 的 render 闭包里，外部无法调用 —— 不抽出来就**没有任何办法**
写「真实调用路径」的回归测试（无头 DOM 桩不投递点击事件）。这里只把同一条逻辑收成一个
具名函数，不改行为、不改数据结构。
**如果你不要这个抽取**：可以内联回去，但代价是回归测试只能测到手机管线，测不到这行本身。

## 2. P0-2｜朋友圈待回复队列在换岛时被整批抹掉

### 现象 / 根因（复盘）

- 现象：切岛 / 换存档后，**别的岛**里「已排期但还没发」的朋友圈回复被整批删除。
- 根因：`pendingAll()` 返回的是**按当前岛过滤过**的列表，而 `savePending()` 把它
  整表写回同一个键 → 其它岛的记录没了。这正是 `core.js:48-58` 纪律注释点名的
  「最惨的一类」：写回一个 scoped 过滤结果 = 别的存档数据被整批抹掉。
  实际有三处这么写：`schedule`（每次排期）、`tick`（每 12 秒一次，**主要肇事者**）、`flush`。

### 改动

| 文件:行 | 改动 |
|---|---|
| `moments-ai.js:251-255` | 新增 `allPending()`（全量，**写**路径用）；`pendingAll()` 保留为 scoped（**读**路径用，行为不变） |
| `moments-ai.js:260`（schedule） | 写路径改 `allPending()` |
| `moments-ai.js:749`（tick） | `savePending(allPending().filter(...))` —— 只从全量里摘掉这一条 |
| `moments-ai.js:755-766`（flush） | 只把**本岛**条目拉到现在（按原实现意图），写回全量 |

读的口径没变（tick 仍然只挑本岛到期的条目去跑），改的只是「写回时不许丢掉别的岛」。

### 顺带闭合的同一类隐患（验收要求，2026-09-23 追加）

| 文件:行 | 改动 |
|---|---|
| `moments-ai.js:775`（改） | `clearPending()` 从 `savePending([])` 改成**只清当前 sandbox** 的条目，返回清掉的条数；没盖章的老条目（迁移前）按纪律不碰 |
| `moments-ai.js:787`（新增） | `clearAllPending()` = 真·全局清空，名字写明「全部」，并导出（`:810`） |

原来 `clearPending()` 会把**所有岛**的待回复一起清掉 —— 与 P0-2 同一类坑。
没有生产调用方（只有导出的 API 与冒烟在用），所以改成「只清本岛」是安全的默认。

## 3. 新增的回归测试

位置：`scripts/smoke.js:6057-6240`（「P0 回归」段，共 **184 行**），
排在「全页渲染冒烟」**之前**（那一节必须最后跑）。

### ① `P0-2 待回复队列跨岛不互相抹掉（schedule + tick 都按全量写回）`

真实链路：真建两座岛 → 各 `schedule` 一条 → 断言岛 A 没被岛 B 抹掉 →
在岛 B 先 `flush`（只当造数据的步骤，把本岛那条拉到「现在到期」）再 `tick`
→ 断言岛 B 被摘、岛 A 仍在。带 `try/finally` 清场，断言失败也不污染后面的渲染冒烟。

### ② `P0-1 回复里的 [手机] 痕迹落进查手机（真实数据链路）`

真实链路：真建 岛 / 角色 / 对话 / 手机壳 → 调 `S.chatApp.applyPhoneTrace(chat.id, 带[手机]的回复)`
→ 断言 note 真的落进 `phones`、正文里的 `[手机]` 标签被剥离、`applied === 1`。

### ③ `P0-1 护栏`（静态，`ok()`）

`page-chat.js` 必须含 `applyPhoneTrace(chatId, finalText)`，且**不含** `rootIdOf(chat.characterId)`。
防的是复发点：有人把这段逻辑抄回 runReply，又踩同一个「作用域里没有 chat」的坑。

### ④ `flush 只处理当前岛：别的岛条目一条不动、内容逐字段不变`（验收要求单列）

真建两座岛各排一条 → 记下岛 A 那条的**整条记录 JSON** → 在岛 B `flush`
→ 断言：返回 1（只动本岛）、岛 A 那条**仍在且逐字段未变**、岛 B 那条 `dueAt` 已被拉到「现在」。
最后一条是为了让测试不自证空洞（证明 flush 真的干活了）。

### ⑤ `clearPending 只清本岛；clearAllPending 才清全部`（验收要求）

真建两座岛各排一条 → 在岛 B `clearPending()` → 断言只清掉 1 条、岛 A 那条**还在**
→ 再 `clearAllPending()` → 断言库里清零。

### 反向验证（重要）

把修复**临时改回旧写法**各跑一次冒烟，断言分别变红，报错信息精确：

```
✗ P0-2 待回复队列跨岛不互相抹掉 …  —— 岛 A 的待回复被岛 B 的 schedule 抹掉了（库里只剩 1 条）
✗ P0-2 待回复队列跨岛不互相抹掉 …  —— 岛 A 的待回复被岛 B 的 tick 抹掉了（库里只剩 0 条）
✗ flush 只处理当前岛 …            —— flush 把别的岛的条目抹掉了
✗ clearPending 只清本岛 …         —— clearPending 把别的岛的待回复清了
```

改回修复即恢复绿色。四次临时改动均已还原，并用 `git diff` 核对过工作区只剩修复版。
这一步是为了证明这几条测试**真能抓到缺陷**，不是恒过的摆设。
