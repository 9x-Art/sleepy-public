## 五、空返回的最小链路核对（**我此前的归因是错的**）

### 抓的是最终 HTTP body

在 `window.fetch` 上包一层，抓 `init.body` 解析后的**实际请求体**，
而不是 `api.requestOnce` 的入参（两者不等价）。

### 实际生效的模型与接口类型

- 端点 `https://api.rua.chat/v1`（`Access-Control-Allow-Origin: *`）
- 模型 `[按量]glm-5.2`；`GET /v1/models` 显示 `supported_endpoint_types: ["openai"]`
- **接口类型：OpenAI 兼容 `/chat/completions`，非流式**

### 最终 HTTP 请求体的参数字段

```json
顶层字段: ["max_tokens", "messages", "model", "stream", "temperature"]
model = "[按量]glm-5.2"   stream = false
max_tokens = 1024          temperature = 0.85
messages 段数 = 8 → 17 递增
messages 角色序列 = [system ×7, assistant, user …]
思考相关字段 = []          ← 请求侧一个都没传
headers = ["Content-Type", "Authorization"]
```

### 决定性证据：第 4 次

| 字段 | 值 |
|---|---|
| HTTP 状态 | **200** |
| 响应顶层键 | `["api_key_id","choices","created","id","model","object","provider","usage"]` |
| `choices[0].finish_reason` | **`"length"`** |
| `choices[0].message.content` | **`""`（长度 0）** |
| `choices[0].message.reasoning_content` | **存在，长度 4044**，前 40 字：`Let me look at the situation. The user s…` |
| `usage.completion_tokens` | **1024**（= max_tokens 打满） |
| `usage.completion_thinking_tokens` | **1020** |
| `usage.completion_tokens_details.reasoning_tokens` | **1020** |
| 耗时 | 59441ms |

**结论：服务端不是没给正文 —— 它把 1024 个 token 里的 1020 个花在了内部推理，
`finish_reason: length` 意味着输出被 max_tokens 截断，正文一个 token 都没轮到。**

### 四种可能性的逐一区分

| 可能性 | 判定 | 依据 |
|---|---|---|
| 服务端未给正文 | **部分成立** | `content` 确实是空 |
| 正文在其他字段 | **不成立** | `reasoning_content` 里是**推理过程**，不是正文；`message` 只有 `role`/`content`/`reasoning_content` |
| 客户端提取丢失 | **不成立** | `content` 字段本身就是 `""`；`parseOfflineReply('')` 走 `!text` 分支是**正确**行为 |
| 流式帧 / 聚合丢失 | **不适用** | 线下**强制非流式**（`stream=false`），没有数据帧可丢 |

**所以这是「服务端在 max_tokens 内没给正文留下空间」，不是客户端问题。**
客户端唯一能做的是调大 `max_tokens` 或关掉思考 —— **两者本批都不做**（不调额度、不加参数）。

### 其余各次

| 次 | HTTP | 耗时 | content | reasoning | finish_reason | usage |
|---|---|---|---|---|---|---|
| 1 | 200 | 8915ms | 427 | 无 | stop | prompt 2007 / completion 244 / cached 1280 |
| 2 | 200 | 8177ms | 453 | 无 | stop | prompt 2118 / completion 256 / cached 1280 |
| 3 | 200 | 9791ms | 240 | 无 | stop | prompt 2321 / completion 165 / cached 1280 |
| 4 | 200 | 59441ms | **0** | **4044** | **length** | completion 1024（thinking 1020） |
| 5-8 | **403** | ~1s | — | — | — | 响应体 `{"error":…}` 177 字节 |

> 1-3 次的 `usage` 是 OpenAI 标准形状；
> 第 4 次是 **Anthropic 风格 + 扩展**（`completion_thinking_tokens` / `reasoning_tokens` /
> `credit` / `prompt_cache_*` / `api_key_id` / `provider`）——
> **同一个端点在不同轮次返回了不同厂商的响应格式**，这点值得记录。

证据：`docs/证据-空返回链路-原始抓取-2026-10-04.json`
（只记录字段名、类型、长度、状态码、`finish_reason`、`usage`；
**不含密钥全文、不含完整对话、不含完整推理内容**）

## 六、端点官方推理配置说明（**只核对，不试塞**）

来源：阿里云百炼 / Model Studio 官方文档 + SGLang GLM-5.2 文档 + 智谱迁移指南。

| 结论 | 依据 |
|---|---|
| **GLM-5.2 是混合推理模型，深度思考默认开启** | 官方：「GLM-5.2 延续支持深度思考能力，**默认为开启**」 |
| 关闭方式是参数 | `enable_thinking: false`（**非 OpenAI 标准参数**，Python SDK 走 `extra_body`、Node SDK 走顶层参数） |
| 思考内容落点 | `message.reasoning_content`（思考）/ `message.content`（正文），**与本轮抓包完全吻合** |
| 推理程度控制 | `reasoning_effort`（`high` / `max`，默认 `max`） |
| 另有 `clear_thinking` | 控制是否保留历史 `reasoning_content` 以省 context |
| SGLang 侧命名 | 走 `chat_template_kwargs: {enable_thinking: false}`，**模板变量是 `enable_thinking` 而非 `thinking`** |
| GLM-5.2 输出上限 | 官方：最大输出 128K、上下文 1M |

### 对本项目的意义（**不构成施工建议，只作定位结论**）

- 代码侧**零推理配置**是**事实**，但**不代表模型不推理** ——
  抓包证明该端点的 GLM-5.2 **默认就在推理**。
- 因此「空返回」与「解析降级」的**真实成因**是：
  `max_tokens=1024` 被思考吃满 → `finish_reason: length` → `content` 为空。
- ⚠️ **本端点（`api.rua.chat`，第三方中转）是否透传 `enable_thinking` / `reasoning_effort`
  尚未验证** —— 中转商可能改写或丢弃这些字段。
  **按要求不试塞通用推理参数**，此项列入未验证。
