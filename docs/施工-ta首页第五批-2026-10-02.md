# 施工 · ta 首页 v1 第五批：已成立影响接入聊天与主动消息（2026-10-02）

> 用户定义：**不是让 ta 再长出新功能，而是让已经确认的生活真正影响角色的表达，
> 同时不越过知情、权限和证据边界。**
>
> 前四批的状态（见 `docs/验收-ta首页第四批-2026-10-02.md`）：
> 三张结构化表 + 提案通道 + NPC 草稿全部成立，但 ta 是一个**独立账本** ——
> `taEvents.impacts` 写进去了，聊天里一个字都看不见（ta-model.js:24-27 明确写着「本轮未接线」）。
> 本批就是把这根线接上。

## 0. 一句话

新增 `ta-impact.js`（影响层，0 模型），把 `taEvents.impacts` 从「ta 内部可读的记录」
变成「F1/F2 可注入、有效期可复核、可被更正、能驱动主动消息判断」的**已成立影响**；
注入只走一道闸：**知情 × 有效 × 相关**，且只当背景。

## 1. 不做什么（用户点名）

- 关系图；
- 日历自动写入；
- 新的模型设置页；
- 钱包、相册等新 App；
- 把所有 ta 数据重构成统一事件总线。

本批**不新增任何模型调用**，不改任何 prompt 卡文案（只加一个 program 槽）。

## 2. 影响的形状（扩展 `taEvents[].impacts[]`，向后兼容）

第四批的 impact 只有 4 个字段（`text/knownCharId/basis/reviewWhen/acceptedAt`，
ta-proposal.js:369-375）。第五批补齐「有效期 + 复核 + 反应史」所需的字段，
**老记录缺字段时按缺省值读**，不做迁移：

```
{
  id,            // 'ti' + … 稳定 id（新增；老记录没有 → 读取时按 eventRef+下标兜底）
  eventRef,      // taEvents.id（老记录从宿主事件补）
  kind,          // 'mood' 短期心绪 | 'situation' 持续处境   （缺省 'situation'）
  text,          // 影响内容（注入用，≤120 字）
  knownCharId,   // 谁知情（root 口径）—— 注入的**硬边界**，老记录沿用
  basis,         // 知情依据
  strength,      // 1..3（心绪可减弱；处境不衰减）           （缺省 2）
  reviewWhen,    // 复核条件（文本）
  resolveWhen,   // 解除条件（文本，处境用）
  expiresAt,     // 到期毫秒（null = 不按时间过期）
  status,        // 闭集见 §3                                 （缺省 'active'）
  reactedAt,     // 角色**已经有过反应**的时间戳（null = 还没）
  staleNote,     // 依据失效的说明（事件被更正时写）
  acceptedAt, history[]
}
```

### 2.1 字段怎么落

- 模型侧：`impact_review` 的 `extra` 白名单**只加 `impactKind`**（`mood`/`situation`）
  和 `resolveWhen`。模型**不能**给 `status`、`reactedAt`、`expiresAt` ——
  这三个是程序与玩家的事（沿用第四批「模型不能写正式状态」的口径）。
- 程序侧：`acceptProposal` 的 `impact_review` 分支按 `impactKind` 定 `kind`，
  `kind==='mood'` 才给默认 `expiresAt`（acceptedAt + 72h），并生成 `id`。
- 玩家侧：有效期、解除、更正、反应史都只能在幕后动（§6）。

## 3. 有效期与复核（用户第 2 条）

### 3.1 状态闭集（**五种，语义不许混**）

| status | 含义 | 谁改 | 注入？ |
|---|---|---|---|
| `active` | 生效中 | 程序/玩家 | **注入** |
| `faded` | 减弱淡了（心绪强度归零） | 程序衰减 | 不注入 |
| `expired` | 过期（超期未解除） | 程序 | 不注入 |
| `resolved` | 已解决 | **只能玩家手动** | 不注入 |
| `stale` | 依据失效（事实被更正） | 事件更正 | 不注入 |

**两条红线（写进代码注释 + 冒烟断言）：**

1. **过期 ≠ 解决**：`refresh()` 只会把东西推到 `faded` / `expired`，
   代码里**没有任何**「时间到了 → resolved」的通路（和第四批「事项完成 ≠ 承诺兑现」同构）。
2. **事实变了 ≠ 角色没反应过**：`correctEvent()` 把影响标 `stale`，
   但**保留 `reactedAt` 与整份 `history`**，也不删除记录 ——
   角色当时确实有过反应，这段经历不能被更正抹掉。

### 3.2 推进规则（`refresh`，纯本地确定性）

```
mood      ：strength -= floor(elapsed / 36h)，下限 0；到 0 → faded（+history）
            若 expiresAt 已到且 strength>0 → 直接 faded（时间到就是淡了）
situation ：不衰减；expiresAt 已到 → expired（+history）
            有 resolveWhen 但条件没成立 → 保持 active（持续处境保留到解除条件成立）
```

- 幂等：同一次推进不会重复写 history（状态没变就不写）。
- 每次变更都留 `history: {from, to, at, note}`，note 说清是「减弱」还是「过期」。

### 3.3 复核条件

- `reviewWhen`（文本）是给**人和模型**看的复核条件，不参与自动判定；
- `resolveWhen`（文本）同理 —— 处境是否解除由玩家点「解除」，
  程序不猜（沿用设计稿「不编生活」）。

## 4. F1 / F2 最小注入（用户第 1 条）

### 4.1 三道闸（顺序不能换）

1. **知情闸（硬边界，fail closed）**：`knownCharId` 必须等于 `core.rootIdOf(charId)`。
   对不上 → 一律不注入，连统计都不算。这条守住「NPC 的私密事件不会被角色提前知道」。
2. **有效闸**：只取 `status === 'active'` 且 `refresh` 后仍在有效期内的。
   **`pending` 提案天然进不来** —— 注入读的是 `taEvents.impacts`，
   而 pending 提案在 `taProposals`，两张表，没有任何通路（冒烟反向断言）。
3. **相关闸**：与「本轮输入」相关才注入。
   - 相关性 = **2-gram 集合重合率**（中文无空格，2-gram 是够用的近似分词）：
     `hit / queryGrams.length`，阈值 `0.25`；
   - query = history 里**最后一条 user 内容**（F1）/ session 当前输入（F2）；
   - 没有 query（纯系统触发）→ 只放 1 条最强最新的 `situation`。

### 4.2 上限与写法

- 最多 **2 条**，每条 text 截到 **60 字**；整块目标 ≤ 200 字。
- **绝不把 ta 全部历史塞进 Prompt**：只读 `taEvents.impacts`，
  不读 items/promises/follows/drafts/proposals 的任何正文。

### 4.3 槽位与文案

- 新槽 `taimpact`（slot `K03d`），排在 `recall`(K03c) 之后、`worldbook`(K04) 之前，
  线上与线下**各注册一次**（`ONLINE_SLOTS` / `OFFLINE_SLOTS`）。
- 块首句与块尾句把用户的三条约束写成模型看得见的话：
  - 这只是**背景**，不是台词任务，不要求每句话提起；
  - **不改变你的性格、说话方式和红线**（人设优先）；
  - 这些事**未必和对方有关**，不要因此对对方冷淡、发火或索取关心。

### 4.4 反应史（区分「事实变了」与「已经反应过」）

- `compile()` 把本轮实际注入的 impact id 记进**内存**（`_lastInject`，不落盘、不含敏感内容）；
- 聊天**回复成功落地后**（page-chat.js 总结引擎/主动消息同一位置）调
  `taImpact.noteReply(charId)` → 给这些影响盖 `reactedAt`（**只记第一次**，幂等）；
- 请求失败 / 空回复 → 不盖（没有反应就不算反应）。

## 5. 主动消息最小闭环（用户第 3 条）

现状（第四批已成立，本批只补最后一环）：

| 环节 | 现状 |
|---|---|
| accepted 的 `contact_candidate` 进现有判断 | ✅ 接受时写进 `attentionInbox:<root>`（ta-proposal.js:379-391） |
| 权限 / 频率 / 冷却 / 值不值得打扰 | ✅ `page-proactive.gateFor` + 模型判 decision |
| 只生成候选，不直接发送 | ✅ 队列 ≠ 发送 |
| **结果回写** | ❌ 缺失 —— 队列里那条永远停着，提案侧不知道后来怎样了 |

### 5.1 补的一环

1. `acceptProposal` 写 inbox 时给条目带上 `taProposalId`；
2. `page-proactive.candidatesFor` 把 `taProposalId` 带进候选对象，
   并让候选 id 变成 `attention:<proposalId>`（**只对带该字段的新条目生效**，
   老存档 handled 指纹不变）；
3. 决策落定（send 成功落库 / skip / defer）后调
   `taImpact.noteProactive(charId, {proposalId, decision, at, messageId})`；
4. 写回提案：`p.outcome = {decision, at, messageId}` + `history` 追加一条。
   **幂等**：同一 proposalId 已记过 `send` 就不再覆盖（send 是终态）。

### 5.2 边界

- 用户**没有**新 UI 确认环节 —— 「既有发送机制」就是现在的主动消息引擎，
  用户明确说「用户确认**或**既有发送机制成功后，才记录结果」，本批走后者；
- `ta` 侧只记结果，**不发送、不改频率、不绕过闸门**。

## 6. 聊天安全验收（用户第 4 条）→ 逐条对应

| 验收项 | 实现 | 冒烟 |
