## 一、真实 API 钉死的三件事（本卡所有改造的前提）

### 1. `forget()` 对外**永不 reject**，失败被吞成 0 —— 这是关键
真实实现（memory-vec.js:913-921）：

```js
function forget(filter) {
  filter = filter || {};
  var key = ownerKeyFor(filter);
  if (!key) return Promise.resolve(0);
  return scanOwner(key, null).then(function (list) {
    var hit = list.filter(function (b) { return forgetHit(b, filter); });
    return removeBlocks(hit.map(function (b) { return b.id; }));
  })['catch'](function () { return 0; });   // ← 失败吞成 0，永不 reject
}
```

- 底层 `withStore`（memory-vec.js:195-208）的 `onerror`/`onabort` **确实会 reject**；
- 但 `forget` 在返回链末尾 `['catch'](()=>0)` **把 reject 吞掉**，resolve 成数字（0 = 没删到 / 或删到 N 块）。
- **结论：光靠「先 `await forget` 再删主表」仍拿不到失败信号** —— 因为失败时它 resolve 0，看起来像「成功删了 0 块」。

### 2. `ownerKeyFor({groupId})` → `groupKey(groupId)` = `group:<gid>`
- memory-vec.js:1697-1712，`o.groupId` 优先 → `group:<id>`；
- `forgetHit`（:900-911）有 `b.groupId === filter.groupId` 维度，群块建块时 groupId+sandboxId 都盖章（buildRecs :1159/1161）。
- **按群精确清，不碰别的池** —— 这条链路 v1 判断是对的，保留。

### 3. 项目1 已确立「向量不可逆操作失败必须可见」范式
- `wipeAll` 返回三态 `cleared / not-applicable / failed`（`docs/修复-第二批-项目1-2026-09-23.md`）；
- 施工前设计（:272）明确「清向量：await memoryVec.forget（失败可见，不吞）」；
- **但项目3 之前，这个约定从没在 `forget` 上落地**（现有 6 个 forget 调用方全是幂等清理，无人依赖失败信号）。
- **v2 的落点：给向量层补一个「不吞错、按群严格删」的出口，供 purgeGroup 专用** —— 不改 `forget` 本身（会波及其它调用方语义）。

## 二、施工清单（改 3 文件 + smoke）

### ① memory-vec.js —— 新增 `forgetGroup(groupId)`（不吞错，供 purgeGroup 专用）

```js
/* 解散群专用：按 groupId 清空 `group:<id>` 整池，失败**拒绝**（不像 forget 吞成 0）。
   语义：空群（0 块）也是合法成功 —— resolve(删掉的块数)。
   调用方：core-group.purgeGroup —— 只有它需要「失败可见」的向量删除。
   为什么不改 forget：现有 6 个 forget 调用方全是幂等清理，改了会波及它们的语义。 */
function forgetGroup(groupId) {
  var key = groupKey(groupId);
  return scanOwner(key, null).then(function (list) {
    return removeBlocks(list.map(function (b) { return b.id; }));
  });   // ← 无 .catch：IndexedDB 打不开 / 写失败 → reject，失败信号透传
}
```

> 追加到 `Sleepy.memoryVec` 导出（memory-vec.js:2441 附近）。
> `groupKey` 是内部函数（:224），`scanOwner`/`removeBlocks` 都在闭包内可直接用。

### ② core-group.js —— 改造 `removeGroup` → `purgeGroup`（异步、事务有序）

```js
/* 解散群：唯一公开入口（异步）。事务顺序硬约定：
   ① 先确认群存在（findGroup）
   ② await memoryVec.forgetGroup(groupId) —— 向量先清，失败即拒
   ③ 只有向量明确成功后，才删派生键 + 线下行 + 三张主表
   失败路径：返回 {ok:false, why}，主表一行没动，可安全重试。 */
function purgeGroup(id) {
  var g = findGroup(id);
  if (!g) return Promise.resolve({ ok: false, message: '找不到这个群' });

  var MV = Sleepy.memoryVec;
  var vec;
  if (MV && MV.forgetGroup) {
    vec = MV.forgetGroup(id);   // 失败 → reject（IndexedDB 打不开 / 写失败）
  } else {
    /* 向量模块未就绪：无向量库可清。按项目1 范式 = not-applicable（不是失败）。
       这里**继续往下**清理主表（本机没有向量层，主表仍是唯一真相）。 */
    vec = Promise.resolve(0);
  }

  return vec.then(function () {
    /* ④ 到这里向量已明确清空（或本无向量层）—— 才开始删非主表 */
    store.remove('groupPending:' + id);
    store.remove('groupInner:' + id);
    store.remove('sumCursor:g:' + id);

    /* ⑤ 两张线下数组按行 groupId 过滤（不整键删）：
       - groupOfflineSessions 先 tombstone active→ended 再滤掉（见 §四 T5 语义）
       - offlineHandoffs 直接滤掉 */
    store.set('groupOfflineSessions', arr(store.get('groupOfflineSessions'))
      .map(function (s) {
        if (s && s.groupId === id && (s.status || 'active') === 'active') s.status = 'ended';
        return s;
      })
      .filter(function (s) { return !(s && s.groupId === id); }));
    store.set('offlineHandoffs', arr(store.get('offlineHandoffs'))
      .filter(function (x) { return !(x && x.groupId === id); }));

    /* ⑥ 最后删三张主表 */
    store.set('groups', allGroups().filter(function (x) { return x.id !== id; }));
    store.set('groupMembers', allMembers().filter(function (x) { return x.groupId !== id; }));
    store.set('groupMessages', allMessages().filter(function (x) { return x.groupId !== id; }));

    return { ok: true };
  })['catch'](function (err) {
    /* ⑦ 向量失败（或中途异常）：主表没动，返回失败，可重试。
       不显示「已解散」，不把失败转成 ok:true。 */
    return { ok: false, why: (err && err.message) || String(err || '向量清理失败') };
  });
}
```

> **关键变化 vs v1**：
> - `purgeGroup` **返回 Promise**（v1 里 `var p=...` 不 await 是错的）。
> - **向量成功是删主表的前置门禁**：`forgetGroup` reject → catch → `{ok:false}`，主表一行不动。
> - **不再有 `p['catch'](()=>0).then(()=>({ok:true}))`** 这种把失败转成功的写法。
> - `store.remove` 是同步的（store.js:375），无需 await。

- `Sleepy.groupStore`（core-group.js:457-479）：
  - **摘掉** `removeGroup: removeGroup`（:463）；
  - **新增** `purgeGroup: purgeGroup`。

## 三、修改后的调用链（端到端，回交）

```
用户长按群 → ui.confirm(解散, danger)
  → yes
    → Sleepy.groupStore.purgeGroup(g.id)        [async]
        ├─ findGroup(g.id) 不存在 → {ok:false,'找不到这个群'}   【不删任何东西】
        ├─ MV.forgetGroup(g.id)                 【向量先清】
        │    ├─ 成功（含空群 0 块）→ 继续
        │    └─ 失败(reject)    → catch → {ok:false, why}   【主表未动，可重试】
        ├─ 清 3 派生键（同步 remove）
        ├─ 线下两数组按行过滤（tombstone + 滤）
        └─ 删 3 主表 → {ok:true}
    → then(res)
        ├─ ok:true  → rebuild() + toast('已解散','ok')
        └─ !ok      → toast(失败原因,'err')    【不显示「已解散」】
```

**失败可重试的保证**：向量失败时 `findGroup(id)` 仍能命中（主表没删）→ 用户可再次长按解散 → `forgetGroup` 重跑 → 成功后彻底清理。这正是用户要求 7「再次重试成功后全部清理」的路径。

### 4.3 tombstone 语义（用户要求 9，定死一条）

**定稿：active 群线下会话 → `status='ended'` 后立即过滤删除，无观察期。**

理由：
- 设计稿最终施工设计 §4 的原文措辞是「tombstone 线下进行中会话」；
- 但「观察期」从未在任何设计文档里定义过（v1 §三 / §四 出现「观察期 ended」是**我写串的**，不是设计稿要求）；
- 群一旦解散，离线会话没有「事后结算」的价值 —— 调度 / 认知结算在群没了以后不会再看它；
- **只声明一种行为**：tombstone→ended 作为**删除路径上的一步**（保留 ended 标记给 UI 一次收尾，然后立刻从数组滤掉）。不做观察期，不保留任何该群线下行。

| # | 场景 | 断言 |
| -- | ---- | ---- |
| T5 | 目标群有 active 线下会话 → 解散 | 该行 `status='ended'` 后从 groupOfflineSessions 消失；**无任何残留行** |
| T5b | 目标群线下会话已是 ended / 无该群会话 | 直接过滤，无副作用 |

## 六、边界 / 回滚（v2 修正）

- **只动本群**：`forgetGroup(gid)` = `scanOwner('group:<gid>')` 整池删，天然只清本群；`sumCursor:g:<gid>` 是裸键同 gid 单份，remove 安全。无跨群误删面。
- **失败可见（硬保证）**：向量失败 → reject → `{ok:false, why}`，**主表一行不删**，`findGroup` 仍命中 → 可重试。彻底消除 v1 的「主表先删、无法重试」。
- **向量层与主表无法跨存储事务**（IndexedDB vs localStorage）：v2 用「向量先成功、再删主表」的**顺序门禁**近似事务 —— 即使极端下主表删了而向量有残留，`forgetGroup` 对已删源也幂等安全（重跑即清）。但**不会再出现「向量失败主表却删了」**（v2 已阻断）。
- **不可逆**：解散即物理删。保持长按→confirm danger 交互，不加「可恢复」。

### 8.2 purgeGroup 事务顺序门禁（core-group.js:203 起，定稿）

```
① findGroup(id) 不存在 → {ok:false,'找不到这个群'}，一行不删
② var hasIDB = !!global.indexedDB;            // 项目1 not-applicable 判据（memory-vec.js:155）
③ !hasIDB → cleanup()（直接删主表，本机无向量层，主表是唯一真相）→ {ok:true}
④ 有 IDB 但 memoryVec 缺失 / forgetGroup 缺失 →
     {ok:false, why:'memory-vector-unavailable/api-missing'}，主表保留   【安全边界：不静默物理删】
⑤ MV.forgetGroup(id)
     ├─ resolve → cleanup() → {ok:true}        // 向量先清成功才删派生键/线下/主表
     └─ reject  → {ok:false, why:'memory-vector-failed', error}   // 主表一行没动，可重试
cleanup(): remove groupPending/groupInner/sumCursor:g 三裸键 +
           按行过滤 groupOfflineSessions（active→ended→立即滤，无观察期）/ offlineHandoffs +
           滤 groups/groupMembers/groupMessages 三主表
```
