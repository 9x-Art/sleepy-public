## 一句话

向量库原来只有**对话**（线上/线下私聊 + 群聊/群线下）。本轮把
**朋友圈 / 日记 / 记忆档案 / 查手机（备忘·计划·订单）** 四类接了进去 ——
角色现在能按语义回忆起「你发过的那条动态」「你自己写的那篇日记」「他记着你怕吵」。

## 用户当场拍板的两件事（都改了设计）

### ① 朋友圈挂「岛级公共池」，不按角色复制

原始施工卡自相矛盾：§4.1 写 `ownerKey = rootOf(charId)`（按角色建），
§8.2 又要求「一条数据只建一个块，不按角色复制」。动态不属于任何角色，
这两条不能同时成立。用户选：**岛级单块** —— `ownerKey = island:<岛>`。

好处是 §8.2 想要的那三条真正成立：权限收紧挡住、权限放宽放行、
**新角色入岛不用补扫**（角色池是岛池的超集关系，不在池里就查不到）。

### ② 日记是**私密内容**，挂 `user:<账号>` —— 不是岛上的公共墙

用户原话：「日记为什么不是个人内容呀，动态我能理解」。
方案 §5-2 本来就写着「日历 / 待办 / 日记属于 user 私密内容，默认不对角色开放」，
是原始施工卡把它和动态归成了一类。改：

- `author === 'char'` 的日记 → `rootOf(那个角色)`，`iso='char'`；
- `author === 'user'` 的日记 → `user:<userId>`，`iso='user'`。

**连带发现**：日记数据结构里**连 `sandboxId` 都没有**（全文 0 命中，也没有 `userId`）。
也就是说日记一直是「全局单份」——跨岛、跨账号共享，而 `getDiaries()` 里的
`core.scoped()` 在有岛时反而会把它们全过滤掉。用户选了「顺手补上」，已做：
`addEntry` 现在走 `core.tagScope` 盖 `sandboxId`，user 写的再记 `userId`（当前马甲）。
老日记没有 `userId` 的，建索引时兜底归到当前账号。

## 四种 ownerKey（这是本轮最核心的改动）

| 池 | 主键 | 装什么 | 为什么 |
|---|---|---|---|
| 角色池 | `rootOf(charId)` | 对话 / 档案 / 查手机 | 都是「他自己脑子里的东西」 |
| 群池 | `group:<groupId>` | 群聊 | 群消息对成员公开（原有） |
| 岛池 | `island:<sandboxId>` | 朋友圈动态 | 一条数据全岛共享，可见性逐角色判 |
| 账号池 | `user:<userId>` | **我写的日记** | 私密内容，按账号隔离 |

一次私聊召回会把**角色池 + 本岛池 + 本条账号池**合起来查（`poolsFor`）。
拼 key 的规则收在 `ownerKeyFor` 一处，调用方不许自己拼。

## 与施工卡 §8.3 的两处偏离（都是按「意图」改的，理由在此）

§8.3 给了一张 iso 落值表，照抄会出两个 bug：

1. **表里 `moment` 的 `charId = null`** —— 但 §3.2 的 `stillVisible` 又写
   `canCharSee(m, b.charId, ...)`。`canCharSee` 第一个判断是
   `if (!m || !charId) return false` → 照着抄，**朋友圈一条都召不回**。
   实际做法：`stillVisible(b, charId, userId, snap)` 收的是**当前召回的人**，
   不是块里的 charId（§8.2 改成「召回时过滤」之后本来就只能这样）。
   另外**角色自己发的动态** `charId = 那个角色, iso='char'`（否则屏障下连
   他自己发的都召不回）。

2. **表里 `diary`（user 写）`iso='user'` 但 `userId = 写日记的身份`** ——
   日记数据里根本没有这个字段（见上）。补字段之后成立；老日记兜底当前账号。

`iso` 缺省 `'both'` → **老块（对话）行为一字不变**（冒烟里专门守着这条）。

## 落地清单

**memory-vec.js（内核）**
- `islandKey / userKey / islandKeyNow / ownerKeyFor`；
- `visibleTo` 按 iso 分流（`both` 缺省 / `none` / `char` / `user`）；
- `buildSnapshot(charId, userId)` + `stillVisible(...)` —— 回源复核，
  **O(1) 查表**（§8.7：一次召回建一份快照，用完就丢，不跨轮缓存）；
  **fail closed**：源定位不到 / 认不出的 kind / 没有快照 → 一律不召回；
- `blocksOf` 合并三池；`prefetch` / `probe` 建快照；
- `trim` **按 itemId 整组淘汰**（§8.8：一篇长日记不能只剩半篇残句）；
- `segText` 分片（1000 字，段落 → 句末 → 硬切，片间不重叠）；
- `reindexItem` 定向重建（§8.1）+ 四个语义化入口
  `refreshMoment / refreshDiary / refreshMem / refreshPhone`
  —— 「源怎么变成块」这套知识只留在 memory-vec 一处，别处不许重写；
- 四个源入口 `sweepMoments / sweepDiary / sweepMem / sweepPhone`；
- `overview` 补 `kinds` 分布 + 两池当前数 / 上限 / 最早块时间。

## 一个我判断「不需要做」的事（请复核）

施工卡 §8.2 说：认知锁 / 马甲映射变化**必须重建索引**（`resetCursors` + 清块）。

**我判断不需要**，理由：`visibleTo` 的 `barrier` 是**每次召回现读** `core.cognitionOf` 的
（`blocksOf` 里），不是建块时钉死的。开关认知屏障 → 下一次召回立刻生效，
不需要重算任何向量、更不需要重新 embed。

真正需要重建的是「**块的 `charId`/`userId` 指向错了**」这类情况（比如皮套改挂大号），
而目前没有这类入口。所以我没有挂自动重建，也**没有**新增 `rebuildChats()`
（不写用不上的代码）。哪天真出现「归属改挂」，用现成的 `resetCursors()` + 清对应池即可。
**若你不同意这个判断，说一声，我把它挂到 `core.setBarrier` 上。**
