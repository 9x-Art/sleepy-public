### 1.2 `weAdd` 现状（page-we.js:91-114，原文）

```js
function weAdd(rec, sandboxId) {
  var now = Date.now();
  var entry = {
    id: 'we-' + now.toString(36) + '-' + Math.random().toString(36).slice(2, 7),
    title: String(rec.title || '').trim(),
    note: String(rec.note || '').trim(),
    at: rec.at || null,
    kind: kindOf(rec),
    sourceType: rec.sourceType || 'manual',
    sourceId: rec.sourceId || null,
    sourceRef: rec.sourceRef || null,
    refCharId: rec.refCharId || null,
    refUserId: rec.refUserId || null,
    createdBy: 'user',          /* 首版只允许 user 创建 */
    createdAt: now,
    updatedAt: now
  };
  core.tagScope(entry, sandboxId);   /* 盖当前房章（core.js:72-77） */
  var list = arr(store.get(WE_KEY));
  list.push(entry);
  store.set(WE_KEY, list);
  return entry;
}
```

要点：
- id：`'we-' + Date.now().toString(36) + '-' + 随机`；
- **sandboxId 不手写**，走 `core.tagScope(entry, sandboxId)`（sandboxId 可显式传，冒烟/真机都传岛 id）；
- `sourceType/sourceId/sourceRef/refCharId/refUserId` 全部由调用方经 `rec` 传入；
- ⚠️ **entry 是白名单式构建**：`rec` 上多带的字段（比如 `createdBy:'char'`、`confirmedBy`、`confirmedAt`）**会被静默丢弃**。char 提议转正式藏品若要写 `createdBy:'char' / confirmedBy / confirmedAt`，必须扩展 `weAdd`（支持可选 `rec.createdBy`，默认 `'user'`；透传 `confirmedBy/confirmedAt`），这是施工轮绕不开的最小改动。

- 唯一要动的是 §1.2 的 createdBy/confirmedBy/confirmedAt 透传（向后兼容：不传仍是 `'user'`，现有调用与测试零感知）。

### 2.4 正文与结构化动作能否分离 —— 能，且是既成事实

`[表情]/[拍一拍]/[生图]/[手机]/[WHISPER]` 五种标签全部在 `onDone` 落盘**之前**从 `finalText` 里抽掉（page-chat.js:2687-2706），正文入库的是抽干净的文本。char 提议收藏若走标签协议（如 `[收藏提议:…]`），天然不会出现在聊天正文中——**这不是"用正则猜自然语言"，是项目已跑了多轮的闭集输出协议**（说明书槽明说格式，模型只填闭集参数，程序校验白名单）。

### 2.5 非法动作 / 重复动作 / 伪造 sourceId 在哪拦截

1. **抽取层**（onDone 内，落盘前）：标签参数过白名单校验（同 `phone.validateDelta` 模式：schema 不对/值域外 → 静默丢弃该条，不影响回复本身）。
2. **伪造 sourceId**：提议的 `sourceId` **不许信模型自报的标题/内容**——程序拿 `sourceId` 回源 `Sleepy.calendar.getEvent(id)`（calendar.js:475-479）复核：事件不存在 / 不属于本岛（`tagScope` 章）/ `eventType === 'char_schedule'` / 已取消，一律丢弃或降级。标题以 `getEvent` 返回为准，模型只提供「为什么想留」的理由文本。
3. **重复动作**：三道闸——
   - `originMessageId`：一条回复（含 reroll，reroll 复用同一 msg.id）最多产出一个提议；
   - `dedupeKey = sandboxId + refCharId + sourceType + sourceId`：已有 pending 的同 key 提议 → 不再新建；declined 过的同 key → 冷却期内不再提；
   - 每 char 全局在途上限：该 char 有 pending 提议未处理时，后续提议标签直接忽略（与 proactive「handled 记账」同思路）。
4. **接收入口**：accept/decline 只存在于 user 的 UI 动作里；`checkSource`（page-collection.js:68）在展示端继续兜底（提议引用的事件后来被删/取消 → 正确降级）。

### 2.6 最适合接入的真实节点

**单聊线上 `onDone` 抽标签链**（page-chat.js:2687-2706），紧跟 `[生图]` 之后、`applyPhoneTrace` 前后皆可：

- 说明书注入：prompt-engine 加一个 **program 槽**（先例 stickers/genimg：ONLINE_SLOTS L591-594 + program 生成器 L895-905——「没有候选就不注入」的闸门模式照抄：当前岛没有可提的日历事件就不教模型这个标签，模型自然不会瞎写）；
- 抽取 + 校验 + 建 proposal + 落一张代码生成的卡片消息（先例 `phone-invite` L2759-2766 / `wj-share` 渲染 wjCard L1855-1856、2004-2007）。

⚠️ 两个备选为什么不选：
- **独立导演调用**（像 ttsDirector 那样回复后补发一次请求）：多一次 API 花费，且门禁本来就该本地判（有没有候选事件是本地事实，不用问模型）——项目契约「不新增第二条调用路径」也倾向不另起炉灶；
- **线下 JSON 链**：那是另一条生成链（page-offline），本轮范围只做单聊，线下要不要提议留后续拍板。

## 四、proposal store 推荐结构

### 4.1 独立 store，还是 weEntries 放 pending？——**独立 store**

判据（全部来自真实代码）：
1. 门厅计数条直接 `entries().length` + `countKind`（page-collection.js:201-205），`weEntries` 一旦混入 pending，**馆藏总数/kind 计数/分组立刻被污染**，除非每个消费点都加 `status !== 'pending'` 过滤——那是对「绝不进入正式馆藏」这条红线最弱的保障（漏一处就穿）；
2. `checkSource` / `findInScope` / 冒烟既有断言全部假设 weEntries = 正式记录；
3. 项目里「pending → confirmed」的既有判例（日历 shared_event：status pending + participantStates，calendar.js:454/505、page-calendar.js:869-874/1087-1094）也是独立状态字段而非另一张表——但日历那个「pending 也算事件」的教训恰好说明：**计数语义敏感的表不要混状态**；
4. 独立 store 让「user 未操作前 char 无权动」的权限边界有唯一载体。

### 4.2 推荐结构（在用户草案上按真实代码微调）

```js
// store key：'weProposals'（scoped）
{
  id: 'wep-<ts36>-<rand>',            // 同 weAdd 风格
  sandboxId,                          // tagScope 盖章（取 chat 自身的岛，不取全局指针）
  refCharId, refUserId,               // 提议者 = 提议当轮的 (characterId, userId)

  status: 'pending' | 'accepted' | 'declined',

  kind,                               // 七类白名单，落正式记录时过 weStore.kindOf
  title,                              // 以 getEvent 复核结果为准，不信模型
  note,                               // char 的提议理由（模型给的文本，截断）
  at,                                 // 展示日期（取事件 startAt 或 day）

  sourceType: 'calendar',             // 首版只开日历一种（sourceCandidates 现有产出）
  sourceId,                           // 事件 id；复核口径同 checkSource
  sourceRef,                          // 同 sourceCandidates 的 r.date

  proposedBy: 'char',
  proposedAt,
  originMessageId,                    // 提议当轮的 msg.id（reroll 复用同 id，天然防重）
  dedupeKey,                          // sandboxId|refCharId|sourceType|sourceId
  originChatId,                       // 回聊天页定位用（可选）

  resolvedBy: 'user',
  resolvedAt
}
```

### 4.3 状态流与四问

1. **accepted 后复制还是转换？** —— **复制生成正式记录，原 proposal 只改状态**。理由：proposal 上有 originMessageId/dedupeKey/resolvedBy 等流程字段，塞进 weEntries 会污染馆藏数据形状；weEntries 的形状必须保持 store.js:162-165 注释那份契约。
2. **accepted 写入走哪？** —— `weStore.add(rec, proposal.sandboxId)`，显式传岛 id；正式记录 `createdBy:'char'`、`confirmedBy:'user'`、`confirmedAt: Date.now()`（**需按 §1.2 扩展 weAdd 透传**）。
3. **declined 保留什么？** —— 保留整行（status:'declined' + resolvedAt），它是去重依据；可选定期清理（如 30 天前的 declined），首轮可以不做、只在注释里说明。
4. **同一条回复反复提议怎么防？** —— `originMessageId` 唯一约束（onDone 只跑一次，天然一次；reroll 同 id）+ `dedupeKey` 查重（pending 存在 → 跳过；declined → 冷却）+ char 在途 pending 上限 1。

### 4.4 必须同步的两处基建（新增 scoped 键的铁律）

- `store.js` DEFAULTS 加 `weProposals: []`（先例 weEntries：store.js:160-168）；
- `core.js:342-357` `cleanupSandbox` 的 scoped 删房名单加 `'weProposals'`（注释 L336-340 明文要求，漏了 = 幽灵数据）。

### 4.5 权限边界

- **char 侧唯一动作 = 创建 pending**，且只能由代码在 onDone 抽标签后创建——模型输出永远只是文本，从不直接写任何 store；
- accept / decline 只在 user UI（详见 §五）；`resolvedBy` 固定 `'user'`；
- user 未处理前：char 不能改/撤/接受（代码上根本没有这条路径，不是「靠校验拦」）。

## 七、风险与不确定项

1. **标签协议 = prompt 内容变更**（prompt-engine c05 之外的槽）——本轮禁改已遵守；施工时说明书措辞需拍板，且「没候选就不注入」的闸门必须做（否则模型会瞎编 sourceId）。
2. **模型伪造 sourceId / 标题**：唯一解法是回源复核（getEvent + 岛章 + 排除 char_schedule/cancelled），标题一律以复核结果覆盖模型自报——已写进 §2.5，施工时必须做成提议创建的前置条件（fail closed）。
3. **stopReply 半截回复**：提议标签可能只写了一半——extract 正则天然抽不到未闭合标签，风险低，但 stopReply 路径必须跑同一抽取链（先例 L2821-2823），否则行为不一致。
4. **weAdd 白名单构建**（§1.2）：不扩展就静默丢 createdBy/confirmedBy —— 这是本轮勘察发现的最容易漏的坑。
5. **reroll 的语义**：reroll 后同一 msg.id 再出一版回复，若新回复又提议同一事件，dedupeKey 会拦——但「user 刚 declined，reroll 又提议」是否算打扰，属产品判断，建议 declined 冷却（比如同 key 7 天内不再提），数值待拍板。
6. **群聊 / 线下不在本轮**：group-ai（page-group-ai.js）与线下 JSON 链是另外两条生成路径，本轮只接单聊线上；未来要不要覆盖需另行勘察。
7. **多 pending 并存**：不同 char 各有 pending 是合理的（群岛多角色）；同一 char 同时多条 pending 建议上限 1，避免门厅待确认条堆叠。
8. **detail 页 createdBy 展示**（page-collection.js:329）：`'char'` 会原样显示英文——施工时改成角色名（`core.findChar(refCharId)`），老记录兜底不变。
