## 〇、一句话结论

`core.js` 的三个删除函数（`removeSandbox` / `removeChar` / `removeUser`）**全是同步的、只清 localStorage 主表，向量库（IndexedDB `sleepy-vec`）一行没清**，也**没有失败可见门禁**。删一座岛 / 删一个角色 / 删一件马甲之后，它的私聊 / 朋友圈 / 日记 / 群聊向量块全部残留 —— 下次同 id 重建（概率极低）会召回幽灵记忆；且 `scanOwner` 的 `scopeNow()` 岛过滤会让「已切走当前岛再删」的场景**漏扫向量**。项目4 就是把这四类删除补成项目3 那样的 purge 级（异步事务门禁 + 向量先清 + 失败可见可重试）。

## 一、现状盘点（四类删除对象）

### 1.1 删除函数现状

| 删除对象 | 入口（UI） | 现实现 | 清了什么 | 漏了什么 |
|---|---|---|---|---|
| **岛**（isle/archipelago） | `page-island.js:551` 拆岛 | `core.removeSandbox`（core.js:233，**同步**） | scoped 名单 28 键按 `r.sandboxId` 过滤 + 动态键 `charRel:<sbId>` 整键删 + `appearance/desktop.islands[id]` 岛覆盖层 + `desktopRemoved` + `charAppearance.byChar` 悬空引用 | **向量池全没清**（`island:<sbId>` 朋友圈 + 各角色 rootOf + 各马甲 user: + 各群 group:）；**失败不可见**；`activeSandboxId===id` 才清 active（可接受） |
| **角色（大号）** | `page-idcard.js:1105` / `page-chat-settings.js:1024` | `core.removeChar`（core.js:557，**同步**） | characters 该 id + 其皮套（sub）+ chats/links/memories（按 doomed root 过滤） | **向量池没清**（该 root 的 rootOf 池全部）；**不涉皮套单独删**；**失败不可见** |
| **NPC** | `page-island.js:1300` | `core.removeChar`（同角色） | 同上（NPC 自身 + 无皮套） | 向量池 `rootOf(npcId)` 没清 |
| **皮套（sub）** | `page-island.js:1300`（isSubC 分支） | `core.removeChar`（同角色） | characters 该 sub + 其下 NPC + chats/links/memories（按 doomed root 过滤） | **向量池没清**；⚠️ 皮套删除必须按 **fromCharId** 维（同一 root 下别的皮套的块**必须留下**）—— `removeChar` 现在**没这维**，直接删会把整个 root 池误删 |
| **user马甲** | `page-idcard.js:1640` | `core.removeUser`（core.js:673，**同步**） | 只删 userMasks 行 + 大号顶替（`isDefault` 继承） | **向量池 `user:<uid>`（我写的日记）没清**；**用它建的 chats / links / 朋友圈 / 线下会话没清**（UI 文案明说「对话会留下来，但找不到马甲」—— 历史遗留） |

### 1.2 现状共同缺陷（三处）

1. **向量库完全没清**：四类删除都没碰 `memoryVec`。残留的块在 IndexedDB 里，下次同 id 重建会召回幽灵记忆。
2. **没有失败可见门禁**：全同步，删主表前不校验向量是否清干净。删岛这种**不可逆物理删**，向量清理失败会静默残留（项目3 已确立「不可逆删必须失败可见」范式，这里没跟上）。
3. **`scanOwner` 岛过滤隐患**：`scanOwner`（memory-vec.js:251-264）用 `scopeNow()`（**当前此刻的岛**）过滤 `b.sandboxId === sid`。**删岛 / 删别岛角色时，当前岛往往已切走** → 目标岛块被 `scopeNow()` 全滤掉 → 扫出空 → 向量没删到。这是删岛/删别岛角色最典型的场景。

## 二、向量块归属（删对象的向量面）

### 2.1 块盖章（buildRecs，memory-vec.js:1165-1193）

一个向量块记录字段（写入时 `sid` = 当时所在岛的 sandboxId，**每个块都有岛章**）：

| 字段 | 语义 |
|---|---|
| `ownerKey` | 召回主键（`rootOf` / `group:` / `island:` / `user:`） |
| `charId` | 属于**哪个大脑**（一律 root；群/岛/账号池为 null） |
| `fromCharId` | 由**哪张脸**产生（精确；群/岛池我的动态/我写的日记为 null） |
| `userId` | 属于哪个账号（user 写的日记） |
| `groupId` | 属于哪个群 |
| `sandboxId` | 属于**哪座岛**（岛的章） |
| `kind` | `chat` / `moment` / `diary` / `mem` / `phone` |
| `sourceId` | 源（会话 id / 子源） |
| `iso` | `both`/`char`/`user`/`none` |

### 2.2 ownerKey 四类（ownerKeyFor，memory-vec.js:1712-1727）

| 内容 | ownerKey | 依据 |
|---|---|---|
| 私聊 / 角色对话 | `rootOf(charId)` | ownerKeyFor 末行兜底 |
| 角色档案（mem） | `rootOf(charId)` | `kind==='mem'` |
| 查手机（phone） | `rootOf(charId)` | `kind==='phone'` |
| 角色日记 | `rootOf(charId)` | `kind==='diary' && charId` |
| 朋友圈动态 | `island:<sid>` | `kind==='moment'` → islandKeyNow |
| user 写的日记 | `user:<uid>` | `kind==='diary' && !charId` → userKey |
| 群聊 | `group:<gid>` | `groupId` |

### 2.3 删对象时向量块分布（关键表）

| 删除对象 | 需要清的 ownerKey 池 | 按什么维 |
|---|---|---|
| **岛** | `island:<sbId>`（朋友圈）+ 岛上每个角色的 `rootOf(charId)`（私聊/档案/日记）+ 每个马甲的 `user:<uid>`（我的日记）+ 每个群的 `group:<gid>`（群聊） | **按 sandboxId 跨全部池** |
| **角色/皮套** | 该 root 的 `rootOf(root)` | 删皮套 → 必须再按 **fromCharId** 精确（同 root 别的皮套块留下） |
| **NPC** | `rootOf(npcId)` | charId=npcId |
| **马甲** | `user:<uid>` | userId=uid |

**核心难点**：删岛要跨 **四类 ownerKey** 精确清，现有 `forget`（单池 + 吞错 + 岛过滤）做不到；`forgetGroup` 只管单群；`wipeAll` 是全库。**没有「按 sandboxId 全库精确删」的原生 API。**

## 三、目标范式（对齐项目3 `purgeGroup`）

项目3 已确立的范式（memory-vec.js:923-936 + core-group.js:214）：

- 向量层提供**不吞错**的整池删出口（`forgetGroup` 失败 reject）；
- 调用方用**异步事务门禁**：先清向量、拿到**硬信号**才继续删主表；
- 失败可见、空结果也算合法成功、可重试。

项目4 依此补四类删除。**新增一个向量层出口 + 三个 core 层异步门禁**：

### 3.1 向量层新增：`forgetSandbox(sandboxId)`（全库按岛章删，不吞错）

```js
/* 拆岛专用：按 sandboxId 把这座岛的**全部**向量块清掉（跨 island:/rootOf/user:/group: 四类 ownerKey）。
   全库游标 + `b.sandboxId === sandboxId` 精确过滤 —— 绕开 scanOwner 的 scopeNow 岛过滤隐患。
   失败**拒绝**（不像 forget 吞成 0）：拆岛是不可逆物理删，必须见错即停。
   语义：空岛（0 块）也是合法成功 —— resolve(删掉的块数)。
   为什么不改 forget：现有 6 个 forget 调用方全是幂等清理，且 forget 单池 + 吞错。
   实现要点：open() 后全库 openCursor 遍历，命中 `b.sandboxId===id` 收集，removeBlocks；
   顶层不 .catch —— IndexedDB open/onerror/onabort 失败 → reject，失败信号透传。 */
function forgetSandbox(sandboxId) { ... }
```

> **为什么能按 sandboxId 跨池清**：每个块都盖了 `sandboxId` 章（buildRecs:1176），且四类池都盖。全库遍历 `b.sandboxId === id` 就能精确命中这座岛的所有块，**不管当前岛是不是它**（绕开 scopeNow）。

### 3.2 core 层新增/改造（异步事务门禁，都返回 Promise）

沿用项目3 的 not-applicable 判据（`!!global.indexedDB`，项目1 范式）：

```
① find 确认存在，不存在 → { ok:false, message }
② var hasIDB = !!global.indexedDB
③ !hasIDB → cleanup()（本机无向量层，主表是唯一真相）→ { ok:true }
④ 有 IDB 但 memoryVec 缺失 / forgetSandbox 缺失 →
     { ok:false, why:'memory-vector-unavailable/api-missing' }，主表保留
⑤ MV.forgetSandbox(id)
     ├─ resolve → cleanup() → { ok:true }
     └─ reject  → { ok:false, why:'memory-vector-failed', error }   // 主表一行没动，可重试
```

- **`removeSandbox` → `purgeSandbox(id)`**（异步）：cleanup = 现有 scoped 28 键 + charRel:<sbId> + 岛覆盖层 + 悬空引用（现有逻辑原样挪进 cleanup，只加向量门禁前置）。
- **`removeChar` → `purgeChar(id)`**（异步）：cleanup = 删 characters（该 id + 皮套 + 其下 NPC）+ chats/links/memories + **向量 `forgetSandbox` 之外再按该 root 清**。⚠️ 皮套单独删时（page-island.js:1300 isSubC）需区分：`purgeChar(subId, {faceOnly:true})` → 向量用三维 `{charId: root, fromCharId: subId, sandboxId}`，**只删这张脸的块**。
- **`removeUser` → `purgeUser(id)`**（异步）：cleanup = 删 userMasks 行 + 大号顶替 + **`forgetSandbox` 之外清 `user:<uid>`** + 用它建的 chats/links/朋友圈/线下会话（补齐历史遗留「对话留下来但找不到马甲」）。

## 四、跨岛引用 / 共享身份边界

### 4.1 现状事实

- char 与马甲**都按岛打章**（`characters.sandboxId` / `userMasks.sandboxId`，2026-09-21 拍板）；`removeSandbox` 按章连坐清人（scoped 名单含 characters/userMasks）。
- 但 `validateSandboxChars`（core.js:119）**只校验「非大号不能入房」，不校验「该角色是否已属于另一座岛」** —— **同一 char id 理论上可被两座岛的 `sb.charIds` 引用**。马甲同理（`setSandboxMasks` 只查存在性）。
- 结果：若发生跨岛共享，删岛 A 会把该角色（按 sandboxId 章）连坐清掉，而岛 B 的 `sbB.charIds` 仍指向它 → **岛 B 幽灵引用**。

### 4.2 设计取舍（待拍板）

- **方案 A（推荐，最小）**：维持「拆岛连人清」语义，**不引入跨岛共享校验**。理由：UI 侧「加角色到岛」从没允许把同一角色加到多座岛（群岛选角色、孤岛唯一），跨岛共享是数据异常而非正常用法。但 **purgeSandbox 时顺手做一次「被删角色是否还被别的岛引用」的守卫**：若发现 `其他沙盒.charIds 仍含被删角色`，返回 `{ok:false, why:'still-referenced', by:[岛名]}` 拒绝拆岛 —— 防止幽灵。
- **方案 B**：允许跨岛共享，删岛只清「本岛引用」不清人。**不推荐**：会推翻 2026-09-21「拆岛连人清」拍板，改动面大。

### 4.3 指针卫兵兜底

即便有残留引用，`activeCharOnIsland` / `activeUserOnIsland`（core.js:744/759）已保证「当前身份必须是本岛名册成员，否则 null」—— 幽灵引用**不会**导致写到错误角色。这是既有安全网，purge 施工后可加一条冒烟守它。

## 五、项目5 三维 forget 依赖（UI 接线缺口）

- `forget` 的三维（`charId/fromCharId/sandboxId`）**逻辑已在**（forgetHit:900-911，T12/idb 测试验过），但**生产 UI 没有入口**（验收-项目5 第7步如实记录：删皮套/移出岛未接线三维 forget）。
- 项目4 的 `purgeChar(faceOnly)` 正好把「删皮套」接上三维 forget —— 这一步同时**补上项目5 遗留的 UI 接线缺口**。
- ⚠️ 但 `forget` 单池 + 吞错 + scanOwner 岛过滤，**不能直接用于 purge 级删皮套**。删皮套走 `forgetSandbox` 拿块列表 → 再按 `fromCharId` 过滤删块（或新增一个不吞错的维度删出口）。**待施工时定**：要么 `forgetSandbox` 支持 `fromCharId` 过滤参数，要么另写 `forgetFace`。
