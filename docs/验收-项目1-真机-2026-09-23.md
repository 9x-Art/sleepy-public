# 项目 1 · 真机验收单（2026-09-23）

> 给执行人的操作手册：**照着点就行，不需要看代码、不需要自己判断哪里可能出错。**
> 每一格都写清：从哪进 → 点哪个 → 要准备什么 → 该看到什么 → 什么算失败 → 失败截哪一屏。
>
> **分成两类**：
> - **A 组（普通项）**：手机上就能做完，不需要电脑、不需要开发者工具。
> - **B 组（开发辅助项）**：**必须**在电脑浏览器 + F12 控制台注入一次故障才能验，
>   手机上做不了。每项都标了「为什么手机做不了」。
>
> **开始前必须先做的一件事**：进「设置 → 数据与备份」→ 点 **导出备份**，把 json 存好。
> A4、B 组都会真删数据，没有备份就只能重来。

## 用到的两个页面（先认路）

| 页面 | 怎么进 | 用来看什么 |
|---|---|---|
| **数据与备份** | 底部 dock 的「设置」→「数据与备份」 | 导出 / 导入 / 清空 / 图库占用 |
| **向量记忆 API** | 底部 dock 的「设置」→「其他能力」组里的「**向量记忆 API**」 | **索引了多少段**（这就是「块数」）、每行多少段、清掉某一份、试试召回 |

「向量记忆 API」页里，我们要盯的三处文案：

1. 开关下方那行小字：有块时显示 **「已经索引了 N 段对话。聊得越多，能找回来的越多。」**；N=0 时这行是**空的**。
2. 「索引」组：有块时每行是「**角色名 · N 段（对话 x/y · 素材 a/b）· 最近 M月D日**」；
   没有块时是一句 **「还没有索引 —— 聊几轮之后会自动开始（在后台跑，不挡聊天）。」**
3. 「试试召回」组的「找找看」按钮。

## A1 用户导出的真实 JSON 里没有过程数据【优先级 1】

**进哪** 设置 → 数据与备份

**点哪** 「导出备份」那一行

**准备什么**
- 先让它**真的有索引**，否则"没有过程数据"是空话：进「设置 → 其他能力 → 向量记忆 API」，填好 embedding 接口（baseUrl / 模型 / Key），点一次「测试连接」看到通过；然后找任一角色**聊 4～6 轮**（每轮你一句、TA 一句）。
- 回到「向量记忆 API」页，确认这句出现了：**「已经索引了 N 段对话」**（N ≥ 1）。
  > 若一直不出现：等 10 秒再刷新这页；还不出现就先看 A2 的"失败判据"里那条诊断（说明索引没建起来，先解决它）。

**该看到什么**
1. 点「导出备份」→ 提示「已导出 · xxx」→ 手机通知/浏览器下载里出现 `sleepy-20260923-15xx.json`。
2. 打开这个文件（手机文件管理器里用文本查看器打开；或把文件传到电脑用记事本/VS Code 打开）。
3. 在文件里**搜索**这几个词：`vecCursor`、`vecEpoch`、`vecFail`、`charMemBackup`、`charMemMigrationState`、`sleepy.rb`
   → **全部搜不到（0 个结果）**。
4. 反过来再搜一次 `vectorApi` 和 `chats` —— **应该能搜到**（说明你打开的是对的文件、正式数据确实在里面）。

**什么算失败**
- 搜索到任何一个 `vecCursor…` / `vecEpoch` / `vecFail…` → **失败**（过程数据漏进备份了）。
- `vectorApi` 或 `chats` 也搜不到 → 说明你打开的不是 Sleepy 的备份文件，重做本项。
- 文件是空的 / 只有几百字节 → 失败，截图。

**失败截哪** ① 导出成功的那条 toast；② 文本编辑器里搜索到那个键的那一屏。

**对应报告条目** 三向边界文档 §6 第 1 条；项目 1 交付 §5 第 1 条的前置。

> 说明：`charMemBackup:*` / `charMemMigrationState` 要等项目 5 做完才会真的出现，
> 本项目能真验的是 `vecCursor*` / `vecFail:*` / `vecEpoch` 这三类（它们现在就会存在）。

## A2 清空全部数据后，向量块真的归零【优先级 2】

**进哪** 设置 → 数据与备份（先）→ 设置 → 向量记忆 API（后）

**点哪** 「清除全部数据」按钮 **两次**（第一次变成「再点一次，确认清除」）

**准备什么**
- 承接 A1：此刻「向量记忆 API」页应显示「已经索引了 N 段对话」，且「索引」组里**有行**。
- **记下当时的 N**（截图留着，下面要对）。

**该看到什么**
1. 第一次点「清除全部数据」→ 按钮文字变成「再点一次，确认清除」。
2. 第二次点 → toast **「已清除，正在刷新…」**，约 0.7 秒后页面重新加载（一般会回到开屏/锁屏）。
   > 如果这里出现的是红色 **「没清干净：本地数据：…；图库：…；向量库：…」** → 看"失败判据"。
3. 刷新后进「设置 → 其他能力 → 向量记忆 API」：
   - 开关那一行下面**没有**「已经索引了 N 段对话」这句话（N=0 时这行本来就空）；
   - 「索引」组显示 **「还没有索引 —— 聊几轮之后会自动开始（在后台跑，不挡聊天）。」**

**什么算失败**
- 清空后，「索引」组里**还留着任何一行**（例：「顾清和 · 12 段（对话 12/300）」）→ 失败。
- 或者还显示「已经索引了 N 段对话」（N 是你刚才记下的那个数）→ 失败。
- 弹出「没清干净：…」→ 失败（这是**设计上**的失败提示，不是崩溃；照下一条截图）。
- 「这台设备用不了 IndexedDB，向量记忆没法工作。」→ 环境问题，不是本项失败，但请截图。

**失败截哪** ① 第二次点击后弹出的那条 toast；② 刷新后「向量记忆 API」页整屏（要能看到「索引」组）。

**对应报告条目** 项目 1 交付 §5 第 1 条；复核修订 §7 第 1 条。

## A3 清空之后，新聊天能重新建块【优先级 8】

**进哪** 设置 → 向量记忆 API（先）→ 聊天（中）→ 向量记忆 API（后）

**点哪** 「测试连接」→ 聊天里发消息 → 回来刷新这一页

**准备什么**
- 承接 A2：此刻是"清空后"的状态。**注意：清空会把 API 配置一起清掉**（这是设计如此），
  所以要先**重新填一次**向量接口：baseUrl / 模型 / Key → 点「测试连接」→ 看到「通了 · 返回 xxxx 维向量」。
- 确认开关「按话题找回聊过的东西」是**开着**的。

**该看到什么**
1. 找一个角色聊天，来回 **4～6 轮**（每轮你一句、TA 一句，聊点有内容的话题）。
2. 回到「设置 → 其他能力 → 向量记忆 API」页（**退出去再进来**一次，这一页不会自动刷新）。
3. 小字重新出现：**「已经索引了 N 段对话」**，且「索引」组里出现**一行**（角色名 + N 段 + 日期）。

**什么算失败**
- 聊了 6 轮、等 30 秒、来回进出这一页 3 次，**始终是「还没有索引」** → 失败。
- 出现「这台设备用不了 IndexedDB」→ 环境问题，截图即可，不算本项失败。

**失败截哪** ① 「向量记忆 API」页整屏（含那句小字与「索引」组）；② 你聊的那段聊天记录截图。

**对应报告条目** 项目 1 交付 §5 第 1、3 条（`total()` 归零与新生）。

## B1 导入失败后：旧 localStorage、向量块、游标、vecEpoch 都恢复【优先级 3】

**为什么手机做不了** 需要把 `store.importAll` 临时替换成"必定失败"，手机上没有控制台。

**准备什么**
- Console 里依次粘贴执行下面 3 段（**一段一段来**，看懂每段回显再粘下一段）：

```js
/* ---------- 复制开始：从这一行往下选中 ---------- */
// ① 看看现在的家底（记下数字）：块数 / 世代号 / 游标键 / 过程数据
Sleepy.memoryVec.total().then(n => console.log('块数 =', n));
console.log('vecEpoch =', Sleepy.store.get('vecEpoch'));
Object.keys(localStorage).filter(k => k.indexOf('vecCursor') >= 0 || k.indexOf('vecFail') >= 0)
  .forEach(k => console.log('进度键', k, localStorage[k].slice(0, 60)));
console.log('恢复区 =', localStorage.getItem('sleepy.rb.pending'));
/* ---------- 复制结束 ---------- */
```

```js
/* ---------- 复制开始：从这一行往下选中 ---------- */
// ② 在存档里塞一个"给导入用的假数据"，并记住现在的一个正式键的值
Sleepy.store.set('验收探针', '导入前的值');
console.log('导入前 =', Sleepy.store.get('验收探针'));
/* ---------- 复制结束 ---------- */
```

```js
/* ---------- 复制开始：从这一行往下选中 ---------- */
// ③ 让写入必定失败 —— 顺便记下"到底被调用了几次"（这是本项的硬证据）
window.bakImport = Sleepy.store.importAll;
window.importCalls = 0;
Sleepy.store.importAll = () => { window.importCalls++; return { ok: false, message: '验收注入的写入失败' }; };
console.log('已注入：写入必定失败');
/* ---------- 复制结束 ---------- */
```

**点哪**
- 进「数据与备份」→ 点 **「导入备份」** → 选**你刚才导出的那个 json**（任意一个 Sleepy 备份都行）。

**该看到什么**
1. 选完文件后，toast 是 **失败**色，开头是 **「导入没完成：验收注入的写入失败（…」**，
   括号里是一串逐项结果，其中**必须有**一段 **「回滚：已按快照恢复…」**。
   > 括号里的内容形如：`校验备份：已清；保存恢复快照：本地存档 + N 块向量 + 索引进度；向量库：…；回滚：已按快照恢复（本地存档 + N 块向量 + 索引进度）`
   > 看到「回滚：已按快照恢复」就说明：**写失败 → 自动回滚 → 回滚成功** 这条链跑通了。
2. **页面不刷新**（停在「数据与备份」）。
3. 回 Console，执行下面这段（**验收 ①**）：

```js
/* ---------- 复制开始：从这一行往下选中 ---------- */
// ④ 验回滚：正式数据、过程数据、索引进度是否都回来了
console.log('写入被调用次数（必须是 1，否则说明你根本没点到导入）=', window.importCalls);
console.log('验收探针 =', Sleepy.store.get('验收探针'));       // 必须是「导入前的值」
Sleepy.memoryVec.total().then(n => console.log('回滚后块数 =', n));  // 必须和 ① 里记的一样
console.log('回滚后 vecEpoch =', Sleepy.store.get('vecEpoch'));        // 必须和 ① 里一样
console.log('游标/退避键 =',
  Object.keys(localStorage).filter(k => k.indexOf('vecCursor') >= 0 || k.indexOf('vecFail') >= 0).length);
console.log('恢复区（应该已被删）=', localStorage.getItem('sleepy.rb.pending'));
/* ---------- 复制结束 ---------- */
```

**什么算失败**
- **`写入被调用次数` 不是 1** → 整项**作废重做**（多半是你没点到「导入备份」，或者注入没生效）——
  这是本项唯一能证明"流程真的跑到了写入那一步"的硬证据。
- toast 不是"导入没完成…"，而是「导入成功，正在刷新…」→ **失败**（注入没生效，重做 ③）。
- 「验收探针」不是「导入前的值」→ **失败**（正式数据没恢复）。
- 回滚后块数 ≠ ① 记的数字 → **失败**（块没恢复）。
- 回滚后 `vecEpoch` ≠ ① 记的数字 → **失败**（世代号没恢复）。
- 最后一行不是 `null` → **失败**（回滚成功了却没删快照）。
- Console 里出现红色报错 → 失败，**把报错整段复制下来**。

> ### ⚠️ 如果 ① 里「块数 = 0」，那"块数"这一条是**空断言**
>
> 0 块的时候，回滚前后都是 0 —— 数字相等，但它**证明不了"块被恢复了"**，只证明了"没更糟"。
> 同理 B2 里的「向量快照库块数」也会是 0。
>
> 所以：**先把 A1 做完（配好 embedding 接口 + 聊 4~6 轮，让块数 ≥ 1），再回来复跑 B1/B2**，
> 那时的块数断言才算数。现在跑也可以，但请在记录里写清「块数 0，块断言未生效」——
> **不要**把它记成"块恢复通过"。

**失败截哪** ① Console 里 ④ 那段的完整输出；② 「数据与备份」页里的失败 toast；③ Console 里红色的报错（如果有）。

**对应报告条目** 复核修订 §7 第 2 条；三向边界 §4 第 8 条。

**收尾（必须做）**

```js
/* ---------- 复制开始：从这一行往下选中 ---------- */
Sleepy.store.importAll = window.bakImport;   // 把注入撤掉
Sleepy.store.remove('验收探针');                 // 清掉本项的临时键
console.log('已还原 importAll，探针已清');
/* ---------- 复制结束 ---------- */
```

3. Console 粘贴执行（**验收 ②**）：

```js
/* ---------- 复制开始：从这一行往下选中 ---------- */
// ③ 验保留：两份快照都必须还在
var p = JSON.parse(localStorage.getItem('sleepy.rb.pending') || 'null');
console.log('恢复区存在 =', !!p, ' 状态 =', p && p.status, ' 原因 =', p && p.failReason);
Sleepy.memoryVec.snapCount().then(n => console.log('向量快照库块数 =', n));
console.log('召回门是否关着 =', Sleepy.memoryVec.recallPaused());   // 必须是 false
/* ---------- 复制结束 ---------- */
```

**什么算失败**
- `恢复区存在 = false`（`sleepy.rb.pending` 没了）→ **失败**（最后一份能回去的东西被删了）。
- `状态` 不是 `restore-failed` → **失败**。
- `召回门是否关着 = true` → **失败**（门没释放，之后这个页面再也不召回）。
- toast 说「恢复完成」或页面刷新了 → 失败。
- Console 红色报错 → 失败，复制报错。

**失败截哪** ① ③ 那段的完整输出；② 失败 toast；③ Console 报错。

**对应报告条目** 复核修订 §7（回滚失败的保留语义）；§3 的"回滚失败"一行。

**收尾**

```js
/* ---------- 复制开始：从这一行往下选中 ---------- */
Sleepy.memoryVec.total = window.bakTotal;
Sleepy.store.importAll = window.bakImport2;
Sleepy.store.remove('验收探针2');
/* 顺手把这份"故意失败"留下的快照清掉 —— 这一步同时也在验「继续恢复」：
   它成功 = 那条链路也能跑通（等价于 B3，只是这里不点 UI） */
Sleepy.backupApp.resumeRestore().then(function (r) {
  console.log('继续恢复 =', r.ok ? '成功' : '失败', r.message);
  console.log('清理后恢复区 =', localStorage.getItem('sleepy.rb.pending'));  // 应为 null
});
/* ---------- 复制结束 ---------- */
```

> 最后那句 `resumeRestore()` 成功 = 「上次导入未完成 → 继续恢复」这条链路也在电脑上验过了。

## B3 「上次导入未完成 → 继续恢复」这个入口【优先级 6】

**为什么手机做不了** 要先让机器上留着一份"未完成的恢复快照"，而制造它就需要控制台。

**准备什么**（在电脑上造一份遗留快照）

```js
/* ---------- 复制开始：从这一行往下选中 ---------- */
// 造一份"导入前的快照"并标成失败状态 —— 等价于「上次导入回滚也没成功」
var snap = {
  v: 1, at: Date.now(), status: 'restore-failed',
  failReason: '验收造的假快照',
  local: Sleepy.store.exportInternalSnapshot(),
  index: Sleepy.memoryVec.indexState(),
  vecBlocks: 0
};
localStorage.setItem('sleepy.rb.pending', JSON.stringify(snap));
console.log('已放置遗留快照');
/* ---------- 复制结束 ---------- */
```

**点哪**
1. 在「数据与备份」页**退出去再进来一次**（或按 F5 刷新）。
2. 找页面顶部出现的 **「上次导入未完成」** 组 → 点里面的 **「继续恢复」**。

**该看到什么**
1. 组标题是 **「上次导入未完成」**，下面有一行可点的 **「继续恢复」**，
   小字提示是「上次的原因：验收造的假快照…」。
2. 点「继续恢复」→ toast **「恢复完成：已按快照恢复…，正在刷新…」** → 页面刷新。
3. 刷新后再进这一页：**「上次导入未完成」这一组不见了**（快照已被消费掉）。
   还可在 Console 里确认：`localStorage.getItem('sleepy.rb.pending')` → `null`。

**什么算失败**
- 页面上**看不到**「上次导入未完成」这一组 → 失败（UI 没接上）。
- 点「继续恢复」报红/没反应/提示「恢复仍未完成」→ 失败（电脑上这份假快照的 local 是完整的，
  不该失败；失败请截图 Console）。
- 刷新后那一组**还在**、`pending` 不是 null → 失败（成功了却没删）。

**失败截哪** ① 「上次导入未完成」那一屏（要点得到"继续恢复"）；② 点完的 toast；③ Console 输出。

**对应报告条目** 复核修订 §3（下次启动能发现并继续）；§7 第 5 条。

**收尾**（如果失败、快照还留着，用它清掉）

```js
/* ---------- 复制开始：从这一行往下选中 ---------- */
localStorage.removeItem('sleepy.rb.pending');
/* ---------- 复制结束 ---------- */
```

> **手机上也能看这个 UI**：在电脑上放好遗留快照后，用同一份存档/同一地址在手机上刷新，
> 进「设置 → 数据与备份」就能看到这一组并点「继续恢复」。如果你想要"手机点一次"的体验，可以这样做。

## B4 双标签页 blocked【优先级 5】

**先说清楚一件事（重要）**：这一项在**当前版本下基本触发不了**，原因是设计如此 ——
`wipeAll` 只是清空一个 store（`os.clear()`），不会和别的标签页抢版本；
**只有"数据库版本升级"时**（`DB_VER` 从 5 变成 6，那是项目 5 的活），
如果用户还开着旧标签页，才会撞上 `onblocked`，代码里那句
「向量库被另一个标签页占着」才会出现。

所以本项分两半：

### B4-a 普通部分（可以做，验"不崩"）
**进哪** 数据与备份 / 向量记忆 API 页
**准备** 手机上或电脑上**开两个标签页**都打开小手机。
**做** 在标签页 A 里点「清除全部数据」（两次）。
**该看到** A 正常完成并刷新；标签页 B 刷新后数据也是空的（因为同一份 localStorage）。
**什么算失败** A 卡住不动 / 弹红字 / 页面白屏。
**失败截哪** A 的 toast + 控制台报错。
> 结论：**预期是通过**，但这只证明"两个标签页同时开着不会坏事"，**不是** blocked 分支。

### B4-b blocked 分支 —— **建议延后到项目 5 再验**（现在做性价比很低）

**先说结论**：这一项**现在不用做**。理由三条，看完你就明白它为什么排最后：

1. **当前版本根本触发不了**：`wipeAll` 只是清空一个 store（`os.clear()`），不和别的标签页抢版本。
   `onblocked` 只在**「数据库版本升级」**时才会响 —— 也就是 `DB_VER` 从 5 变成 6 的那一刻。
2. **那个"升级"是项目 5 的活**（项目 5 会给块加 `fromCharId`，那时才会 5→6）。
   到那时**顺便验**才是真实场景：老用户开着旧标签页 + 新版首次打开 → 被挡住 → 提示"关掉另一个标签页"。
   现在为了验它，要先改代码、再改回来、还要删库重建，全是人造步骤。
3. 它**验不出新东西**：它证明的是"浏览器会 block、我们的代码会给出提示"，
   而这两件事都由**平台行为 + 现有代码**保证，跟项目 1 的改动没关系。

**所以本项的结论先写成：延后（项目 5 升 DB_VER 时一并验）。**
如果你现在就想要一个结果，下面两段任选。

#### 想亲眼看一眼 blocked 长什么样（**零副作用，推荐**）

不用改代码、不碰真库，随便在哪个标签页的 Console 里跑：

```js
/* ---------- 复制开始：从这一行往下选中 ---------- */
// 演示 blocked 机制（用的是临时库名 blocked-demo，跟小手机的库无关）
var c1 = null;
var req1 = indexedDB.open('blocked-demo', 1);
req1.onsuccess = function () {
  c1 = req1.result;                                  // 先占住一个 v1 连接
  var req2 = indexedDB.open('blocked-demo', 2);      // 再要更高版本
  req2.onblocked = function () {
    console.log('✅ 看到 blocked 了：旧连接还开着，升级被挡住');
    c1.close();                                      // 松开 → req2 立刻成功
  };
  req2.onsuccess = function () {
    console.log('v2 打开成功，演示结束（临时库已删）');
    req2.result.close();
    indexedDB.deleteDatabase('blocked-demo');
  };
};
/* ---------- 复制结束 ---------- */
```

该看到：先打印 **✅ 看到 blocked 了…**，紧接着 **v2 打开成功，演示结束**。
（这就是"另一个标签页占着库、升级被挡住"的完整过程 —— 小手机到时候就是在这个位置
给出「向量库被另一个标签页占着」那句提示。）

#### 非要现在验小手机自己的 blocked 分支（**会清掉向量索引，且要改代码**）

有条件、也有风险，步骤必须一步不落（我上一版这里写错了，下面是修正版）：

1. 电脑上把 `memory-vec.js` 的 `var DB_VER = 5;` 改成 **6**，保存。
2. 打开**标签页 A**：用改后的文件打开小手机 → 它用 v6 建了库，A 持有连接。
3. 打开**标签页 B**：同样打开小手机（也是 v6，复用同一个连接）。
4. 把 `DB_VER` **改回 5**，保存，然后**刷新标签页 B** →
   此时库是 v6、B 请求 v5 → **B 会直接报版本错误**（不是 blocked）。
   > 到这一步你会发现"改回 5"这条路走不通 ——
   > **真正能触发 blocked 的唯一组合是「库还是旧版本 + 有连接占着 + 来一个新版本请求」**，
   > 而小手机的版本号是常量，所以只能靠"一个标签页跑旧版、一个跑新版"。
   > 这已经超出"照单操作"的范围了 —— 所以我建议就按上面那条零副作用的演示收尾。
5. 真要往下做，收尾是：关掉所有标签页 → 任意页面 Console 执行
   `indexedDB.deleteDatabase('sleepy-vec')` → 把 `DB_VER` 改回 **5** → 重新打开小手机。
   **这一步会清掉向量索引**（你现在的块数是 0，没损失，但别再拿有数据的档来做）。

**失败截哪**（只在真做了第 5 步那一版时）「向量记忆 API」页整屏 + Console 整屏。

**收尾** 把 `DB_VER` 改回 5；关掉多余标签页。

**对应报告条目** 项目 1 交付 §5 第 2 条；复核修订 §7 第 4 条。
