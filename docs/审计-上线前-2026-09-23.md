## 3. 问题清单

> 严重程度：**P0** 数据丢失 / 隐私越权 / 身份串线 / 记忆严重错误 / 核心流程不可用；
> **P1** 主要功能不稳定 / 数据不同步 / 记忆漏写 / 旧数据错误 / 跨模块联动失败；
> **P2** 体验 / 维护性 / 后续扩展。

### P0-1｜聊天里的「手机痕迹」永远不落库（静默丢数据）

- **严重程度**：P0　**影响模块**：线上私聊 → 查手机（AI 自动生成痕迹）
- **文件/行号**：`page-chat.js:2509`（`var phOwner = SC.rootIdOf(chat.characterId) || chat.characterId;`）
- **实际现象**：角色回复里带 `[手机]` 痕迹时，查手机里不会多出任何备忘/订单/计划/痕迹。全程无报错提示。
- **预期行为**：抽出 `[手机]` 行 → 校验 → `ensurePhone` + `applyDelta` 落库（`:2510-2523`）。
- **根本原因**：`chat-detail` 页面 render 的作用域里只声明了 `chatId`（`page-chat.js:1135`）；`chat` 这个变量只在**另一个函数** `createChat` 里声明（`page-chat.js:383`，已核对：全文件仅此一处 `var chat`，且无任何赋值型 `chat =`、无 `window.chat`）。在 `runReply` 里引用 `chat.characterId` 会抛 `ReferenceError`，被 `page-chat.js:2525` 的 `catch (e) { /* 手机痕迹失败不影响这条回复 */ }` 吞掉。
- **影响范围**：查手机模块"由对话自动长出来"的全部内容（`extractPhoneDeltas` / `applyDelta` 所有 app 类：notes / shop order / order_status / planChanges / permission）；手动功能不受影响。
- **复现步骤**：让角色在回复中出现 `[手机]` 痕迹行 → 打开查手机 → 无新增。
- **建议修复方式**：`var phOwner = SC.rootIdOf(c0 && c0.characterId)`（复用 `runReply` 里已有的 `c0` 或重取 `getChat(chatId)`），并对 `chat` 类引用做一次全文件排查（避免同类残留）。
- **是否需迁移旧数据**：不需要（该链路从未成功落过数据）。
- **是否需补测试**：需要。冒烟应加一条「带 `[手机]` 的回复能落进 `phones`」——现冒烟用注入桩，覆盖不到这一层，这正是它漏掉的原因。

### P0-2｜朋友圈待回复队列在换岛时被整批抹掉（跨岛数据丢失）

- **严重程度**：P0　**影响模块**：朋友圈 AI（`moments-ai.js`）
- **文件/行号**：`moments-ai.js:251-254`
  ```
  function pendingAll() { return core.scoped(store.get(PENDING_KEY)) || []; }
  function savePending(list) { store.set(PENDING_KEY, list); }
  ```
- **实际现象**：切岛 / 换存档后，**别的岛**里「已排期但还没发」的朋友圈回复会被整批删除。
- **预期行为**：读用 `scoped` 过滤，写必须对**全量数组**做增删后再整体 set。
- **根本原因**：`pendingAll()` 返回的是**按当前岛过滤过**的列表，`savePending()` 把它整表写回同一个键 → 其它岛的记录没了。这正是 `core.js:48-58` 纪律注释点名的最惨一类错误（"把过滤过的数组写回 store → 别的存档的数据被整批抹掉"）。`schedule()`（`:257`）与 `tick`（`:738/:745`）都走这一对函数。
- **影响范围**：多岛用户的朋友圈 AI 排期（`momentPending`）；单岛用户无感。
- **复现步骤**：在岛 A 攒下若干条待回复（触发 AI 但未到时间）→ 切到岛 B → 再切回岛 A → 待回复全空。
- **建议修复方式**：`pendingAll()` 改读全量 `store.get(PENDING_KEY)`，过滤只在**选取要处理的那几条**时做；`savePending` 保持整表写。参照 `page-chat.js:142-150` 的 `allChats()`/`getChats()` 双出口写法。
- **是否需迁移旧数据**：不需要。
- **是否需补测试**：需要。冒烟加「两岛各挂待回复 → 保存一侧不抹另一侧」。

### P1-1｜总结产出的档案不进向量库

- **文件/行号**：`page-summary.js:154`（`store.set('charMem:' + charId, file)`）；全文件对 `memoryVec` **零引用**（grep 0 命中）
- **现象**：总结里 `status='active'` 的条目 L0（K03）立刻可见，但向量库里永远没有。
- **根因**：进向量库的唯一口子在 `page-memory.js` 的 `addMemoryItem/writeMemoryItems → sweepMem`；总结引擎直接写 `charMem` 文件，绕过了它。
- **影响**：`user_explicit` / `confirmed_event` 这类高价值记忆长不进去，L4 召回长期缺一块。
- **复现**：清掉索引 → 跑一次总结 → 清聊天再问相关话题 → 召不回；去留痕手动加一条后，同批才补进。
- **建议**：总结 ingest 对每条新增且 active 的条目调 `memoryVec.refreshMem(charId)`（或统一改走 `memoryStore` 的写入函数）。
- **补测试**：需要（「总结产出 → 向量块出现」）。

### P1-2｜记忆系统开关只关 L0，不关 L4（权限绕开）

- **文件/行号**：`page-memory.js:381`（`if (!cfg.enabled) return '';`）；`memory-vec.js` 全文件无 `memoryIsland` / `charConfig` 引用（grep 0）
- **现象**：关掉某角色的「记忆系统」后，K03 注入为空，但向量块照旧建、照旧经 K03c 注入。
- **影响**：用户以为"关掉了"，实际角色仍能回忆起那些内容 —— 属于授权与预期不符。
- **建议**：`blocksOf` / `sweepMem` 入口先判 `charConfig(charId).enabled`（关 = 不召回，是否停建块按产品定）。
- **补测试**：需要（「开关关掉后 K03c 也空」）。

### P1-3｜清空数据 / 导入备份都不动向量库，且 chat 类块无回源复核

- **文件/行号**：`page-backup.js:170-185`（只 `store.clearAll()` + `Sleepy.media.clear()`）、`:65`（`store.importAll`）；`memory-vec.js:49`（`sleepy-vec`）；`memory-vec.js:339`（`if (kind === 'chat' || kind === 'offline' || kind === 'group') return true;`）
- **现象**：清空全部数据后，IndexedDB `sleepy-vec` 里的块（**含块内保存的原文文本**，`memory-vec.js:426`）仍在；导入旧备份后同样保留。
- **根因**：`store.clearAll()` 只扫 `sleepy.v1.` 前缀（`store.js:472-487`），向量库是另一个存储层，代码里没有任何 `memoryVec.clear()/wipe()` 的调用点（唯一导出 `memory-vec.js:1663`，仅被 `page-singleapi.js:581` 的 `forgetStale` 使用）。且 `stillVisible` 对 chat/offline/group 三类**不做回源复核**，所以残留块不会被"源已不存在"挡掉。
- **影响**：隐私残留（清库不彻底）+ 幻觉源（导入后可能召回当前存档里根本不存在的原文）。`docs/说明-记忆系统地图.md` 自己写过"索引里那份原文和存档对不上就是幻觉源"。
- **复现**：写入若干向量 → 设置→数据与备份→清空全部 → DevTools → IndexedDB 看 `sleepy-vec` 仍有记录；或 备份→继续聊→导入旧备份→提问，可能召回到新档没有的消息。
- **建议**：清空路径与 importAll 后各调一次整库重建/清空（`indexedDB.deleteDatabase('sleepy-vec')` 或遍历 `forget`）；删角色/拆岛同理补 `forget`。
- **是否需迁移**：不需要，但要做一次「存量用户清一次索引并重建」的提示。
- **补测试**：需要（「清空后 IDB 块数 = 0」）。

### P1-4｜解散群不清群向量块与线下痕迹

- **文件/行号**：`page-chat.js:1066`（`Sleepy.groupStore.removeGroup(g.id)`，无 `memoryVec.forget`）；`core-group.js:205-211`（只清 `groups`/`groupMembers`/`groupMessages`）
- **现象**：删群后 `group:<groupId>` 池的块残留；`groupOfflineSessions`、`offlineHandoffs` 也留着（只有删整岛时才清，`core.js:249-250`）。
- **影响**：`groupSince` 取不到成员时回落 0 → 越界过滤失效，可能召回已删群的内容；localStorage 越积越多。

### P1-5｜素材向量游标不绑岛 → 换岛后永久漏索引

## 4. 账号与主号 / 小号审计

### 4.1 当前实际账号模型（从代码读出，非猜测）

代码里**没有** `accountId` / `mainAccountId` / `subAccountId` 这套命名（全仓 0 命中）。实际是**四个 ID 命名空间 + 一个群内句柄**：

| 名字 | 是什么 | 载体 | 证据 |
|---|---|---|---|
| `userId` | User 侧账号 = 一件马甲 | `userMasks[].id` | `core.js:583` |
| `charId` | Char 侧账号 = 一张脸（大号/皮套/NPC） | `characters[].id` | `core.js:393/403-420` |
| `rootId` | 记忆库主人 = 大号的 id（皮套归父） | 由 `parentId` 推 | `core.js:480/487` |
| `sandboxId` | 存档作用域键（"此刻数据属于谁"） | 记录上的章 + `activeSandboxId` | `core.js:340/72` |
| `maskId` | 朋友圈「哪张脸发的」= `userId` 的**别名** | `moments[].maskId` | `page-moments.js:240` |
| `groupId` | 群 id；另有 `groupKey='grp:'+排序后 charIds` | `groups` | `core-group.js:111`、`core.js:1178` |
| `accountId` | **群内账号句柄**（不是账号模型）：`kind='user'` 时=userId，`char/npc` 时=charId | `groupMembers.accountId` | `core-group.js:85/140/155` |

设计稿里的「主账号/小号」在代码中对应：**主账号 = 本岛 `maskIds` 中标 `isDefault` 的那件马甲**（`core.js:708`、`:692`）；**小号 = 同岛其余马甲**。Char 侧对应 `kind:'main'`（大号）/ `kind:'sub'`（皮套），皮套经 `boundUserId` 绑马甲（`core.js:530`）。

**注意**：`page-group.js` 里的「主账号 · 群主」文案（`:1142/:1821`）指的是**群主**，不是账号体系里的主账号，别混。

### 4.2 主号与小号的设计关系

代码里**同时存在三种**大小号语义，要分开看：

1. **同岛马甲（user 侧大小号）**：共享 `sandboxId`，`isDefault` 互斥（`core.js:697`）。**聊天 / 朋友圈按账号隔离**（`page-chat.js:173`、`page-moments.js:107`），**记忆共享**（同一 `rootId`，`core.js:961`），除非该 `link.barrier` 为真（`core.js:1012-1023`）。
2. **角色大小号（char 侧）**：皮套 `parentId → 大号`，**共享同一个记忆库**（`rootOf`），聊天各自独立（`characterId` 不同）。
3. **岛与岛**：完全平行存档，按 `sandboxId` 整批切开。

结论：**是「同一存档下不同身份 + 共享部分资料（记忆/人设/岛屿）+ 隔离聊天与朋友圈」**，与设计基本一致。不一致的遗留项见 P1-14 / P1-15。

### 4.4 切换 / 退出 / 删除 / 恢复

- **切换**：只改三个全局指针（`core.js:768 switchTo`），数据不搬。两个卫兵 `activeCharOnIsland`/`activeUserOnIsland`（`core.js:744/759`）挡住旧指针，已落到聊天/桌面/日记/朋友圈/主动/线下/查手机。**残留风险**：① 页面实例缓存复用导致表单/订阅/开场旗标残留（P1-9/P1-10/P1-11）；② 异步嵌入在切换期间返回 → 盖错岛章（P1-6）；③ 朋友圈名单陈旧（P1-7）。
- **退出/返回旧数据**：无"登出"概念；`chat-detail` 的 `onShow → reload → getChat(chatId)` 在跨岛后返回 null 即 `ctx.back`（`page-chat.js:3645`），读路径基本安全。
- **删除**：删岛清 32 个 scoped 键 + `charRel` + islands 覆盖层，但漏 `momentWall`/`charMem` 系列 + IndexedDB（P1-14）；删马甲只动 `userMasks`（P1-14）；删角色只清 3 张表（P1-14）。
- **恢复/清库**：`store.clearAll` 只清 localStorage；备份页清了图库（`page-backup.js:173-174`），**没清向量库**（P1-3）。导入备份不清向量库 → 旧块可被召回（P1-3）。

### 4.5 与 Prompt / 记忆 / 向量的关系

- Prompt 的 K01/K02/I01 都按 (charId, userId) 取人设与认知；认知模式由 `link.cognition/barrier` 推（`prompt-engine.js:694-715/779-809`）。
- 记忆按 `rootId` 汇总，注入前由 `memoryViewFor` 按 barrier 分裂为「物理隔离 / 全量+归属保护」两档（`core.js:1012-1030`）。
- 向量召回按 `cognitionOf().barrier` 实时过滤（`memory-vec.js:357`），**不依赖建块时钉死的值** —— 这点是对的，冒烟里守着。
- **待验证**：`memoryStore.loadCharMemory(charId)` 在向量路径里拿到的 `charId` 是 root 还是皮套（`memory-vec.js:282`），决定 `charMem` 归属是否稳定；代码内无法确证。

### 4.6 是否需要历史数据迁移或清理

**不需要破坏性迁移**：`charMem/charState/openLoops/attentionInbox/momentWall` 等键虽无 `sandboxId` 字段，但 `charId` 全局唯一，正常路径不会串。需要补的是**删除/清库路径的清理逻辑**（P1-3/P1-4/P1-14），并对存量用户提示"清库/换岛后索引会重建"。
