## 一、结论（三句话）

1. **3～4 人能被完整送进请求**：3 人、4 人两组各自恰好 1 次请求，每个人物块恰好一份，
   没有漏人、没有多拼一块、没有互相覆盖（T4 / T5 / T6 / T7，共 30 条断言）。
2. **空主体不会被 filter 掉后继续出图**：少于 3 人拦下、第 4 人留空拦下、共同描述留空也拦下，
   三种情况请求数都是 0，报错文案点名是哪个人物（T3，共 7 条）。
3. **General 与文字通道（chat）都通**：两条路吃的是同一份群像提示词，差别只在负面怎么送
   （独立 `negative_prompt` 字段 vs 拼成「画面里不要出现这些要素」自然语言段），NAI 被明确拦下（T9 / T10）。

新增测试 `scripts/browser-e2-group-visual-test.js`：**76 ✓ / 0 ✗**，退出码 0，
全部请求被 `page.route` 拦在浏览器内（6 次 `images/generations` + 1 次 `chat/completions`），**零付费**。

## 四、是否需要抽公共 UI —— 结论：**不抽**

三档临时入口（单人 / 双人 / 多人）差异集中在「主体下有哪些框」，公共的那部分（视觉模式、接口选择、
生成按钮、结果回显）本来就是共用的。本轮做法是：**新增独立函数 + UI 局部扩展**，不引入第四套抽象：

- 拼接函数独立：`buildGroupSubjectExperimentPrompt`，`buildPromptForPlan` 与「`subjects.length !== 1` 单人守卫」一行未动
  （纯函数夹具里两条「真实身份路拿到 N 个主体仍然 `null`」断言过了，证明守卫没被放宽）。
- UI 层是 `subjOptions` 加一项 + 两个 textarea + 两个按钮 + 一条 `syncGroup()`，
  没有新的折叠面板、没有新的参数行分支模式，参数行只是 `paramLine` 里多一个 `if (snap.group)` 分支。
- 双人那套（`twoHint` / `twoApiWarn` / `paPick` / `pbPick`）完全复用，人物A / B 就是双人的那两个框 →
  切回双人时原输入不被覆盖（T11 覆盖）。

**踩到的坑（写进后面_mem）**：`syncExpUI` 改显隐时，群像的 C/D 与按钮**必须**由 `syncGroup()` 全权管，
不能在 `syncExpUI` 里顺手置灰；而且切走时要显式 `foldRow.style.display='none'`，
否则在 4 人档切到「单人」会把「收起第 4 位」漏在单人面板里（T11 反向断言）。

## 六、这轮修掉的两个真 bug（不是测试问题）

1. **`allowedRefs` 漏哨兵（03 遗留 / 本轮 `@temp-group`）**——`page-imggen.js:456`。
   `allowedRefs` 只登记了 `@temp`，选过 `@temp-two` / `@temp-group` 后重开页面会被判
   「这个主体已经不在本岛或已被删除」。已把三个哨兵一起补上。
2. **群像分支 fall-through**——生成的 `if/else` 链里，群像那块是独立 `if` 且尾部没有 `return`，
   `group=true` 时设完 `built` 继续往下，落入最后那个「真实主体」`else`，误报「不在本岛」，
   请求根本没发出去。已并入链首（`page-imggen.js:757` 起）。

另外补了「**回到 3 人**」这条必需要路：原来人物数只增不减，一旦放出 D 就卡在 4，
想画三人组既填不上也退不回（T4 / T5 / T6 直接出不了图）。现在上限时露出一个「收起第 4 位（回到 3 人）」。

## 十、真实群岛接入前的阻塞项（7 条，本轮一律没做）

1. **群岛成员 → 稳定主体列表**：现在 `TEMP_GROUP_REF` 是哨兵字符串，不是 `entityType` / id；
   接真身份要先定义「多人里每个人对应哪张名册里的哪一件」。
2. **失效 / 重复 / 离岛要明确报错**：本轮「空人物 = 拦下并点名」，但真实身份可能
   失效、重名、已离岛——现在没有这几类分支，也不能静默减员。
3. **id / 名 / 性别 / 年龄 / 外貌必须分块绑定**：本轮只是把用户手写的描述整段搬进
   `Person X（人物X）: …`，没有结构位；真实接入要按字段分块，避免「名字串到人身上」。
4. **未出镜成员要明确排除**：群里 A 没出现在画面里时，不能因为「他是成员」就被带上。
5. **结构化位置 / 动作 / 物件 / 关系要能传进 `description`**：本轮靠自然语言描述扛，
   4 人以上的位置关系（谁站哪、看向哪、手碰什么）没有结构化通道，模型容易合并身份。
6. **3～4 人以上的人数 / 费用 / 画幅 / 模型限制**：本轮完全不限幅，接真接口后要确认
   多人物下是否降质、是否要拆图、单次费用是否可接受。
7. **正式 chat 的 `[生图:]` 要限人数防模型扩大群像**：模型可能在计划里写出 5 个以上的
   `subjects`，本轮守卫在 `buildGroupSubjectExperimentPrompt` 里挡（>4 → null），
   正式链路也要有同样的上限，否则一发请求就被拒、用户体验很差。
