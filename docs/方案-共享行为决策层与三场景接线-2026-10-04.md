## 〇、结论摘要

现有两个决策函数 `btOnlineDecision` / `btOfflineDecision` 的**十步校验完全同构**，
差异只有四个参数（场景常量 / 槽位契约 / override 判定 / 第三块协议正文）。
因此**不需要新写一套决策逻辑**，只需把这两个函数参数化成一个内部工厂。

**本轮施工范围（已按用户三项语义修正收敛）**：

| 场景 | 接入力度 | 诊断口径 |
|---|---|---|
| online / offline | 不动（已完整接线） | 维持现状 |
| **proactive** | **完整接线**：shell + **E/S3 全注入** | `modules = ['B','P','L','E','S3']`、`partial = false` |
| **groupOffline** | **部分接线**：只接 shell | `modules = ['B','P','L']`、`pendingModules = ['N','S5']`、`partial = true` |
| **groupOnline** | **不接线**，只交静态冲突清单 | — |

⚠️ **上一版设计的错误已修正**：原方案让三场景「sceneText 只记账不注入」，
但诊断会照 PLANS 报全量 —— **那是撒谎的诊断**。现改为
「要么真注入、要么显式标 partial + pendingModules」，并加 spec 护栏与负向测试锁死。

⚠️ **groupOnline 冲突清单里有一条规则冲突（C1）**：`shell` 卡第 ⑦ 节
「不输出完整内部计划」与 `groupRound` **硬要求**的 `plans[]`（含 `internalUpdate`）
直接矛盾，若注入可能让群聊整轮不发消息。详见 §4.3。

### 1.2 建议替换结构（不删任何现有函数）

```
btDecide(spec)   // 新增：唯一的参数化实现，spec = {
                 //   scene, contract:{shell:[], scene:[]},
                 //   touchedCards:[], protocolText:string|null,
                 //   injectShell:bool, injectScene:bool
                 // }
  ├─ ⛔ 第 0 步：spec 合法性护栏（见 §1.3，失败即抛，不进决策）
  ├─ ① touchedCards 任一 isOverridden → USER_OVERRIDE
  ├─ ②~⑨ 与现状逐字相同（契约 = contract.shell.concat(contract.scene)）
  ├─ ⑩ protocolText 非 null 时校验其为非空白字符串
  ├─ ⑪★ 按 injectShell / injectScene 决定 shellText / sceneText 是否可用
  │      —— **不允许静默丢弃**：见 §1.4
  └─ 返回 { ok, reason, VERSION, modules, touched, injectShell, injectScene,
            shellText, sceneText, protocolText }

btOnlineDecision()  → 保留为薄包装，传 online spec（**行为逐字不变**）
btOfflineDecision() → 保留为薄包装，传 offline spec（**行为逐字不变**）
```

**为什么不直接删旧函数**：两个现有函数的十步校验已被
`scripts/behavior-offline-migration-test.js` 67 条断言逐条卡住
（含负向回归「then 回调里不得有丢弃式守卫」等）。改成薄包装后，
断言锚点（`var isLatest = (reqId === requestSeq)` 等）仍在，**不需要改测试**。

⚠️ **`BT_C05_ONLINE` 不能进 spec 的必填位**：offline 明确「不接管输出协议」。
spec 里它必须是 `null` 且 ⑩ 步要能跳过 —— 这是两个场景的**刻意差异**，不是遗漏。

### 1.3 spec 合法性护栏（第 0 步，**必须先跑，不通过就抛**）

⚠️ **护栏缺失的后果**：`btDecide` 是唯一入口，一份写错的 spec 会让
**错误正文静默进 system** —— 而 `behavior-text.js` 的十步校验只管
「模块正文本身合不合法」，**管不了「这个模块该不该出现在这个场景」**。
这是本层最容易出静默故障的地方。

| # | 护栏判据 | 失败处理 |
|---|---|---|
| G1 | `spec.scene` 必须是 `behaviorText.planOf` 认识的五个场景之一 | `throw`（**不返回** —— 返回会让调用方误当回退） |
| G2 | `contract.shell` 必须**逐项等于** `['B','P','L']` | `throw` |
| G3 | `contract.shell.concat(contract.scene)` 必须**逐项等于** `planOf(scene)` | `throw` |
| G4 | `contract.scene` 的元素必须**是媒介段**（`E` 或 `N`），不能含 `B/P/L` | `throw` |
| G5 | `protocolText` 只能是 `string` 或 `null`；非 null 时必须非空白 | 走既有 ⑩ 步 `BAD_TEXT` |
| G6 | `touchedCards` 必须是**字符串数组**，元素必须是真实存在的卡 id | `throw` |
| G7 | `injectShell` / `injectScene` 必须是**布尔** | `throw` |

**G2/G3 的意义**：它们把「槽位契约」与「模块自己的 PLANS」**双向钉死**。
现有 ⑨ 步只做了单向校验（`plan` 与 `contractFlat` 比对），
但**没有校验 `contract` 本身写对没有** —— 若有人把 `contract.shell`
误写成 `['B','P']`，`planOf` 仍会返回 5 项、⑨ 步仍会因长度不符而回退（安全）；
但若误写成 `['B','P','L','E']`（长度对、前四项对），**只有 G3 能抓住**。

### 1.4 ⚠️ 禁止「丢弃 sceneText」（用户指出的语义问题 1 的根因）

**现状设计的缺陷**：§2.2 原本让三个新场景「`sceneText` 只记账不注入」，
但诊断会照 `PLANS[scene]` 报出 `['B','P','L','E','S3']` ——
**诊断说 S3 已使用，实际 system 里没有 S3。这是撒谎的诊断。**

**修正后的强制规则**：

```
if (!spec.injectScene) {
  /* 决策仍然成功（shell 位可用），但 modules **只报实际注入的那几段** */
  out.modules = spec.contract.shell.slice();   // 不含 E/S3/N/S5
  out.sceneText = null;                         // 显式置空，不留半套
  out.partial = true;                           // ★ 显式标记「部分接线」
}
```

**判据（写死，不可协商）**：
> `out.modules` 里出现的每一个模块 id，都**必须**真的出现在这一轮的 system 里。
> 反之，system 里出现的每个行为文本模块，**必须**出现在 `out.modules` 里。

**这条判据的负向测试**：注入一个 `injectScene:false` 但让诊断报
`PLANS[scene]` 全量的版本 → 必须被测试抓到。

### 1.5 partial 字段与诊断口径

| 字段 | 含义 | 取值 |
|---|---|---|
| `behaviorUsed` | 本轮 system 里**是否真用了**新正文 | 布尔（`injectShell && ok`） |
| `modules` | **实际注入**的模块（不是 PLANS 全量） | 数组 |
| `partial` | 是否为部分接线 | `true` = scene 位未注入 |
| `pendingModules` | **已知但本批未接通**的模块（诚实记账） | 数组，如 `['E','S3']` |
| `shellCard` | 记账：本次 shell 位读的是新正文还是卡片 | `'behavior'` / `'card'` / `'absent'` |

⚠️ **`pendingModules` 是本批新增的关键字段** —— 它让「未接通」变成
**可查询的事实**而不是沉默的缺口。UI 上应显示
「已接 B/P/L · 未接 E/S3」，而不是假装完整。

## 二、五个场景的 shared shell / scene text / fallback 来源

### 2.1 PLANS 与模块归属（`behavior-text.js` 55-61，原文）

```js
var PLANS = Object.freeze({
  online:       Object.freeze(['B', 'P', 'L', 'E', 'S1']),
  offline:      Object.freeze(['B', 'P', 'L', 'N', 'S2']),
  proactive:    Object.freeze(['B', 'P', 'L', 'E', 'S3']),
  groupOnline:  Object.freeze(['B', 'P', 'L', 'E', 'S4']),
  groupOffline: Object.freeze(['B', 'P', 'L', 'N', 'S5'])
});
```

即：**B/P/L 三个模块五场景全共有**，第四块按媒介分 `E`（消息）/ `N`（现场），
第五块是场景专属（S1 线上应答 / S2 私聊线下 / S3 主动 / S4 群线上 / S5 群线下）。

### 2.2 逐场景归属表（**已按本轮修正更新**）

| 场景 | shared shell（B/P/L） | scene text（E/N + S*） | 第三块（协议，**不由行为文本接管**） | fallback 来源 | 接入力度 |
|---|---|---|---|---|---|
| **online** | `btDec.shellText` | `btDec.sceneText`（E/S1）→ `f1Text` | `BT_C05_ONLINE`（1428） | `cardBody('shell')` / `cardBody('f1')` | **完整** |
| **offline** | `btDec.shellText` | `btDec.sceneText`（N/S2）→ `f2Text` | **无** —— `offlineOutProto` 程序槽负责 | `cardBody('shell')` / `cardBody('f2')` | **完整** |
| **proactive** | `btDec.shellText` | ✅ **注入 `btDec.sceneText`（E/S3）**，位置在 `proactive` 卡**之后** | `proactive` 卡自带 `{"decision":...}` | `cardBody('shell')` / `cardBody('proactive')` | **完整**（本轮修正） |
| **groupOnline** | ❌ **本批不接** | ❌ **本批不接** | `groupRound` 卡自带 plans/messages | 现状不变（无 shell 位） | **未接通**（先做冲突清单） |
| **groupOffline** | `btDec.shellText` | ⚠️ **明确不注入**（`pendingModules: ['N','S5']`） | `[OUTPUT]` 五件套（298-320）自建 | `cardBody('shell')` / `cardBody('f2')` | **部分接线** |

### 2.3 ⚠️ 三处「卡自带协议，场景模块顶不掉」—— 但**可以并列注入**

上一版我写的是「`sceneText` 不注入」，用户指出那会导致**诊断撒谎**。修正后：

**结论：scene 位必须注入，但要放在场景卡之后，并列而非替换。**

| 场景卡 | 自带什么 | 与 scene 位的关系 |
|---|---|---|
| `proactive`(621, locked) | `{"decision":"send\|skip\|defer\|blocked",...}` | **并列**：E/S3 讲「人物为什么想主动、怎么措辞」，`proactive` 卡讲「能不能发、输出什么结构」。**两者同向不冲突** —— S3 第一段就是「不是对新消息作必答回复，而是在程序允许的范围内判断此刻是否想主动联系」，正是 `proactive` 卡的前置条件 |
| `groupRound`(681, locked) | plans/messages 双段 + `forbiddenDisclosures` | **本批不接**（见 §4.3）。S4 与它的「知识边界」「不虚构账号」**语义高度重叠**，注入前必须先看冲突清单 |
| 群线下 `[OUTPUT]`(298-320) | 五件套 + `speaker` 字段 | **本批不注入 N/S5**（S2 二人取向与 S5 群体取向不一致，见 §3.3 勘误） |

⚠️ **注入位置很关键**：`proactive` 的顺序应是
`shell → proactive → sceneText(E/S3) → K01 → I01`，
即 **scene 位在场景卡之后**。若放在 `proactive` 之前，
`proactive` 卡的「【输出结构】」会被 E 模块的「具体结构使用本轮协议」
冲淡 —— 两者都在谈输出结构，顺序会决定谁生效。

## 三、群聊场景的共用边界（明确「哪些能共用、哪些必须群聊自己负责」）

### 3.1 可以共用（B/P/L 三块，shell 位）

| 模块 | 为什么群聊能用 |
|---|---|
| **B** 授权边界 | 「模型看见材料不等于每个人都知道」「user 台词由 user 给出」—— 群聊里**更关键**（多个 NPC 各自知情边界不同） |
| **P** 人物一致性 | 「愿望/自我认识/实际选择可以不同」「不同人不是同一回答的换词版本」—— 正是群像要的 |
| **L** 篇幅 | 第三段已写明「多人场景按全场需要分配篇幅，不按人数平均分配、不逐人凑份额」—— 与群线下 `lengthHintOf` 的「全场加起来的字数」**语义一致** |

**结论：B/P/L 三块是本层唯一真正共用的东西，五个场景零分歧。**

### 3.2 必须由群聊场景层自己负责（不许从行为文本拿）

### 3.3 单人现场叙事与群像的边界（一处需要修正的表述）

⚠️ **勘误（2026-10-04 施工前修正）**：本节上一版写的是
「`N` 是单人专属」+「S2 与 S5 **直接矛盾**」。**两处都不准确**：

**修正一：`N` 不是「单人专属」。**
`N` 的原文是「从**已成立现场中**的话语、动作、注意力与未完成的事情继续。
保持位置、物品、时间先后和已发生变化的连续」—— 它讲的是**现场连续性**，
**没有限定人数**。`PLANS` 也确实把 `N` 同时给了 `offline`（私聊线下）
和 `groupOffline`（群线下）两个场景。所以「N 是单人专属」是错的。

**修正二：S2 与 S5 是「语义张力」，不是「引文已证明的硬矛盾」。**
准确的说法是**两段正文的取向不同**：

| 模块 | 原文里的取向 |
|---|---|
| `S2` | 「当前以线下相处承接 **user 与角色之间**正在发生的交流…不因存在 NPC 就把当前相处变成**每个人轮流表现**」 |
| `S5` | 「以共同现场中正在发生的事情组织叙述，**而不是先为每个人分配一段表现**」 |

两者**都在说「不要轮流表演」**（方向一致），差别在**主语**：
S2 的主语是「user 与角色之间」，S5 的主语是「共同现场」。
所以 S2 的措辞**偏向二人互动**，与 S5 的群体视角**不协调**，
但**没有一句话是互相排斥的**。

**为什么本批仍然不接 N/S5**（结论不变，理由要准确）：
不是「已证明矛盾」，而是**未验证**——
把 S5 与 f2 卡（现含 N/S2）同时注入后，两段取向相近但主语不同的正文
会不会让模型在「共同现场」与「user 与角色」之间摇摆，**本批没有证据**。
要接需先做一次对照观察，属独立一批。

**因此 §2.2 / §4.2 里「S2 与 S5 矛盾」的措辞统一改为
「S2（二人取向）与 S5（群体取向）取向不一致，本批不同时注入」。**

## 四、建议替换结构（逐场景，含文件与行号）

### 4.1 proactive（完整接线，本轮推荐方案）

**文件**：`prompt-engine.js`（spec 表 + 薄包装）、`page-proactive.js:200`
**契约**：`{ shell: ['B','P','L'], scene: ['E','S3'] }` · `injectShell:true, injectScene:true`

现状（`page-proactive.js:200-203` 原文）：
```js
var sys = [PE.cardBody('shell'), PE.cardBody('proactive')];
var k01 = PE.compileCharacter ? PE.compileCharacter(charId) : '';
if (k01) sys.push(k01);
else if (ch && ch.content) sys.push('[CHARACTER]\n' + ch.content + '\n[/CHARACTER]');
```

建议替换为：
```js
/* B/P/L 走共享决策层；E/S3 注入在 proactive 卡**之后**（并列，不替换）——
   proactive 卡自带【输出结构】decision JSON，负责「能不能发 / 怎么发」；
   S3 负责「人物为什么想主动、怎么措辞」。两者同向，顺序不可颠倒
   （E 模块的「具体结构使用本轮协议」若排在 proactive 之前会冲淡它）。 */
var bt = PE.btDecideScene ? PE.btDecideScene('proactive') : null;
var btOk = !!(bt && bt.ok);
var sys = [
  btOk ? bt.shellText : PE.cardBody('shell'),
  PE.cardBody('proactive')
];
if (btOk && bt.sceneText) sys.push(bt.sceneText);
var k01 = PE.compileCharacter ? PE.compileCharacter(charId) : '';
/* ↓ 以下三行原样不动 */
```

**诊断**：`behaviorUsed = btOk` · `modules = ['B','P','L','E','S3']`（= PLANS 全量）
· `partial = false` · `pendingModules = []` · `shellCard = btOk ? 'behavior' : 'card'`

**override 判定**：`touchedCards: ['shell']`
⚠️ **不能**把 `proactive` 算进 touched —— 用户改 `proactive` 卡只该让那张卡回落，
不该把 shell 的 B/P/L 一起拖回退。但用户改 shell 时必须让**整条回退**（保持既有口径）。

**fallback 分两级**（现状是单级）：
- 决策失败 → `cardBody('shell')`（现状行为）
- 决策成功但 `cardBody('proactive')` 为空 → 现状已允许（空串不 push），
  **不要**因为 proactive 卡空就判定决策失败 —— 两者是独立的东西

## 五、诊断信息如何从私聊闭包中抽出（说明，不改代码）

### 5.1 现状

诊断是 `page-offline.js` 的**模块级私有闭包**：

| 位置 | 内容 |
|---|---|
| `page-offline.js:373-384` | `DIAG_STAGE` 枚举 + `DIAG_STAGE_SET` 闭集 |
| `page-offline.js:405-407` | `requestSeq` / `diagSeq` / `diagLast` 三个模块级变量 |
| `page-offline.js:439-444` | `diagNewRequest()` |
| `page-offline.js:446-468` | `diagRecord(requestId, stage, behavior, extra)` |
| `page-offline.js:470-476` | `diagSnapshot()`（深拷贝） |
| `page-offline.js:2311-2320` | `Sleepy.offlineDiag = { snapshot, stageLabel }`（**只读**） |

### 5.2 为什么不能直接复用

1. **它是「私聊线下的出站记账」**，字段含 `requestOk`（该轮 HTTP 结论）、
   `at`（时间戳）—— 这些对 proactive/groupOnline **语义不同**
   （群线上一次 `composeRound` 只发一次请求，但**调度出多个本体**）。
2. 它在 `page-offline.js` 的 **IIFE 闭包内**（23-2318 行），
   别的文件**在语法上就拿不到**那些函数。
3. 已有的 `smoke.js` 护栏「线下诊断导出面：没有写入/重置入口」
   卡的就是 `Sleepy.offlineDiag` 的导出面 —— **改成共享模块会动这条护栏**。

### 5.3 建议的抽出方式（三步，**本批不做**）

**第一步：提出「行为决策诊断」子集（与出站诊断分离）**

共享决策层只需要回答「**这一轮用了什么行为正文**」，不需要回答
「HTTP 成功了吗」。所以建议**两个诊断不要合并**：

```js
/* 建议新增：Sleepy.behaviorDiag（只读 + 决策层自己写） */
{
  at: '2026-10-04T...',        // ISO 时间
  scene: 'proactive',          // 五个场景之一
  behaviorUsed: true,          // 本轮 system 里**真的**有行为文本正文
  reason: '',                  // '' = 成功；否则 BT_REASON 的键
  touched: false,              // 是否因用户 override 整条回退
  version: 'sleepy-behavior-v1-review-01',
  modules: ['B','P','L','E','S3'],   // ★ **实际注入**的，不是 PLANS 全量
  pendingModules: [],                // ★ 已知但本批未接通（如 groupOffline 的 ['N','S5']）
  partial: false,                    // ★ true = 部分接线（pendingModules 非空）
  shellCard: 'behavior'              // 'behavior' | 'card' | 'absent'
}
```

⚠️ **三个新字段的必要性**（缺了任一个都会产生误导）：

| 字段 | 缺了会怎样 |
|---|---|
| `modules` 只报实际注入 | **诊断撒谎** —— 报 S3/E 已用但 system 里没有（用户本轮指出的问题 1） |
| `pendingModules` | 「未接通」是沉默的缺口，UI 无法显示「已接 B/P/L · 未接 N/S5」 |
| `partial` | 无法一眼区分「完整接线」与「部分接线」 |
| `shellCard` | `modules` 都是 `['B','P','L']` 时**无法区分「决策成功」与「失败回落同一张卡」** |

**字段校验口径**（沿用现有闭集，不放宽）：
- `scene` 必须是五个 PLANS 键之一
- `behaviorUsed` / `partial` 必须是布尔
- `reason` 必须是 `BT_REASON`（prompt-engine.js:90-102，11 个键）的值之一
- `version` 未知时用**固定未知串**，不回显任意原串
- `modules` 必须是 `PLANS[scene]` 的**子集且同序**
- `pendingModules` 必须与 `modules` **不相交**，且并集恰好等于 `PLANS[scene]`
  （⚠️ 这一条是「不许静默丢弃模块」的形式化保证）
- `shellCard` 必须是三个闭集值之一

**第二步：不动 `page-offline.js` 的现有闭包**

现有 `Sleepy.offlineDiag` 一行不改（其 `requestOk` / `seq` 语义是私聊线下专属）。
共享层**另开**一个 `Sleepy.behaviorDiag`，两者并存。
`offline` 场景在接线时**同时**写两份（出站诊断 + 行为决策诊断），
或者更省事：**`offline` 场景的决策诊断由 `page-offline.js` 自己写**，
共享层只服务另外三个场景 —— **这样 `page-offline.js` 一行不动**。

**第三步：UI**

诊断面板目前在 `page-offline.js` 的设置 sheet 里（第三个页签）。
另三个场景要看到诊断，需要**独立的查看入口**（各自的设置 sheet）
或**一个全局诊断页**。这是**独立一批**，不应与接线混做。

### 5.4 闭集校验的现成先例

`DIAG_STAGE_SET`（`page-offline.js:384`）已经实现了「枚举 + 闭集校验 + 未知值不
回显原串」的模式 —— `behaviorDiag` 的 `reason` / `partial` / `shellCard`
三处**照搬同一写法**即可，不要另创一套。

⚠️ **不要把 `behaviorDiag` 的闭集校验写成 `typeof x === 'string'`** ——
「是字符串」不等于「是合法值」。这一点与 `page-offline.js` 导出面收口时
修掉的旧问题同类。
