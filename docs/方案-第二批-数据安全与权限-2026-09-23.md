> 性质：**只给证据与最小施工方案，本轮一行代码都不改**（用户要求「先给证据和复现，再最小修改」）。

## 项目 1｜清空 / 导入与向量库一致

### 证据（现状）

| 事实 | 证据 |
|---|---|
| 向量库是另一个存储层：IndexedDB `sleepy-vec`（版本 5，store 名 `vec`） | `memory-vec.js:49`、`:63`、`:138 open()` |
| 「清空全部数据」只清 localStorage + 图库，**完全没碰向量库** | `page-backup.js:170`（`store.clearAll()`）、`:173-174`（`Sleepy.media.clear()`）；该文件 grep `memoryVec` / `vec` / `indexedDB` = **0 命中** |
| 导入只做 `store.importAll` 然后 reload，也不碰向量库 | `page-backup.js:65`、`:68` |
| `store.clearAll()` 只扫 `sleepy.v1.` 前缀 | `store.js:472-487` |
| 现成的清库入口只清**一个大脑**，**没有全库入口** | `memory-vec.js:481 clearAll(charId)` → `:408 allOfRoot(charId)` |
| 「全库」是可枚举的（说明能实现全清） | `memory-vec.js:429 total()` 用 cursor 遍历整个 object store |
| 已有「清旧模型块 + 作废游标」的先例可照抄 | `memory-vec.js:461 forgetStale()` → `:814 resetCursors()` |
| 游标 / 退避键在 localStorage，清库后必须一并处理 | `memory-vec.js:749 cursorKey`（`vecCursor3:`）、`:756 backoffKey`（`vecFail:`）、`:813 epochNow` |
| 残留块**不会**被「源已不存在」挡掉（chat/offline/group 无回源复核） | `memory-vec.js:339` `if (kind === 'chat' \|\| 'offline' \|\| 'group') return true;` |

### 复现方法

- **node 能做的（接线层）**：node 里没有 `indexedDB` → `available()`（`memory-vec.js:176`）返回 false，冒烟已有这条断言 → **"清干净没清干净"在 node 里验不了**。
- **只能真机**：DevTools → Application → IndexedDB → `sleepy-vec`，记下条数 → 设置→数据与备份→清除全部数据 → 条数**现在不为 0**（应改为 0）。
- 导入路径：备份 → 继续聊几句（产生新块）→ 导入旧备份 → 旧块仍可被召回（幻觉源 + 隐私残留）。

### 最小施工方案

1. `memory-vec.js` 新增 **`wipeAll()`**（照 `forgetStale` 的 cursor 写法）：
   删 store 里全部块 → `resetCursors()`（作废所有游标）→ 清 `vecFail:*` 退避键。
   `supported` / IDB 不可用时**安静返回 0、不抛**（node 与老浏览器安全）。
2. 导出到 `Sleepy.memoryVec`（`wipeAll`）。
3. `page-backup.js` 两处调用：清空路径（`:170` 之后）、导入成功后（`:65-68` 的 reload 之前）。
   失败只 warn、不阻断（别让"清一半"卡死流程）。
4. 文案：`:79` 那句「图片不在里面」补一句「向量索引也不在备份里；清空/导入会一并清掉索引」。

### 回归测试方案（含反向验证）

- `t('wipeAll 在无 IndexedDB 环境安静返回 0 且作废游标')` —— node 里可**真验**：
  调 `S.memoryVec.wipeAll()` → 断言不抛、返回 0、且 `vecEpoch`（localStorage）**+1**。
- 静态护栏 `ok()`：`page-backup.js` 必须含 `wipeAll`，且清空/导入两条路径各有一处调用。
- 反向验证：删掉其中一处调用 → 护栏变红。
- **只能真机**：块数真的归零（这条我会在文档里标死，不拿接线测试冒充）。

## 项目 2｜记忆开关同步控制 L0 / L4 建块 / L4 召回

### 证据（现状）

| 事实 | 证据 |
|---|---|
| 开关存在 `memoryIsland.byChar[charId].enabled`，**按 charId** | `page-memory.js:88-100 charConfig()`、`:101 store.set('memoryIsland', raw)`、`:102 setCharConfig()` |
| 默认值：主角开、NPC 关 | `page-memory.js:94` |
| 目前**只有一个**读取方：L0 注入 | `page-memory.js:380-381`（`if (!cfg.enabled) return ''`）、`:154`（UI 展示） |
| L4 完全不知道这个开关 | `memory-vec.js` grep `memoryIsland` / `charConfig` = **0 命中** |
| L4 建块入口共 7 个，前置只有全局 `enabled()` | `memory-vec.js:enabled()`（看 `vecCfg.enabled` + 有没有配向量接口）；`sweepSource` + `sweep/sweepOffline/sweepGroup/sweepMoments/sweepDiary/sweepMem/sweepPhone` |
| L4 召回入口 | `memory-vec.js:355 blocksOf(charId,userId,snap)` → `:347 poolsFor` |
| 私聊调用点传的是**皮套** id | `page-chat.js:2391 prefetch(c0.characterId,…)`、`:2428 sweep(c.characterId,…)` |

### 交叉发现（与项目 5 同源，很重要）

开关按 `charId` 存，但：私聊传**皮套**（`page-summary.js:253`）、留痕 UI 传**大号**（`page-memory.js:170 charsOfSandbox`）。
→ **在留痕里关掉某角色，对「该角色皮套的私聊」的 L0 注入很可能根本不生效**（写的是大号的配置，读的是皮套的配置）。
→ 所以项目 2 的实现**必须**先和项目 5 的归属口径对齐（见下方依赖）。

### 最小施工方案（口径③：关 = 不注入 + 不召回 + 不建块）

1. `memory-vec.js` 加纯函数 `charMemOff(charId)`：`Sleepy.memoryStore.charConfig(<归一后的 charId>).enabled === false`；拿不到 memoryStore 时返回 false（保持旧行为，不误伤）。
2. **建块侧**：`sweepSource` 与 4 个素材 sweep 入口各加一道 `charMemOff` → 关则 `{ok:false, why:'off'}`，**不调 embedding**。
3. **召回侧**：`blocksOf` 开头判 `charMemOff` → 直接返回空（K03c 拿不到东西）。
4. **重开补扫**：开关 `false→true` 跳变时喊 `memoryVec.resetCursors()` + `sweepMem(charId)`（游标作废 → 历史内容自然补扫）。

### 依赖与需拍板

- **依赖项目 5 的归属选择**：归一用 root 还是皮套。若选 root，则"关掉大号"会同时关掉它所有皮套的 L4（与"记忆共享同一个大脑"一致，但和"皮套是不同人设"的直觉冲突）。
- 需拍板：**开关作用域 = root（整个大脑）还是 charId（单张脸）？**

### 回归测试方案

- 纯函数打表：`charMemOff` 在开/关/无配置三种输入下的返回值。
- 注入假 `memoryStore.charConfig` → 断言 `blocksOf` 返回空、sweep 入口不进入 `embedTexts`。
- 反向验证：去掉任一闸 → 断言变红。
- **只能真机**：真配 embedding 后确认"关掉期间不产生新块"。

## 项目 5｜验证 `loadCharMemory` 用 rootId 还是皮套 charId

### 证据（结论：**归属不一致**）

| 路径 | 传进去的是谁 | 证据 |
|---|---|---|
| 实现 | **不做任何归一**，直接 `'charMem:' + charId` | `page-memory.js:120 loadCharMemory` → `:103 charMemKey` |
| 私聊总结 | **皮套**（`chat.characterId` = 哪张脸） | `page-summary.js:253 var charId = chat.characterId;` → `:303 ingest(charId,…)` → `:57 loadCharMemory(charId)` |
| 群 / 群线下总结 | **rootId**（ownerId） | `page-group-offline.js:1946 ingest(oid,…)`；`oid` 来自成员表，`core-group.js:149/256` 写的就是 `rootIdOf(accountId)`；该文件 `:1832` 注释亦写 `charMem:<ownerId>` |
| 留痕 UI | **大号**（+ 岛内 NPC） | `page-memory.js:170 charsOfSandbox(sb)` → `:140 pushChar(c)` |
| K03 注入 | **皮套**（当前对话的脸） | `page-switch.js:409 compileMemory(charId,…)` → `:417 getMemoryInjection(charId)`；`prompt-engine.js:862` 由对话上下文给 charId |
| 向量 · 读 | **皮套** | `memory-vec.js:280-283 buildSnapshot` |
| 向量 · 写 | **大号**（只有留痕会调） | `memory-vec.js:1096-1100 sweepMem(charId)` ← `page-memory.js:229/457`；ownerKey 用 `rootOf`（`:1095` 注释） |
| 群线下读取记忆库 | **root** | `page-group-offline.js:1882 gmExistingBlocks(ownerIds)` |

**后果**（都可复现）：
1. 皮套私聊整理出的记忆写进 `charMem:<皮套>` → **留痕里看不到**（列表只列大号）、**向量里没有**（sweepMem 只被留痕调、传大号）、**开关设不到**（charConfig 按 charId，留痕设的是大号）→ 用户视角就像"记忆丢了"。
2. 同一角色在私聊与群线下**各长一套库**，模型看到哪套取决于场景 → 记忆分裂。
3. `core.js` 的旧 `memories` 体系是按 `rootId` 归一的（`memoriesOfRoot` → `rootIdOf`，`core.js:961-969`）→ 与 charMem **口径相反**，两套记忆体系对"归属"的定义不一致。

### 复现（node 可做，只读不改行为）——**已落地**

`t('探针：charMem 归属 —— 皮套与 root 落在两个不同的键上')`
见 `scripts/smoke.js:6241-6288`（「第二批证据探针」段，48 行）。做法：
建 大号 + 皮套 → 走**真实写入口** `memoryStore.addMemoryItem(皮套)` 与 `(大号)` →
断言：① 两个 charId 落在**两个不同的键**上；② 留痕列表（`loadIsland().chars`）里**只有大号**、
皮套不可见；③ L0 注入（`getMemoryInjection`）按 charId 分裂，各看各的。
finally 里删掉两个 `charMem:` 键并拆岛，不留痕。

**实跑结果**：`{"两键独立":true,"皮套留痕不可见":true,"注入按皮套分裂":true}` ——
现状（归属不一致）已从「读代码推断」升级为「可执行断言」。

### 最小施工方案（两条，需拍板选一）

- **方案 A（推荐）**：`loadCharMemory` 内部**归一到 root**（`charId = core.rootIdOf(charId) || charId`），
  条目里保留"哪张脸写的"印记（`fromCharId`）以便按脸剔除。
  代价：需要**一次性迁移** —— 把现存 `charMem:<皮套>` 合并进 `charMem:<root>`（保留条目 id 去重）。
  好处：所有调用方自动一致，开关/向量/留痕一次对齐。
- **方案 B**：保留多键，所有**读取方**改成"枚举 root + 它的皮套并合并"（新增 `loadCharMemoryAll(rootId)`）。
  代价：不改存量数据，但每个读取点都要改（现在至少 6 处），**容易再漏**；写路径仍需决定写哪把键。

### 依赖

- 项目 2（开关作用域）依赖这里的 A/B 选择 —— 建议**先定 A/B，再做项目 2**。
