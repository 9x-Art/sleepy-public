## 二、weProposals 最终数据结构

```js
{
  id: 'wep-<ts36>-<rand>',
  sandboxId,                 // chat 记录自身的岛（tagScope 语义显式盖章，不读全局指针）
  refCharId, refUserId,      // chat.characterId / chat.userId
  status: 'pending' | 'accepted' | 'declined',
  title,                     // 真实事件 title（程序复核覆盖，模型自报值不采信）
  note,                      // char 的提议理由（≤60 字，超长整个丢弃）
  kind,                      // WE_KINDS 白名单内
  at,                        // 事件 startAt（原样，详情 fmtFull 可解析）
  sourceType: 'calendar',    // 本轮唯一开放来源
  sourceId, sourceRef,       // sourceRef = startAt 前 10 位（ISO 日）
  proposedBy: 'char',
  proposedAt,
  originMessageId,           // 产生提议的 assistant 消息 id（reroll 复用同 id → 天然防重）
  originChatId,
  dedupeKey,                 // sandboxId|refCharId|sourceType|sourceId
  resolvedBy,                // 'user'（accept/decline 时写）
  resolvedAt,
  acceptedEntryId            // accept 成功后回写正式 weEntries 的 id
}
```

`page-we-proposal.js` 导出（L288-303）：`KEY / SOURCE_TYPE / REASON_MAX / DECLINE_COOLDOWN_MS / MAX_PENDING_PER_CHAR / extractTag / dedupeKey / validateSource / candidatesOf / createFromReply / listPending / countPending / findInScope / accept / decline`。

## 三、标签协议最终格式

```
[收藏提议:calendarEventId|kind|理由]
```

- 全角半角冒号都认；一条回复最多认**第一个**；三个字段都允许空位（正则 `([^|\]\n]*)`）——**空字段的标签照样从正文剥干净，但提议整个丢弃**（smoke 抓到过「字段缺失时标签残留正文」的 bug，已修：page-we-proposal.js TAG_RE）。
- 模型只许带这三个字段；sandboxId / refCharId / refUserId / title / at / sourceRef / originMessageId / dedupeKey 全部程序生成。
- 说明书槽（prompt-engine `compileWeProposal`）只在当前岛存在可提议事件时注入，且把**真实事件 id 清单**列成闭集——模型只能从里面挑，从源头压伪造。理由 >60 字 / kind 不在白名单 → 静默丢弃，聊天回复不受影响。
- 标签在正文落盘前抽取（onDone L2810）；模型若把标签写进 `[WHISPER]` 心声，也在 L2815 剥掉并并入提议；`stopReply` 半截回复同链路（L2954/2976）。**气泡正文、历史正文、心声三处都不会出现标签文本**（P2 真机断言验证）。

## 四、source fail-closed 逻辑（validateSource，page-we-proposal.js:135-158）

按序校验，任何一条不过即拒，**不影响聊天回复本身**：
1. `calendar.getEvent(sourceId)` 拿不到 → `deleted`
2. `status === 'cancelled'` → `cancelled`（**completed 放行** —— 有效历史来源，语义同 P1 修正轮的 checkSource）
3. `eventType !== 'char_schedule'` → `type`
4. `ownerCharId !== chat.characterId` → `char`（跨角色）
5. `ev.sandboxId !== chat.sandboxId` → `scope`（跨岛）
- title / at / sourceRef 一律取真实事件字段。

## 五、accept 幂等实现（page-we-proposal.js:216-257）

1. 只吃 `status === 'pending'`；`acceptedEntryId` 已存在 → `{ok:false, why:'already-accepted', entryId}`（**不生成第二条 weEntries**）；
2. **确认前重新核验来源**：已取消/已删除 → 拒绝入馆、**保留 pending**，把 why 交回 UI（聊天卡与确认页都 toast「这条约定已经不在了，提议先留着」——绝不静默变成正式藏品）；
3. 通过 `weStore.add({... createdBy:'char', confirmedBy:'user', confirmedAt:Date.now()}, proposal.sandboxId)` 复制生成正式记录；
4. 写回 proposal：`status:'accepted' / resolvedBy:'user' / resolvedAt / acceptedEntryId`。
decline：只改状态 + resolvedBy/resolvedAt，不生成 weEntries，不触发 char 任何消息；declined 记录保留做去重（冷却 7 天，`DECLINE_COOLDOWN_MS`），本轮不做清理。

去重五闸（`createFromReply`，L170-225）：同 originMessageId → `dup-message`；同 dedupeKey 已 pending → `dup-pending`；已 accepted → `dup-accepted`；declined 冷却期内 → `cooldown`；同 char pending ≥ 1 → `pending-limit`（不同 char 各自可有一条）。

## 七、发现的风险与未实现内容

1. **排序 NaN 防御（本轮顺手修的最小修复）**：char 提议入馆的 `at` 继承事件 `startAt`（日期字符串），门厅 `entries()` 原来的 `b.at - a.at` 会得到 NaN（排序结果依赖实现）。已在 `page-collection.js:167-176` 归一（解析不出当 0 保持原序），未改任何其他排序语义。
2. **weEntries 契约变化**：正式记录新增可选 `createdBy:'char' / confirmedBy / confirmedAt` 字段。消费点排查过：详情展示（L353）已适配，门厅计数/checkSource/导出不受影响。
3. **declined 冷却 7 天**是本轮拍板缺省（拍板只说「冷却期内拦截」，没定量）；改常量 `DECLINE_COOLDOWN_MS` 即可。
4. **prompt-engine 旧组装路径（引擎关闭兜底）未注入收藏提议说明书** —— 引擎默认开启，未覆盖旧路径；若有人关引擎，标签不会出现（安全侧失败）。
5. **群聊 / 线下 / 朋友圈不在本轮**（拍板明确排除）；`sourceType` 只开放 calendar，其余来源在 validateSource 前就被 `SOURCE_TYPE` 常量 + kind 白名单挡住。
6. **测试种子 bug（非生产，已澄清）**：bug 只在本轮 P2 测试初版——`u` 取了 `.id` 字符串后又写 `[u.id]`（→ `[undefined]`，maskIds 落空 → chat.userId 为 null → 提议被 fail-closed 正确拒绝）。**首轮 `browser-collection-test.js` 的 `seedIsland` 没有这个 bug**（那里的 `u` 是 upsertUser 返回的对象，`[u.id]` 本来就正确）——初版回交误记，已更正；P1 复跑 20/20 确认。
7. **未做**（拍板排除）：双方留言、搜索、来源跳转、DIY、自动搬运历史、实体卡片视觉统一、declined 自动清理。
