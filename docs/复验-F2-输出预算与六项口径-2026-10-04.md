## 一、只读核对：`maxTokens` 能否完整传到最终 HTTP body

**结论：传递正常，三档全部原样落地，运行时零裁剪 → 不改生产代码。**

### 三档实测（抓 `window.fetch` 的最终 body）

| 配置 | 期望 | 最终 HTTP body 里的 `max_tokens` | 一致 |
|---|---|---|---|
| 留空（用内置默认） | 1024 | **1024** | ✅ |
| 用户设 4096 | 4096 | **4096** | ✅ |
| 用户设 32768（UI 上限） | 32768 | **32768** | ✅ |

body 顶层字段恒为 `["max_tokens","messages","model","stream","temperature"]`。

证据：`docs/证据-maxTokens传递核对-2026-10-04.json`

### 四个环节的确切位置与原文

**① 配置入口** — `page-settings.js:484`

```js
f.maxTokens = numField({ label: '单次回复上限', hint: '留空＝用内置默认',
  value: preset.maxTokens, min: 64, max: 32768, step: 64 });
f.maxTokens.input.placeholder = String(def.maxTokens);
```

落库：`page-settings.js:548` → `maxTokens: f.maxTokens.getNum()`。
留空语义：`ui.js:192` `getNum()` —— **空输入回 `null`（不是 0）**，
注释里记着「0 在 `api.genParams` 里是有效值，会真的发出去一个 `max_tokens: 0`」。

**② 场景层是否另有覆盖** — `page-offline.js:319`（`callModel`）

```js
return Sleepy.api.requestOnce(cand, messages, {}).then(function (res) {
```

⚠️ **第三个参数 `ov` 传的是空对象 `{}`** ——
**线下场景层没有任何覆盖**，`maxTokens` 完全由接口配置决定。
（对照：`page-singleapi.js:254` 的连通性测试传了 `{ maxTokens: 8 }`，
证明 `ov` 通道本身是通的，只是线下没用。）

**③ 传递位置** — `api.js:51-76`（`genParams`）

```js
function pick(key, fallback) {
  if (ov[key] !== null && ov[key] !== undefined) return ov[key];
  if (cfg[key] !== null && cfg[key] !== undefined) return cfg[key];
  if (def[key] !== null && def[key] !== undefined) return def[key];
  return fallback;
}
...
maxTokens: pick('maxTokens', GEN_DEFAULTS.maxTokens),
```

三层回落：对话级覆盖 > 单接口配置 > 聊天默认值 > 内置默认。
**`maxTokens` 没有任何 `Math.min` / `Math.max` 裁剪**
（与 `timeoutSec` 不同 —— 那个有 `if (!(tout >= 60)) tout = GEN_DEFAULTS.timeoutSec` 的强制下限）。

**④ 最终构建位置** — `api.js:119-128`（`bodyFor`，全库唯一请求体构造点）

```js
function bodyFor(cfg, messages, stream, ov) {
  var p = genParams(cfg, ov);
  return JSON.stringify({
    model: cfg.model, messages: messages, stream: !!stream,
    max_tokens: p.maxTokens, temperature: p.temperature
  });
}
```

`requestOnce` 在 `api.js:172` 调用它（`bodyFor(cand.cfg, messages, false, ov)`）。

### UI 上限是唯一的「上限」，且在客户端

`page-settings.js:484` 的 `max: 32768` 只是输入框的 `max` 属性
（`numField` 会据此约束输入），**不是运行时的裁剪**。
换句话说：**32768 以内，用户填什么就发什么。**

## 三、六项口径（**修正了此前的矛盾**）

| 口径 | 数量 |
|---|---|
| 总请求数 | **10** |
| 请求成功数（HTTP 200） | **10** |
| 非空内容数 | **7** |
| 解析成功数 | **7** |
| 可用角色回复数 | **7** |
| 降级提示数 | **0** |

**校验自洽**：7 + 3 = 10 ✅

### 四类失败分开登记

| 分类 | 数量 | 说明 |
|---|---|---|
| **权限不可用（403）** | **0** | 上一轮是 4 次 —— 本轮端点已恢复，**不计为提示词效果失败** |
| **超时** | **0** | 上一轮 1 次（120s） |
| **预算截断** | **3** | HTTP 200 + `finish_reason:length` + `content` 长度 0（推理吃满预算） |
| **非空但解析失败** | **0** | 上一轮 3 次（裸 JSON 进正文）—— **P0 降级已生效，本轮 0 次** |
| 网络失败 | 0 | |

### 此前矛盾的成因（我自己的两个错）

**① 「10/10 落地」把降级记录算成了落地。**
降级轮确实 `append` 了消息（`parseFailed` 记录），但它**不是可用的角色回复**。

**② 第二次栽在同一个 14 字坑。**
六项口径的「输出」列在**降级轮**里装的是折叠区那句
`（本次没有可查看的原始内容）` —— **正好 14 字**。
第一版口径按「输出不以 `{` 开头」判有内容，于是 3 个失败轮被算成成功
（曾报出「解析成功 10 / 可用回复 10」这种内部矛盾的数字）。

修正：**唯一可信判据是原始请求结果里 `content` 的长度**（`raw.len`），
并显式排除那句空提示文案。

> 这和上一批「长度 14 → 14」是**同一个坑** —— 我在两处不同批次里都踩了它。
> 记入长期约定：判「有内容」必须用**上游原始长度**，
> 不要用下游展示文本（降级文案、固定提示都会伪装成内容）。

### 有效样本的定性观察（**7 轮，单次输出，不是普遍结论**）

| 组 | 观察 |
|---|---|
| 1 人格与连贯性 | 保持材料/尺寸语言（阁楼、木板、铁皮雨棚），未滑向通用体贴人设；未替 user 安排台词 |
| 2 连续三轮 | 轮 1/轮 3 各有独立描写（窗扣、A3 方格纸、方格纸被吹歪），**未见复读**；轮 2 降级 |
| 3 平淡回应 | 轮 1「我没事」→ 只写「沈砚在门口停了一下，手还搭在门把上。看了过来，两秒。」—— **未见「逞强/嘴硬/需要安慰」类解读** |
| 4 正常收束 | 两轮收在具体动作（「嗯。应该是今年的新白茶。」），**未见问句式收尾或关系升华** |
| 5 NPC | 轮 2 老板娘**保持在楼下**（应了一声 + 杯子碰碟子响 + 没脚步声），未无故上楼；沈砚未替 NPC 表态 |

⚠️ **轮 2 的「我没事」组**因预算截断无有效输出；
**组 5 轮 1** 同理。样本量因此不足，**不宣布 F2 效果达标**。
