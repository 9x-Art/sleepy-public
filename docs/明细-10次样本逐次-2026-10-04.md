## 二、那 3 次空正文：是不是都「预算耗尽」？

### 3 次空正文的直接观测

| 轮次 | content 长度 | 耗时 | 诊断 requestOk |
|---|---|---|---|
| 3-2 | **0** | 26231 ms | `true`（**HTTP 200**，不是失败） |
| 4-2 | **0** | 65883 ms | `true` |
| 5-1 | **0** | 24060 ms | `true` |

### 能确定的三件事

1. **服务端返回了 HTTP 200**，不是网络失败、不是超时、不是 403。
2. **`message.content` 是空字符串**（长度 0）—— 空的是**正文**，不是整个响应
   （`api.js:172` 的 `requestOnce` 会把 `content || ''` 交给 `parseOfflineReply`）。
3. `parseOfflineReply('')` 走 `if (!text)` 分支返回 `{ok:false, paras:[]}` →
   **正确触发降级**（不是崩溃、不是伪称成功）。

### 不能确定的那一件事

**「预算被推理吃满」这个具体归因，这批数据证明不了** ——
需要 `finish_reason`（是否 `"length"`）与 `usage`（是否
`completion_thinking_tokens` 吃满 `max_tokens`），**两个字段都没记**。

### 但有**间接证据**指向同一方向

来自**上一批（maxTokens=1024）**的 `window.fetch` 原始抓取
（`docs/证据-空返回链路-原始抓取-2026-10-04.json`），那次**记全了**：

```
HTTP 200
choices[0].finish_reason : "length"        ← 输出被截断

choices[0].message.reasoning_content : 长度 4044
usage.completion_thinking_tokens : 1020
usage.completion_tokens          : 1024    ← 等于 max_tokens
```

**这是「预算耗尽」的教科书式形态**：1024 全部消耗在推理上，正文 0 空间。

### 但本批有个**反证**，必须如实指出

**3-2 只耗时 26 秒**。而 1024 那次截断耗时 **59 秒**。
若同样是「思考吃满 8192」，26 秒内烧完 8192 token 推理不太合常理
（1024 烧完要 59 秒）。

→ **3 次空正文的成因在本批可能不止一种**，「都由预算耗尽造成」**不能确认**。
可能包括：思考提前结束但正文为空、端点侧其它截断、或其它未记录的原因。

## 三、顺带纠正：上一份报告的「降级提示数 = 0」是**错的**
