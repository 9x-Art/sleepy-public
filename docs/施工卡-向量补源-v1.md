# 施工卡 · 向量记忆补源（朋友圈 / 日记 / 记忆档案 / 查手机）· v1

> 日期 2026-09-23，基线 v114。前置：`docs/方案-向量记忆-v1.md`（§2 定了「哪些进」）。
> 本卡只解决「**怎么接进去**」—— 加源必须照 `memory-vec.js` 的既有契约来，**不许自造第二套**。

---

## 0. 一句话

向量库里现在**只有对话**（线上私聊 / 线下私聊 / 群聊 / 群线下）。
本批把**朋友圈 / 日记 / 记忆档案 / 查手机（TA 自己的内容）**四类接进去，
让角色能按语义回忆起「你发过的那条动态」「你自己写的那篇日记」「我们约定过的事」。

## 1. 接口契约（读自 `memory-vec.js:593`，加源的唯一入口）

```js
sweepSource({
  ownerKey,      // 召回主键。四个新源一律 = rootOf(charId)（挂到「这个角色的大脑」）
  kind,          // 新增值：'moment' / 'diary' / 'mem' / 'phone'
  cursorId,      // 游标键，每个源唯一且稳定
  messages,      // ★ 必须按时间【正序】的条目数组，每条要有 .id 和 .timestamp
  charId, userId, sourceId,
  lineOf,        // 条目 → 一行文本（返回 '' 表示跳过这条）
  blocker,       // ★ 新增参数（见 §3.1）
})
```

块记录（`sweepSource` 内部构造，字段不用改）：
`{id, ownerKey, kind, charId, userId, groupId, sourceId, sandboxId, at, at0, model, dim, fromId, toId, msgCount, msgIds, text, vec}`

## 2. 加源必须遵守的三条硬约束（读代码得出的，不是猜）

### 2.1 切块器要换 —— `nextBlock` 的 8～12 条规则**只适合对话**

`nextBlock`（`memory-vec.js:422`）的规则是「8～12 条 或 600～1000 字合并成一块」。
朋友圈一条动态、日记一篇、档案一条、订单一条 —— **都该一条一块**；合并会串味
（三条不相干的动态拼成一块，召回来是四不像）。

→ **给 `sweepSource` 加 `src.blocker`**（默认 `nextBlock`），并新增 `blockerOne`（一条一块）。

### 2.2 数组必须是时间正序 —— 游标按「位置 + lastId」走

`readCursor`（`:545`）用 `indexOfId(msgs, cur.lastId)` 找回位置再 +1。
源数据若是**倒序**（新→旧），新数据会插在数组前面 → **游标全乱、内容重复索引**。

⚠️ **实测**：phone 的 `listNotes/listBrowser/listShop/listFavs/listCart/listHealth`
（`phone.js:823-849`）**全部倒序**；`moments.all()`（`page-moments.js:44`）与
`diaries`（`page-diary.js:87`）是追加序（≈正序）。
→ **一律自己 sort 成时间正序再喂。**

### 2.3 屏障语义 —— `visibleTo` 只认「同 charId + 同 userId」

`visibleTo`（`:182`）在有认知屏障时，只认 `b.charId === charId && b.userId === userId` 的块。
→ **写块时必须带正确的 `charId` / `userId`**，否则有屏障的身份**一条都召不回**。

## 3. 要改的公共部分（三处）

### 3.1 `sweepSource` 参数化切块器（小改）

```js
var blk = (src.blocker || nextBlock)(msgs, from, src.lineOf);
```
+ 新增 `blockerOne(messages, from, lineOf)`：取 `messages[from]` 一条成块（lineOf 返回空则跳过）。

### 3.2 回源复核（`blocksOf` 的 filter 加一层）

`blocksOf`（`:188`）现在的 filter 是 `visibleTo(...) && sameModel(b)`。
**但权限是会变的** —— 用户能改「不让 TA 看我的动态」、能关掉日记授权、能删档案。
**写块时可见 ≠ 现在可见。**

→ 加一个**同步**的 `stillVisible(b)`（store 读是同步的，不用改异步结构）：
按 `b.kind` 回源查「这条原始数据还在不在、还有没有权限」：

| kind | 回源复核 |
|---|---|
| `moment` | 原动态还在（`status !== 'deleted'`）**且** `canCharSee(m, b.charId, b.userId)` |
| `diary` | 还在，且（`author==='char'` 比 charId ／ `author==='user'` 比 `diaryShared`） |
| `mem` | `charMem:<charId>` 里还在，且 `status === 'active'` |
| `phone` | 源头还在（TA 自己的内容，无权限概念） |
| `chat` / `offline` / `group` | **不查**（保持现状 —— 那些的可见性由 `visibleTo` + 群成员过滤负责） |

### 3.3 配额要分池（否则对话块会被挤光）

现在是「**500 块 / 大脑**，超了丢最老的」（`trim` `:717` 按 ownerKey）。
四个源进来后块数大涨 —— 按时间淘汰会让**长期的档案 / 日记被近期对话块挤掉**
（而档案恰恰是最该留的）。

→ 建议**按 kind 分池**：`chat/offline/group` 一个池、`mem/diary/moment/phone` 另一个池，
各自 `trim`。比例待拍板（§5.1）。

## 4. 四个源逐个

### 4.1 朋友圈（`kind:'moment'`）

- **源**：`moments`（`page-moments.js:44 all()`）；
  单条 `{id, characterId, name, text, at, likes[], comments[], maskId?, mediaId?, privacy?, visibleTo?}`
- **可见性（复用，别另写）**：`canCharSee(m, charId, userId)`（`page-moments.js:129-146`）
  ⚠️ **挡角色看的只有两个字段**：`iHideFromChar`（**我**对 TA 隐身）+ `charHidesFromMe`（**TA** 不看我的）。
  `iHideChar` / `charHidesMe` 是**反方向**（影响 user 看 TA 的）—— **方向写反 = 隐私事故**
  （冒烟 `scripts/smoke.js:6185-6191` 专门守着这条）。
- **切块**：**一个动态事件包一块**（正文 + 评论/点赞各一行）
- **ownerKey**：`rootOf(charId)`；`charId` = **看的人**，`userId` = 动态主人（maskId/userId）
- ⏳ **要绕开的**：`listForChar`（`:151`）带「10 天 / 12 条」窗口 —— 那是给**实时注入**用的。
  建索引必须**全量**（否则三个月前的动态永远进不了库）→ 自己遍历 `all()` + `canCharSee`。
- **forget 联动**：`remove(momentId)`（`:347`）、`removeComment`（`:332`）→ 按 sourceId 失效
- **写入时机**：发动态 / 删动态后

### 4.2 日记（`kind:'diary'`）

- **源**：`diaries`（`page-diary.js:87 getDiaries()`）；
  单篇 `{id, content, timestamp, status, author:'user'|'char', charId?}`
- **可见性（复用）**：`author==='char'` → 比 `charId`；
  `author==='user'` → `lifeShare:<charId>.diary`（实读在 `life-feed.js:161-164 diaryShared`）
- **切块**：**一篇一块**
- **forget 联动**：`removeEntry`（`:117`）、`patchEntry`（`:109`）
- **写入时机**：写 / 改 / 删日记后

### 4.3 记忆档案（`kind:'mem'`）

- **源**：`charMem:<charId>`（`page-memory.js:109-115 loadCharMemory`）；
  条 `{id, charId, kind, content, source, status, isAnchor, ...}`
- **只接 `status === 'active'`**（`pending` 未确认、`invalid`/`superseded` 已废 → 都不进）
- **切块**：**一条档案一块**
- **可见性**：档案天然挂在 `charId` 下（每角色一份）→ 隔离已成立；但**要回源复核 status**
- **forget 联动**：`deleteMemoryItem`（`:220`）、`updateMemoryItem`（`:191`）、
  `invalidateMemoryItem`（`:250`）
- **写入时机**：`writeMemoryItems`（`:417`，总结引擎写完）/ 手工增删改后
- ⚠️ **与对话块内容重叠**：档案是对话提炼的，可能与对话块语义重复（v1 不去重，靠 `rank` 排）

### 4.4 查手机（`kind:'phone'`）

- **本轮只接三类**（§5 决议）：`phoneNotes`（备忘 → `'phone:note'`）/
  `phonePlans`（计划 → `'phone:plan'`）/ `phoneShop`（订单 → `'phone:shop'`）
  —— 最有叙事价值、「最像记忆」。
- **明确不在 v1 范围**（是**本轮不做**，不是"暂缓"）：
  - `phoneBrowser`（浏览）/ `phoneHealth`（健康）/ `phoneMsgs`（派生会话 + 草稿）
    —— 噪声大（搜个天气也会进库）；要做另开一批。
  - `phoneTraces` / `phoneSessions` / `phonePerms` —— 那是「**user 翻手机的痕迹**」，
    按方案 §2 **永远不进**（混淆会让 TA 记住他不该知道的事）。
- **可见性**：TA 自己的东西，**无权限概念**（只按 `charId` + 岛隔离）
- **切块**：**一条一块**
- ⚠️ **排序**：`list*` 全倒序（`phone.js:823-849`）→ 自己 sort 正序
- **写入时机**：查手机的 App 数据变更后

## 5. 决议（2026-09-23 用户拍板）

1. **配额分两池**：对话类（`chat/offline/group`）**300** ／ 素材类（`mem/diary/moment/phone`）**200**，
   各自淘汰。长期素材不会被近期聊天挤掉。
2. **查手机先接三类**：`phoneNotes`（备忘）+ `phonePlans`（计划）+ `phoneShop`（订单）
   —— 最有叙事价值、「最像记忆」。浏览 / 健康 / 派生会话与草稿**这一轮不接**（噪声大）。
3. **写入时机 = 变更时显式喊**（跟对话一致）：在「发布 / 删除动态」「写 / 改 / 删日记」
   「档案增删改」「查手机那三类变更」之后，调用一次对应的 sweep。
   **不用 `store.onChange` 统一监听**（时机隐式、出错难查）。

## 7. 冒烟要锁的契约红线（不是锁功能）

- **朋友圈方向**：`iHideFromChar=true` 时那条动态**不许**出现在该角色的召回里；
  `iHideChar=true` 时**照常出现**（反方向，别误伤）。
- **日记授权**：`lifeShare:<charId>.diary` 关掉后，user 的日记**不许**被召回。
- **档案状态**：`status !== 'active'` 的档案**不许**被召回。
- **删除即失效**：删动态 / 删日记 / 删档案后，对应块**必须**召回不到。
- **倒序源不出错**：phone 的倒序数组喂进去后，游标不重复、不漏块。
- **屏障**：有认知屏障的身份，只召回**按 `iso` 模式**该看到的块（见 §8.3 —— 原写法
  「只认 `charId` + `userId`」对档案 / 查手机是**错的**：那是他自己脑子里的东西，跨马甲共享）。

## 8. 评审修正（2026-09-23 · 五条，逐条核实后补）

> 来源：用户给的一份代码评审。五条**逐条对过代码，全部成立**。其中 8.1 / 8.2 会改设计。

### 8.1 修改旧条目不能只删块，要能**定向重建** ✅ 成立

**现状**：`forget`（`memory-vec.js:326`）是**删块不重切**，注释里写明这是**有意的取舍**
（重切要花钱 + 会切出与现有块重叠的新块；且「宁可召不回，也别让 TA 引用一句不存在的话」）。
对**对话**站得住：编辑通常发生在刚说过的话上（还在近期窗口、L2 总结兜得住）。

**对四源站不住**：改一篇两个月前的日记、改一条旧档案 —— 删块 = **永久失去**
（近期窗口兜不住、总结层也未必覆盖）。**这是本方案必须先解的问题。**

**解法**：新增

```js
reindexItem({ ownerKey, kind, sourceId, charId, userId, iso, item, lineOf })
```
流程 = **先按 `msgIds` 精确 forget 这条的旧块 → 再用 `blockerOne` 对单条重新切块 + embed + 写入**。
（**不是**喊普通 sweep —— 游标已经越过，普通 sweep 永远不回头。）

**挂点**：日记 `patchEntry`（`page-diary.js:109`）；档案 `updateMemoryItem`（`page-memory.js:191`）、
`toggleAnchor`（`:253`）；订单 `moveOrder`（`phone.js:810`）；计划 `movePlan`（`:526`）。
（动态本身**没有编辑功能** —— `page-moments.js` 全文无 `editMoment`，只有新增/删除。）

### 8.2 权限「关上 → 开启」要能补进来 ✅ 成立 —— 但解法是**改设计**

原设计是「**写入时**按可见性过滤」（只写这个角色能看到的）→ 权限放宽后**永远不补**。

**改法：全量建块 + 召回时过滤。**
一条数据只建**一个**块（**不按角色复制**），可见性**只在召回时判**（`visibleTo` + `stillVisible`）。
好处：
- 权限**收紧** → 召回时挡住 ✅（不用删块）
- 权限**放宽** → 召回时放行 ✅（**不用补扫**）
- 只有「**源数据被删**」才需要删块

→ **问题 2 从根上消失**；`stillVisible` 的职责也简化成「回源确认这条还在 + 现在还有权」。

⚠️ **一个真例外**：**认知屏障 / 马甲映射变化**。块的 `charId`/`userId` 是**建块时钉死的**，
映射一改（比如从「知道是同一人」变成「有屏障」），旧块的归属就不对了 →
**必须重建索引**（`resetCursors` + 清块，现有的 `vecEpoch` 正是干这个的，`memory-vec.js:579`）。
这一条要挂到「**改认知锁 / 改马甲**」的动作上。

### 8.3 `charId` / `userId` 落值 + 隔离语义 ✅ 成立（原卡只写了朋友圈，其余悬空）

**先定原则**：改成「全量建块」后，块里的 `charId`/`userId` 记的是**「这条数据属于谁」**，
**不是「谁在看」**。

**再定隔离模式** —— 关键：不同源的隔离口径本来就不同，**不能一刀切**：

| kind | 块里的 `charId` | 块里的 `userId` | `iso` | 理由 |
|---|---|---|---|---|
| `chat` / `offline` | 对话角色 | 对话的 user 身份 | **both** | 现状，不动 |
| `group` | — | — | **none** | 群消息对成员公开（现状） |
| `moment` | `null`（不是角色发的） | 发布动态的身份（maskId / 默认 user） | **user** | 屏障下「A 号发的动态」不该被 B 号身份关联到 |
| `diary`（user 写） | `null` | 写日记的身份 | **user** | 同上 |
| `diary`（char 写） | 作者角色 | `null` | **char** | 他自己写的，跟 user 用哪个号无关 |
| `mem`（档案） | 档案所属角色 | `null` | **char** | **他自己脑子里的东西**，跨马甲共享 |
| `phone` | 手机所属角色 | `null` | **char** | 同上 —— 他的手机不因我换号而不同 |

**实现**：块加字段 `iso`（缺省 `'both'` → **现有块与断言行为不变**），`visibleTo` 按它分流：

```js
function visibleTo(b, charId, userId, barrier) {
  if (!b) return false;
  if (!barrier) return true;                 /* 无屏障 → 整个大脑互通 */
  var iso = b.iso || 'both';
  if (iso === 'none') return true;
  if (iso === 'char') return b.charId === charId;
  if (iso === 'user') return b.userId === userId;
  return b.charId === charId && b.userId === userId;
}
```

### 8.4 `sourceId` 的粒度 ✅ 成立（原卡的写法会误删整个源）

原卡写「删除动态后按 `sourceId` 失效」，但 `sourceId` 在 `sweep` 里是**一次 sweep 的固定值**
（对话用 `chat.id`）→ 对四源会把**整个源**删掉。

**解法（复用 `forget` 的现有能力，不新增接口）**：
- `sourceId` 细到**子表**：`'moment'` / `'diary'` / `'mem'` / `'phone:note'` / `'phone:plan'` / `'phone:shop'`
- **条目 id 放块里的 `msgIds`**（裸 id）
- 删除时：`forget({ charId, sourceId: 'phone:note', ids: [noteId] })` ——
  `forget` 已支持这两个条件的**交集**（`memory-vec.js:348-350`）

⚠️ **phone 必须带子类型**：否则 `phoneNotes` 的 `m1` 与 `phoneShop` 的 `m1` 会**串源**。

### 8.5 `blockerOne` 空文本必须推进游标 ✅ 成立 —— 而且 `nextBlock` 有**同一个坑**

现在的循环（`memory-vec.js:603-608`）：
```js
var blk = (src.blocker || nextBlock)(msgs, from, src.lineOf);
if (!blk) break;                    // ← from 不推进
```
若从 `from` 起连续若干条 `lineOf` 都返回空，`blockerOne` 会 while 到末尾返回 null
→ **游标停在原地** → 下次 sweep 重扫同一段（不是死循环，但白扫、且永远不前进）。
`nextBlock` 同理（末尾全是空行时 `lines.length === 0` → 返回 null；
**群聊里「整段都是撤回消息」就会走到这里**）。

**解法：给 blocker 加「纯跳过」返回协议**
```js
var blk = blocker(msgs, from, lineOf);
if (!blk) break;
if (blk.skipTo != null) { from = blk.skipTo; continue; }   /* 这些不进库，游标推过去 */
made.push(blk);
from = blk.end;
```
`blockerOne` 全空时返回 `{ skipTo: messages.length }`；`nextBlock` 切不出任何有效行且已到末尾时同样。

**冒烟要加的断言**：
- 中间某条 `lineOf()` 返回空 → 能继续处理下一条
- 游标最终**越过**空条目
- 重跑**不产生重复块**

### 8.6 「一条一块」要处理超长条目 ✅ 成立

一篇长日记、一条评论很多的动态，**可能远超 embedding 的安全长度** —— `blockerOne` 现在**没有长度上限**，
超了要么被服务端悄悄截断（我们不知道截在哪）、要么直接报错。而"截断规则"目前**根本没定义**。

**修正原则**：
- **一个条目 = 一个逻辑事件包**（**不与其他条目合并** —— 这条不变）；
- **但允许条目内部切成多个分片**（同一个事件、同一 `sourceId`、共享 `itemId`）。

**实现**：分片**在构建 `messages` 时做**（各源的适配层），**不在 blocker 里做**（blocker 保持"一条一块"）：

```js
// 分片后的伪条目
{ id: 'diary123#0',      // ★ 片 id：唯一，游标用它
  itemId: 'diary123',    // ★ 条目 id：删除 / 整组淘汰用它
  seg: 0, segCount: 2,
  timestamp: …, text: '第一片正文' }
```

- `blockerOne` 的 `msgIds` 取 **`m.itemId || m.id`** —— 同一事件的所有片记**同一个条目 id**，
  一次 `forget({ids:[itemId]})` 删干净；游标仍走 `m.id`（片 id 唯一，`indexOfId` 不会找错）。
- 块新增字段 **`itemId` / `seg` / `segCount`**（整组淘汰 + 调试用）。
- **切点**：优先段落（`\n\n`）→ 句号 → 硬切；**片长上限** `SEG_CHARS`（默认 **1000**，与对话块同量级）。
- 片与片之间**不做重叠**（素材是"一件件的事"，重叠会导致重复注入）。

### 8.7 `stillVisible` 不许每块全表扫描 ✅ 成立

一次召回若有 N 个候选块，每块都调一次 `moments.all()` / `getDiaries()` → **N 次全表读**。

**修正**：一次召回**先建一份按 ID 的快照**，`stillVisible` 做 O(1) 查表：

```js
{ momentsById, diariesById, memoriesByCharAndId, phoneByTypeAndId }
```
快照**跟着 `prefetch` 的调用建一次、用完就丢**（不跨轮缓存 —— 否则权限改动看不见）。

**并且 fail closed**：读不到 / 字段残缺 / `kind` 不认识 / 源数据定位不到 → **一律不召回**
（**不**默认可见）。理由：索引里的原文是**给模型看的证据**，来源不明的东西宁可不用。

### 8.8 配额的键、未识别 kind、整组淘汰、设置页展示 ✅ 成立（前两条已对，后两条要补）

- **配额单位 = `ownerKey + pool`**（**不是**全库共用 300/200）—— 现有 `trim(ownerKey)` 就是
  「按 ownerKey 扫 + 分池」，**已经对了**；本卡写清，免得施工时误解成全局。
- **未识别 kind 的归属**：`poolOf` 用 `MEMO_KINDS` **白名单**，不在表里的**一律算 `chat` 池**
  （写死，不留"看情况"）。
- **同一 `itemId` 的分片要整组淘汰**（否则会"只剩半篇日记"，召回出来是残句）：
  `trim` 淘汰时**先按 `itemId` 分组**，超限时**整组一起丢**（组间按组内最新 `at` 排序）。
- **设置页要展示**：`当前数 / 上限 / 最旧块时间 / 各 kind 数量`（现在 `stats` 只有池级计数）。

### 8.9 冒烟再加 7 条 ✅ 全部采纳

1. 修改旧日记后：只召回**新**正文，旧正文**不再命中**；
2. 删掉动态评论后：旧评论文本**不再命中**；
3. 日记授权 `关 → 开` 后，历史日记**能召回**
   （验证 §8.2 的「全量建块 + 召回时过滤」真的做到了 —— **不需要补建**）；
4. 动态解除屏蔽后，历史动态**能召回**（同上）；
5. 同一角色面对**两个 userId / maskId** 时，块**不许跨身份召回**（`iso:'user'` 的正例）；
6. **phone 三种来源出现相同原始 ID**（都叫 `m1`）时**不互相覆盖**（`sourceId` 子类型生效）；
7. **超长日记**能分片、能**一次删干净**、且**不会与下一篇日记合块**。

## 9. 施工回执（2026-09-23 实施 · 与上面卡面的三处偏离）

> 完整交接见 `docs/交接-2026-09-23-向量补源.md`。这里只记**偏离**和**新增决议**。

### 9.1 本卡自相矛盾的一处：ownerKey 挂谁

§4.1 写 `ownerKey = rootOf(charId)`（按角色建块），§8.2 又要求
「一条数据只建一个块，**不按角色复制**」。动态不属于任何角色，两条不能同时成立。

**用户拍板（2026-09-23）**：朋友圈挂**岛级公共池** `island:<sandboxId>`，一条动态一个块。
四种 ownerKey 定稿：

| 池 | 主键 | 装什么 |
|---|---|---|
| 角色池 | `rootOf(charId)` | 对话 / 档案 / 查手机 |
| 群池 | `group:<groupId>` | 群聊（原有） |
| 岛池 | `island:<sandboxId>` | **朋友圈动态** |
| 账号池 | `user:<userId>` | **我写的日记** |

一次私聊召回合并「角色池 + 本岛池 + 本条账号池」（`poolsFor`）。

### 9.2 日记不是岛上的公共墙 —— 是**个人内容**（用户当场纠正）

方案 §5-2 本来就写着「日历/待办/日记属于 user 私密内容」，是本卡 §4.1 把它和动态归成了一类。改：

- `author==='char'` → `rootOf(角色)` + `iso='char'`
- `author==='user'` → `user:<账号>` + `iso='user'`

**连带**：日记数据结构里**连 `sandboxId` 都没有**（grep 全文 0 命中），
`getDiaries()` 的 `core.scoped()` 在有岛时反而会把日记全过滤掉。
已按用户决定「顺手补上」：`addEntry` 走 `core.tagScope` 盖 `sandboxId`，
user 写的再记 `userId`（当前马甲）；老日记建索引时兜底当前账号。

### 9.3 §3.2 的 `stillVisible` 表照抄会坏事 —— 收「当前召回的人」

表里写 `canCharSee(m, b.charId, b.userId)`，但 §8.3 又定 `moment` 的
`charId = null`。`canCharSee` 开头就是 `if (!m || !charId) return false`
→ 照抄的结果是**朋友圈一条都召不回**。

实际签名：`stillVisible(b, charId, userId, snap)`，收的是**当前召回的人**
（§8.2 改成「全量建块 + 召回时过滤」之后只能这样）。
另外**角色自己发的动态**落 `charId=该角色, iso='char'`，否则屏障下连他自己发的都召不回。

### 9.4 落地的挂点（都是「变更时显式喊」，§5-3）

`page-moments`（add/remove/removeComment）、`page-diary`（addEntry/patchEntry/removeEntry）、
`page-memory`（write/add/update/delete/confirm）、`phone`（addNote/addOrder/addPlan/moveOrder/movePlan）。
查手机 `applyDelta` 的四条写入路径已核过全覆盖；`fav`/`cart` 不入库（`listShop` 本就排除），不用挂。

### 9.5 一条**没做**的（请复核）

§8.2 说认知锁 / 马甲映射变化**必须重建索引**。实测判断**不需要**：
`barrier` 是每次召回现读 `core.cognitionOf` 的（`blocksOf` 内），开关立刻生效。
真正需要重建的是「块里 `charId`/`userId` 指向错了」，目前无此入口，
所以没挂自动重建、也没写用不上的 `rebuildChats()`。见交接文档同名小节。

### 9.6 已知未做

- **新增评论 / 点赞不重建块**（只做 §4.1 要求的 `removeComment`）——
  每条互动都重算 embedding 太贵。要准就调 `refreshMoment(momentId)`。
- 真机四项（倒序源游标 / 删除即失效 / 整组淘汰 / 端到端召回质量）**未验**
  —— node 没有 indexedDB，只能真机；见交接文档「待真机」。
