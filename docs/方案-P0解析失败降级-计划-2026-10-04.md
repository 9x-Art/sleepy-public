### 为什么报告里会写成「与轮 2 输出逐字相同」——**我的采集器有 bug**

```js
// 错误判据

// 然后：LATEST() 从后往前找最后一条 char/scene 当作「本轮输出」
```

`st.n > before` 因为 `before` 取的是「发消息前」的值、而失败轮不追加消息，
两个条件合起来仍被判成「已落地」→ 接着 `LATEST()` 抓到了**轮 2 残留的旧消息**。

**把不存在的东西当成了证据。**

## 二、数据结构设计

### 消息级：新增**两个字段**，都只挂在内存会话上

```js
// appendMessage 的 data 新增两个可选入参（沿用现有「有才写」的模式）
if (data.parseFailed) msg.parseFailed = true;
if (data.rawReturn != null) msg.rawReturn = String(data.rawReturn);
```

**关键设计点**：

| 字段 | 存哪 | 进 paras 正文？ | 进历史回灌？ | 进下一轮上下文？ |
|---|---|---|---|---|
| `parseFailed: true` | 消息对象 | ❌ | ✅ 可（只有一个标记词） | ✅ |
| `rawReturn: "<原始返回>"` | 消息对象 | ❌ **绝不** | ❌ **绝不** | ❌ **绝不** |

**`rawReturn` 的隔离是本方案的核心**，三条都不许破：

1. **不进 paras** —— `parasText()` 只 map `p.text`，
   原始返回**不作为任何 `p`**，所以 `fillMessages` 渲染不到它、
   `blockFor` 也不会画它。
2. **不进历史回灌** —— 历史回灌走 `parasText(paras)` 拼 assistant 内容。
   只要**不塞进 paras** 就自动隔离。
3. **不进下一轮上下文** —— 装配层只读 `m.paras` / `m.text` / `m.role`。
   `rawReturn` 是**新字段**，装配层不认 → 自动不进。

> ⚠️ **必须显式验证第 3 条**：跑一次真实出站，探查 `built.messages`
> 里**搜不到**原始返回的任意片段。这是本方案唯一的隐含假设，
> 必须在施工后立刻验，不能靠推理。

### 渲染层：`blockFor` 加一个分支

```js
if (m.parseFailed) return parseFailedBlock(m);
```

放在 `blockFor` 的**最前面**（`scene` / `user` / `photo` 之前），
因为这种消息既不是 `scene` 也不是正常 `char`。

### 新增两个渲染函数

```js
/* 解析失败：正文只给一句人话 + 一个默认折叠的「查看原始返回」 */
function parseFailedBlock(m) {
  var b = h('div', 'off-parsefail');
  b.appendChild(h('div', 'off-parsefail-hint',
    '这一轮没能读懂模型的回复格式，先原样收着。'));
  var d = h('details', 'off-parsefail-fold');       // <details> = 默认折叠
  d.appendChild(h('summary', 'off-parsefail-summary', '查看原始返回'));
  d.appendChild(h('pre', 'off-parsefail-raw', m.rawReturn || '（空）'));
  b.appendChild(d);
  return b;
}
```

用原生 `<details>`：**默认折叠**不需一行 JS，和诊断面板
`h('details', 'off-diag-fold')` 是同一个既有模式（照抄，不发明新写法）。

### 降级消息的字段取值

```js
appendMessage(id, {
  role: 'char',                    // 保留 char —— 历史回灌时它是「他说/她想」的容器
  paras: [{ type: 'prose', text: '（这一轮没能读懂格式）', trans: null }],
  parseFailed: true,
  rawReturn: r.text
});
```

⚠️ **`paras` 里只放一句中性的失败说明，不放任何原始内容。**
这样：
- 正文渲染是干净的（不会出现裸 JSON）
- 历史回灌里是「（这一轮没能读懂格式）」，模型不会把裸 JSON 学走
- 长度可控，不会有几万字进上下文

### 不写诊断

`diagRecord` 的字段**一个都不加**，`requestOk` 照旧为 `true`
（请求**确实成功了**，只是没解析出来 —— 这是两件事）。
**`rawReturn` 不进诊断**（诊断是纯内存白名单字段，异常全文一律不记）。

## 三、施工前必须先定的一个问题（**可能影响方案**）

重跑组 2 时暴露了一个**原先被采集 bug 掩盖**的问题：

| 轮 | 诊断 stage | 原始 `requestOnce` 结果 | 有无输出 |
|---|---|---|---|
| 1 | `model-returned` | `{ok:true, len:521}` | ✅ len=86（正常） |
| 2 | `model-returned` | `{ok:true, **len:0**}` | ❌ **无** |
| 3 | `model-returned` | `{ok:true, **len:0**}` | ❌ **无** |

组 3 轮 1「我没事」同样是 `{ok:true, len:0}`。

**HTTP 200 但内容为空** —— 这不是协议格式坏，是**模型返回了空字符串**。
`parseOfflineReply('')` 走的是 `if (!text) return {ok:false, paras:[], ...}`
→ `paras.length === 0` → **既不 append 也不提示**，用户看到的是
「发出去什么都没发生」。

⚠️ **这是与 P0 同类的用户可见问题，但触发点不同**（空内容 vs 语法坏）。
**本轮计划只做你指定的「解析失败可见降级」**，`len=0` 怎么处理**需要你定**：

- 选项 A：并入本方案 —— `ok === false` 一律走同一条降级路径（推荐，代码更少）
- 选项 B：本轮只做语法坏，空内容另开一批（严格贴合你本轮的字面要求）

我倾向 **A** —— 两者对用户来说是同一个现象（「模型回了个看不懂的东西」），
分成两条路径会让代码多一倍、日后还得再合。
