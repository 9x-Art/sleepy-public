## 2. 纪念日实际调用链与绑定前后状态

### 调用链

```
page-calendar.js:619  openAnniversarySheet 的「让他记住这一天」
  → calendar.js:1126  saveAnniversary(charId, mem, opts)
      → :1056  ownedMemory(charId, memId)      三道闸，任何一道不过 → 什么都不发生
      → :1140  requestCreateEvent(payload, {
                   requestKey: 'anniversary:' + sandboxId + ':' + memoryId,
                   allowConflict: true,          ← 纪念日是留痕标记，不占时间
                   authorizedVia: 'anniversary_sheet' })
          → :864  addEvent(rec)                 唯一落库点
      → :1197  updateMemoryItem(charId, memId, { calendarEventId })
```

### 入口边界三道闸（`calendar.js:1056 ownedMemory`）

| 闸 | 错误码 | 挡什么 |
|---|---|---|
| `!memId` | `no-memory` | 没绑留痕的纪念日 |
| 当前岛名册里查不到 | `no-such-memory` | 伪造 id、**跨岛留痕** |
| `rootIdOf` 对不上 | `memory-not-owed` | 本岛但属于别的角色的留痕（迁移残留那种） |

**跨岛为什么能被这道闸挡住**：`memoryFile` 走 `charMem:<root>`，跨岛根本不在同一份文件里。
`no-such-memory` 就是跨岛的正确结论。

### 幂等键

`anniversary:<sandboxId>:<memoryId>` —— **去掉了进场时那个 `charId + date + title` 弱键**。
带 sandboxId 是因为同一句留痕在两个岛各自算一天。

### 绑定前后状态

```
保存前：memory = { id, charId, content, isAnchor, sourceRef }   ← 没有 calendarEventId
保存后：event  = { id, eventType:'anniversary', memoryId, sourceIds, requestKey,
                  authorizedVia:'anniversary_sheet', sourceType:'memory',
                  meaningType:'char_subjective', visibility, repeatRule:'yearly' }
        memory.calendarEventId === event.id                    ← 本轮新补的那一半
```

`page-memory.js:282 updateMemoryItem` 原来字段白名单只有 `content/status/isAnchor`，
**`calendarEventId` 会被静默忽略** —— 绑定等于没写。本轮开了这个口，并让它
**不进向量重建**（改的是 id 指针不是内容，白跑一次 embedding 是纯浪费）。

## 4. 帷境实际调用链、审阅确认语义与 requestKey

### 调用链与授权边界

```
page-wj-canon.js:321  唯一调用方：第四步那个「写入现实（n 条）」按钮的 onclick
  （页面上只调 CAN().plan() —— 纯预览，注释明写 return 不写盘）
  → wj-canon.js:319  write(workId)
      → 留痕：writeMemoryItems（按 content+source 去重，重跑不写第二份）
      → calendar.requestCreateEvent({
            requestKey: canonRequestKey(workId, candId, charId),
            allowConflict: true, historical: true, authorizedVia: 'review_desk' })
```

**审阅台确认是否等价于「用户确认执行」——是**，依据有两条：
1. `page-wj-canon.js:320` 那个按钮是唯一调用点（静态护栏断言该页 `.write(` 恰好 1 次）；
2. `plan()` 与 `keptOf()` / `writersOf()` 全是纯读，无头 Edge `C4` 实测打开审阅台
   `calEvents` 零增长。

`historical: true` 的理由写进注释了：定史记的是**已经发生**的事，不存在「等他表态」，
没有它会被强制成 pending 邀请，语义正好反了；该开关同时要求作者必须是 user。

### requestKey

`wjcanon:<workId>:<candId>:<charId>` —— 稳定可复算，导出了 `canonRequestKey` 供断言。
比进场时（只靠 `rec.written` 一个整批标记）多一层：**中途失败再跑，已写进去的不会重写。**

### `rec.written` 何时成立

| 情形 | `written` | `writtenPending` | 返回 |
|---|---|---|---|
| 留痕都在 + 日历全落成 | `true` | `false` | `ok:true, written:true` |
| 留痕写了 + 日历**部分失败** | **`false`** | `true` | `ok:true, written:false, writtenPending:true` |
| 留痕写了 + 日历**全失败** | `false` | `true` | 同上，`evFailed` 逐条列出 |
| 一条都没落地 | `false` | `true` | `ok:false, why:'nothing-written'` |

**判据是「逐条回查留痕是否真在记忆库里」**（`wj-canon.js:465 memAllThere`），
不是「这次新建了几条」。这一点是本轮抓到的真 bug，详见 §6。

`rec.eventRefs` 存真实 `eventId`（`[{cand, charId, eventId, dup}]`）——
「正史与日历引用一致」要能查证，不能只有一句「写好了」。

**纪念日重复（有差异）**：

          message:'这条留痕已经标过日子了，改不了名字（现在是「…」）、日期（现在是 2031-05-20）。要去日历里改那一条。' },

## 6. 本轮抓到的两个真 bug

### ① 统一入口的 dup 分支不返回 `event`

`calendar.js:844` 原来只回 `{ok, eventId, dup:true, receipt}`，**没有 `event`**。
重跑的人拿不到事件对象 —— `saveAnniversary` 重试时没法补写绑定，也没法核对字段。
冒烟里「第二次保存的 title 读不到」当场暴露。已补：`event: hit`。

「已经建过」是一条完整的成功答复，不该是半截的。

### ② 帷境重跑补日历的死循环

进场时的写法是 `r.written = !!(n > 0 && allCalOk)`。重跑时因为留痕已写、被去重跳过，
**`n` 恒为 0** —— 于是「日历补上了」永远被判成「没写完」，
而「没写完」又永远不放行重跑。**补不上日历。**

改成 `complete = memAllThere && allCalOk`：`memAllThere` 是**逐条回查记忆库**
（不信自己刚写的结果，正如施工单 §2「不得信任模型自报」）。
修完无头 Edge 与冒烟都验到「重跑补上 1 条、留痕仍只有 1 份」。

> 教训：`n > 0` 表达的是「这次新建了几条」，不是「这批落地了没有」。
> **增量语义 ≠ 完成语义** —— 凡是「完成」判定，别用「本次新增量」当判据。

### ③（附带）产品语义分歧，已问你后定

同一条留痕第二次保存时用户改了标题/日期：进场时的实现会**静默沿用旧值**并报成功，
用户的输入被悄悄扔掉。施工单 §1 要求先确认产品是否允许一条留痕多个纪念日实例 ——
不允许，于是用稳定 key。但稳定 key + 静默沿用 = 吞输入。

**你选了「拒绝并说明」**，已实现（`calendar.js:1191 already-marked`）：
明确拒绝 + 说清差在哪 + 不建第二条 + 事件不被偷偷改；
无差异的重跑仍是正常 dup。`page-calendar.js:625` 原有 `r.error.message` 弹窗已能如实显示，**未改 UI**。

## 8. 是否新增 action 状态或补偿状态

- **`action.js` 一行没动**（`KINDS` 仍只有 `calendar.create_event`），
  纪念日与帷境都**不经过 action 层** —— 它们是内部适配路径，不是用户逐次确认的独立动作，
  走 action 只会多一层无意义的 request 记录。施工单 §5「仅在帷境需要时接既有 action」→ 不需要。
- 新增的**补偿状态**（都在 `wjCanon` 记录里，不进新表、不进 `core.js` 删房名单）：
  `writtenPending: boolean`、`calendarFailed: [{cand, charId, err}]`、`eventRefs: [{cand, charId, eventId, dup}]`。
- 纪念日侧：只有返回值的 `bindOk: boolean`（绑定回写是否成功），**没有新增持久化状态**。
